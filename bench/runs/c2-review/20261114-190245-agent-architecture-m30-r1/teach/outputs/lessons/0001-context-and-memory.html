The context window 5 min

A language model reads text as tokens, small pieces of text, roughly a short word or part of a word. The context window is all the text the model can use when it writes a response, and it includes the response itself; the documentation calls it the model's "working memory" (Claude docs: context windows). The set of tokens in it is the model's context (Anthropic: effective context engineering).

Analogy from soccer: the context window is the pitch at one moment. Only the players on the pitch can touch the ball. A player on the bench, or one who played last season, contributes nothing unless the coach brings them on. Whatever the model needs to answer, you must put on the pitch for that call. The bench is storage outside the window (notes, the manuals); retrieval is the coach choosing which bench players to send on for this play.

Everything you send counts toward the window: the system prompt (the standing instructions), every message so far, including tool results, and the tool definitions; the output counts too (Claude docs). So for the makerspace assistant, the window holds the rules you wrote, the description of each tool, the student's question, each tool's result, and the answer being written.

Two limits follow. The first is a hard size: the same page lists 1M tokens for current Claude models and 200k for some older ones, and a request whose input alone exceeds the window is rejected with an error.

The second is softer and matters more for your design. Context rot is the loss of recall as the context grows: more tokens means less accurate use of any single one. Anthropic describes context as "a finite resource with diminishing marginal returns" and sets the goal as "the smallest possible set of high-signal tokens" (Anthropic). Cost is the third limit: you pay for the tokens you send, and the model reads all of them every time.

Window sizes change with model releases; check the current docs page rather than trusting any number in a lesson. Your team's decision does not depend on the exact size, because cost and rot arrive long before the limit. Prompt caching can lower the price of the repeated prefix, so the cost figures later are an upper bound; the growth in tokens read still holds.
A common mix-up

"With a window of a million tokens, I can paste all the manuals in and skip the design work." It is tempting because a bigger limit sounds like a bigger brain. But the limit says what fits, not what is used well: recall degrades as the context grows, and a 300,000-token context is billed at 300,000 tokens on every call. A window is a budget, not a goal.

Check yourself

A student's question is 40 tokens. The system prompt is 700, tool definitions total 900, and the assistant's answer will be 160. Roughly how many tokens does this single call use against the window?

Show the answer

1,800. Input is 700 + 900 + 40 = 1,640; the 160-token answer is output; both count: 1,640 + 160 = 1,800.

What is kept between steps 5 min

Here is the fact that surprises most people: the model keeps nothing between calls. Each call is a fresh computation on whatever text you send. What looks like the agent "remembering" step 1 at step 3 is the program sending step 1 again. The docs describe each turn's input as containing "all previous conversation history plus the current user message", and the output "becomes part of the input for the next turn" (Claude docs). The program keeps the history in an ordinary Python list and resends it.

In code, the agent loop you already know looks like this. The only memory between steps is the list messages:

messages = [{"role": "user", "content": question}]   # the whole "memory"

steps = 0
while steps < MAX_STEPS:
    reply = call_model(system=RULES, tools=TOOLS, messages=messages)  # sends ALL of it
    messages.append(reply)                      # keep the model's output
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_request)       # the program runs the tool
    messages.append(tool_result_message(result))  # keep the tool result
    steps += 1

Because each call re-reads everything, the input grows with every step, and the total tokens you pay for grows faster than the length of the conversation. If call k reads nk tokens, the bill is the sum of all nk, not the final length.

With a fixed overhead F (system prompt plus tool definitions) and each step adding about s tokens, call k reads roughly F + k·s, so m calls cost about m·F + s·m(m+1)/2: linear in the fixed part, quadratic in the growing part. Long agent runs are expensive for this reason.

Numeric case: F = 2,000 and s = 500. Three calls read 2,500, 3,000 and 3,500 tokens, which is 9,000 (3 × 2,000 + 500 × 6). Ten calls read 2,500 up to 7,000, which is 47,500 (10 × 2,000 + 500 × 55). Ten steps cost 5.3 times as much as three, not 3.3 times. For a three-call request like the one below, fixed overhead and one large tool result dominate; the quadratic term matters in runs of ten or more steps.

Everything that sits in messages is therefore a design choice. Anthropic names a light fix, tool result clearing (dropping old tool results once the agent no longer needs them), and a heavier one, compaction: "taking a conversation nearing the context window limit, summarizing its contents, and reinitiating a new context window with the summary" (Anthropic). For a makerspace question that needs three tool calls, you will rarely need either; a step limit and small tool results are enough.

A common mix-up

"The assistant remembers what I told it a minute ago because the model has memory." What it has is a list that your program resends. If your program builds messages fresh for each request, the model has no idea the earlier turns happened. Nothing is automatic; memory is whatever your code chooses to keep and send.

Check yourself

A student chats with the assistant for ten turns, and your program accidentally starts messages from scratch on turn 11. On turn 11 the student says, "Book it for the time we agreed." What happens?

Show the answer

The model cannot know the time. The conversation existed only in the list the program resent; when the list was dropped, the information was gone. This is why the program, not the model, owns memory.

What is kept between sessions: notes 6 min

A session is one run of the agent for one student visit, from the first message until the program ends. When it ends, the Python list is garbage-collected. A student who returns next week starts with an empty context. To remember anything across visits, the program must save it somewhere outside the context window and load the relevant part next time. That saved information is the agent's memory in the practical sense.

The simplest design is structured note-taking: the agent writes notes to storage outside the window and reads them back later, for example a to-do list or a NOTES.md file (Anthropic). You are using this pattern right now: this workspace's NOTES.md is how a tutor remembers you between sessions.

Anthropic ships this as a memory tool. It "lets Claude store and retrieve information across conversations in a directory of memory files", and it "operates client-side: Claude requests file operations, and your application runs them" (Claude docs: memory tool). Client-side means your program does the work, not Anthropic's servers. That is the same split you learned in the loop: the model asks, your program acts. The operations are view, create, str_replace, insert, delete and rename, on files under /memories. The docs add a security warning: your handler must confine every path to that directory, since a path such as /memories/../../secrets.env could otherwise escape it.

A minimal version for the makerspace assistant is two ordinary functions. The student id picks the file, so each student has a separate store:

from pathlib import Path

# student_id must come from your own system, never raw user text, or ../ could escape the folder
def load_notes(student_id):
    f = Path("memories") / f"{student_id}.md"
    return f.read_text() if f.exists() else ""      # empty for a first visit

def save_notes(student_id, text):
    Path("memories").mkdir(exist_ok=True)
    (Path("memories") / f"{student_id}.md").write_text(text)

# start of session: put the notes on the pitch
messages = [{"role": "user", "content": f"Notes on this student:\n{load_notes(sid)}\n\nQuestion: {q}"}]
# end of session: the model (or your code) writes a short update
save_notes(sid, updated_notes)

This version loads the notes for the model. With the memory tool the model asks to view them, and your handler does the same work.

Not everything belongs in notes. Compare three facts the assistant must know:

Your notes say the assistant must remember each student's training status. The table gives the answer: training status is a database lookup done by a tool such as check_training_record, because a safety decision should rest on a record, not on a note a model wrote last month. Use notes for preferences and progress.

Two cost rules for notes. Keep them short, since they are loaded into context on every visit and every call re-reads them (section 2). And decide who writes them: letting the model write freely is flexible but can accumulate errors; having your code write fixed fields is rigid but predictable.
A common mix-up

"Memory is something the model does, so it is the model's job to get it right." The model only requests reads and writes. Your program stores, protects, limits and loads them. If the notes grow to 20,000 tokens, that is a design problem in your program, and you pay for it on every call.

Retrieval: finding the right page 6 min

The machine manuals are shared, long and too big to put in context every call (section 1). Retrieval means fetching only the few pieces that matter for this question and placing them in context. This is memory for knowledge instead of for a person. The standard pipeline has four steps:

  1. Chunk each manual into pieces, such as a section of about 1,000 tokens. A chunk is one such piece.
  2. Embed each chunk: an embedding is a list of numbers (a vector) produced by a model so that texts with similar meaning get similar vectors. Do this once, ahead of time.
  3. Compare the question's embedding with each chunk's using cosine similarity, the cosine of the angle between two vectors: 1 means the same direction, 0 means unrelated.
  4. Take the top k chunks (k is how many of the best-scoring chunks you keep, say 3) and place them in the tool result, so the model reads those and nothing else.

A numeric case with two-dimensional vectors, small enough to compute by hand. Suppose axis 1 means "laser settings" and axis 2 means "booking rules". The question "What power for 3 mm acrylic?" embeds to q = (1.0, 0.0). Chunk A (a settings table) embeds to (0.9, 0.1); chunk B (cancellation policy) to (0.2, 0.9).

  • cos(q, A) = (1.0·0.9 + 0.0·0.1) / (|q|·|A|) = 0.9 / (1 · 0.906) = 0.994
  • cos(q, B) = (1.0·0.2 + 0.0·0.9) / (1 · 0.922) = 0.2 / 0.922 = 0.217

Chunk A wins by a wide margin, so it goes into context and B stays out. Real embeddings have hundreds or thousands of dimensions, but the arithmetic is the same.

A common mix-up

"Retrieval finds the right answer." It finds the chunks closest in meaning to the question, and a close chunk is not always the correct one. If the manual had a chunk about 3 mm acrylic for a different machine, it would score nearly as high as chunk A. Retrieval ranks; the model still has to read the chunks and check that they apply.

Where does retrieval run? Two designs, described in Anthropic's post (the names here are this lesson's labels). In up-front retrieval the program embeds the question and retrieves chunks before the model is called. In just-in-time retrieval the agent holds lightweight identifiers and loads data at runtime with tools, such as a search_manuals(query) tool: this is slower and needs a good tool description, but the model decides what to look up.

Anthropic's advice is "do the simplest thing that works" (Anthropic). For your assistant a search_manuals tool fits naturally into the loop you already have, and a question that needs no manual (a calendar check) simply does not call it.

Retrieval can fail silently: if chunking splits a safety warning from the procedure it belongs to, the right chunk is retrieved without its warning. Chunk by section, and test with real student questions.
Check yourself

With vectors as above, a question embeds to q = (0.0, 1.0). Which chunk is retrieved first, A = (0.9, 0.1) or B = (0.2, 0.9)?

Show the answer

Chunk B: cos(q, B) = (0·0.2 + 1·0.9) / 0.922 = 0.976, against cos(q, A) = 0.1 / 0.906 = 0.110.

Worked example and practice 5 min

Now combine sections 1 to 4 into the quantity you will defend at the review: the input tokens a request consumes.

Worked example

The student asks: "Is the laser cutter free tomorrow at 3 pm, and what power for 3 mm acrylic?" Fixed overhead: system prompt 800 tokens, tool definitions 1,200, question 50. The model calls check_calendar (request 60 tokens, result 300), then search_manuals (request 60, result 3,000: the top three chunks), then writes the final answer (150). What total input tokens are billed across the three calls?

  1. Call 1 reads the overhead and the question: 800 + 1,200 + 50 = 2,050. It outputs a 60-token tool request.
  2. Call 2 re-reads call 1's input, plus the request and the calendar result: 2,050 + 60 + 300 = 2,410. It outputs a 60-token request.
  3. Call 3 re-reads call 2's input, plus the request and the manual chunks: 2,410 + 60 + 3,000 = 5,470. It outputs the 150-token answer.
  4. Total input = 2,050 + 2,410 + 5,470 = 9,930 tokens, plus 270 output tokens (60 + 60 + 150).
  5. At an illustrative price of $3 per million input tokens (not a real quote), that is 9,930 × $3 / 1,000,000 ≈ $0.03 per request.

Notice that the 2,050 tokens of call 1 are paid for three times, because they sit inside every later call. Figure 2 shows the same totals.

Your turn

Same request and numbers, but the team skips retrieval and the search_manuals tool returns the whole 30,000-token laser cutter manual instead of 3,000 tokens of chunks. The model then writes the final answer in call 3. Step 1 is given: call 1 still reads 2,050 tokens. Find call 2, call 3, the total, and the ratio of the new total to the 9,930 above.

Show a solution

Call 2 is unchanged: 2,410 (nothing yet differs). Call 3 = 2,410 + 60 + 30,000 = 32,470. Total = 2,050 + 2,410 + 32,470 = 36,930 tokens. Ratio = 36,930 / 9,930 ≈ 3.7, so the request costs about 3.7 times as much, and the model must also find two sentences inside 30,000 tokens, where recall is weaker. Retrieval earns its place on cost and on accuracy.

Budget (part of the same 5 minutes)

Your turn: budget

Use the illustrative price of $3 per million input tokens. A $20 budget buys how many requests of the 9,930-token version, and how many of the 36,930-token version? Count input tokens only.

Show a solution

$20 buys 20 / 3 = 6.67 million input tokens. With retrieval: 6,670,000 / 9,930 ≈ 671 requests. Without retrieval: 6,670,000 / 36,930 ≈ 180 requests. Retrieval gives about 3.7 times as many requests for the same money, which is the argument to make to your sponsor. Replace $20 with your sponsor's real figure.

Summary 1 min

  • The context window is all the tokens the model uses in one call: instructions, tool definitions, history, tool results and its own output. It is a budget, limited by size, by recall (context rot) and by cost.
  • Between steps, the model keeps nothing; your program keeps a list and resends all of it, so each call re-reads every earlier call's tokens. The bill is the sum of all calls and rises faster than the conversation length; one large tool result is repeated in every later call.
  • Between sessions, only what your program saves survives. Notes suit soft, personal information; records that matter, such as training status, belong in a database read by a tool.
  • Retrieval puts only the best-matching chunks of a long manual into context, which cuts cost and improves recall.
