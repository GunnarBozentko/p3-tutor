Context and memory: what the assistant sees, keeps and looks up

By the end of this lesson you can decide, for each fact in a makerspace request, whether it belongs in the assistant's context, in saved notes between sessions, or in a manual it retrieves on demand.

Objective O3: context and memory in an agent About 30 minutes Builds on learning record 0002, "An agent is a model called in a loop, with tools and a way to stop"
Why this matters for you

Your assistant must answer from long machine manuals, remember each student between visits, and stay inside a small model budget. All three problems are decisions about context and memory, and you will defend those decisions at your design review.

Check your answer

The model knows only what it learned in training plus the text it is given. Its training stops at a date, and it writes plausible text whether or not it is true. Everything in this lesson is about the second part, the text it is given.

Tokens and the context window 4 min

A token is the chunk of text a model reads and writes: a short word, part of a longer word, or a piece of punctuation. In English, one token is roughly three quarters of a word, so 100 words is about 130 tokens. That is a common rule of thumb; your provider's token-counting tool gives exact counts. Models are measured, limited and billed in tokens, not in words.

The context window is all the text a model can reference when it generates a response, including the response itself. The Claude documentation calls it the model's working memory, as distinct from the data it was trained on. Think of the model as a soccer coach who forgets everything the moment each decision is made. Before every decision, staff hand the coach a clipboard with a fixed number of lines: that clipboard is the context window. The coach can use only what is on it.

Per the same documentation, everything in one request counts toward the window: the system prompt, every message, every tool result (the text a tool returns to the program), the tool definitions, and the model's own output. This lesson calls each model call a step. The system prompt is the standing instructions you write, such as "You are the makerspace assistant." A tool definition is the written description of a tool that the model reads in order to choose it.

Numeric case. Suppose the system prompt is 800 tokens and your four tool definitions total 1,400 tokens. Before the student has typed a word, 2,200 tokens are already spent. If the student's question is 30 words, about 40 tokens, the first request holds roughly 2,240 tokens. This fixed overhead is why a long, wordy tool description costs money on every single call.

What is kept between steps 5 min

The model itself keeps nothing between calls. Each call is a fresh computation on whatever text the program sends. The documentation spells out the pattern: each turn's input contains all previous conversation history plus the current message, and the output becomes part of the next turn's input.

The program keeps a list of everything so far and resends the whole list on every step. In the clipboard picture, the staff photocopy the whole clipboard and hand it over again before each decision.

messages = [{"role": "user", "content": question}]

while True:
    reply = call_model(system=SYSTEM, tools=TOOLS, messages=messages)  # whole list sent
    messages.append(reply)                      # the model's request joins the history
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_request)       # the program runs the tool
    messages.append(result)                     # the result joins the history

The list messages is the only thing that carries information from step to step. If you did not append the tool result, the model at the next step would never know the tool ran. This is what "kept between steps" means: not model memory, but a list your program maintains and resends.

Cost, worked out

Input tokens are the tokens in the request you send; output tokens are the tokens the model writes back. The assistant starts with 2,200 input tokens (system prompt, tools and the question). Each step adds about 1,000 tokens: the model's request plus a tool result such as a manual excerpt. The assistant takes five calls.

  1. Input to call k is 2,200 + 1,000 (k − 1), so the five calls read 2,200, 3,200, 4,200, 5,200 and 6,200 tokens.
  2. The total is an arithmetic series: n·a + d·n(n − 1)/2, where n is the number of calls, a the first call's input and d the tokens added per step. Here 5 × 2,200 + 1,000 × 10 = 21,000 input tokens.
  3. At an illustrative price of $3 per million input tokens, that is 21,000 × 3 / 1,000,000 = $0.063 per request.
  4. The last call alone holds only 6,200 tokens, so the billed total is more than three times the final context size.

This counts input only. Output tokens are billed separately, usually at a higher price per token. The $3 is a made-up round number; use your provider's real price list.

Proof that the history grows with the square of the steps: the input to call k is a + d(k − 1), so the sum over k = 1..n is n·a + d·(0 + 1 + ... + (n − 1)) = n·a + d·n(n − 1)/2. The first term is the fixed prompt paid n times. The second is d·n²/2 − d·n/2, which grows as n² for large n.

Check: 10 calls read 10 × 2,200 + 1,000 × 45 = 67,000 tokens, which is 3.2 times the 21,000 for 5 calls, although the call count only doubled. Prompt caching, a provider feature that charges less for a repeated prefix, lowers the price but not the size: the documentation states that cached prompt prefixes still occupy the context window.

A common mix-up

"The model remembers what happened in the earlier steps." It is tempting because a chat feels like one continuous conversation. But the model is called afresh each step. Remove the first tool result from the list you send, and the model behaves as if that tool never ran.

When the window fills up 4 min

A 300-page manual is about 150,000 tokens. Even if it fits in the window, pasting it into each of five calls costs about 5 × 150,000 + 21,000 = 771,000 input tokens, or $2.31 per request at the illustrative price. That is about 37 times the $0.063 of a design without the manual. Fitting in the window and being affordable are different questions.

A bigger window does not make the problem go away, for two reasons. First, cost grows as shown above. Second, quality can fall: Anthropic's engineering team describes context rot, where as the number of tokens grows, the model's ability to recall information from that context decreases (Effective context engineering for AI agents).

The same post advises finding the smallest set of high-signal tokens that gets the job done. An input larger than the window is rejected with a "prompt is too long" error, according to the context-window documentation.

Two tools keep the list small. Compaction takes a conversation nearing the limit, summarizes it, and starts a new window with the summary. Clearing removes old tool results that the model no longer needs; the post calls this one of the safest, lightest-touch forms of compaction.

Both lose detail, so the post advises first maximizing recall, then trimming for precision. Recall is the share of the relevant information that is kept; precision is the share of the kept information that is relevant. A statistical parallel: compaction is like replacing a dataset with its summary statistics. The 5,000-token dialogue is the dataset, the 600-token summary is the mean and standard deviation, and an outlier lost in the summary is a dropped fact.

Compaction, worked out

After 12 steps, a booking conversation holds 14,000 tokens of messages. Most of it is three long manual excerpts the student no longer asks about.

  1. Clear the three excerpts, about 9,000 tokens, but keep a one-line identifier of each, such as "laser cutter manual, page 14".
  2. Summarize the remaining discussion into about 600 tokens: the student's goal, the booking made, and open questions.
  3. Clearing leaves 14,000 − 9,000 = 5,000 tokens of dialogue. Summarizing that into 600 tokens cuts it by a further 4,400, so about 600 tokens now carry the whole story. The 2,200 tokens of system prompt and tool definitions stay, so the window drops from 16,200 to about 2,800 tokens, a cut of about 83%. The excerpts can be fetched again by identifier if needed.

In the clipboard picture, when the clipboard is nearly full, the staff rewrite it as a short summary. If the summary drops one fact that mattered, such as a player's earlier red card, the next lineup decision goes wrong. That is the risk of compaction.

What is kept between sessions: notes 4 min

A session is one conversation from start to finish. Dana says on Monday, "I like evening slots." On Friday she opens a new session, and the window is empty. The preference survives only if it was saved outside the window. In an agent, "memory" is therefore three different things. The context window is short-term memory: it holds this session's messages. Saved notes are long-term memory of one student: written by the agent, read back at the start of the next session. Retrieval is a lookup in a reference library: the manuals do not change per student, and only the relevant chunk is loaded. The window is the only one the model reads directly; the other two work by placing text into it.

When a session ends, the list of messages is gone. The next visit starts with an empty window, so anything the assistant should know next time must be saved outside the window and loaded back in.

The engineering post calls this structured note-taking: the agent regularly writes notes persisted to memory outside the context window and pulls them back in later (Anthropic). A to-do list or a notes file are its examples. In the clipboard picture, the scouting binder in the club office, kept between matches, is the saved notes.

For you, that is a small store, a JSON file or database table keyed by student, that your program reads at session start and writes at session end:

notes = load_notes(student_id)          # {} for a first visit
system = SYSTEM + "\nSaved notes about this student:\n" + json.dumps(notes)
# ... run the loop ...
save_notes(student_id, updated_notes)   # e.g. {"prefers": "evening slots"}

Notes cost tokens on every call too, so keep them short and useful: preferences, open requests, and what was already explained. Cost check: 10 notes of 20 tokens each add 200 tokens to every call. Over five calls that is 1,000 input tokens, or $0.003 at the illustrative price. A good note is {"prefers": "evening slots", "open_request": "band saw booking Fri"}. A bad note is a pasted transcript.

Notes are copies, not records

A note is a summary written by the model, so it can be wrong, stale, or missing. An everyday parallel: a sticky note on the fridge says "rent paid", while the bank statement is the record. To decide whether to pay again, you read the statement, not the note. The sticky note is the saved note, the bank statement is the training record, and a roommate saying "rent paid" is the student saying "I finished the training."

A common mix-up, with a safety edge

"The notes say Dana is trained on the laser cutter, so the assistant may book it." A note is a copy. The training database is the system of record, the one source that is officially correct, kept by whoever is accountable for it, and the assistant must read it through a tool at the moment of the decision, such as check_training_record(student_id, "laser cutter"), a tool like the ones in your earlier work on the agent loop. A note, or the student saying "I finished the training," can only remind the assistant which record to check. If the tool fails or the student is not found, the answer is "not permitted yet" and a pointer to the makerspace staff who can confirm.

Retrieval: finding the right page 4 min

Retrieval means finding the few pieces of a large body of text that matter for this request and putting only those into the context. A machine manual is the large body, and the window is the clipboard: you copy the one relevant diagram onto it, not the whole book. In the clipboard picture, the league rulebook in the library is the manual, and the analyst who brings you the one relevant page is retrieval. If a 300-page manual is about 500 tokens a page, it is 150,000 tokens; three retrieved chunks of 500 tokens are 1,500, which is 1% of the manual.

One common method is a similarity search:

  • Split the manual into chunks, pieces of a page or less.
  • Turn each chunk and the question into an embedding, a list of numbers that represents the meaning of the text so that similar meanings give similar lists.
  • Return the chunks whose lists point in the closest direction to the question's. That closeness is the cosine similarity: the dot product (the sum of the products of matching entries) of two vectors (the lists of numbers) divided by the product of their lengths.
Cosine similarity, with numbers

Use two-number embeddings for clarity. The question is q = (4, 3). Chunk A, on laser power settings, is a = (3, 4). Chunk B, on cleaning the lens, is b = (4, −3).

  1. Lengths: |q| = √(16 + 9) = 5, |a| = 5, |b| = 5.
  2. q · a = 4×3 + 3×4 = 24, so cos = 24 / 25 = 0.96.
  3. q · b = 4×4 + 3×(−3) = 7, so cos = 7 / 25 = 0.28.
  4. Chunk A scores higher, so it goes into the context. Real embeddings have hundreds of numbers, but the arithmetic is the same.
import math
def cosine(u, v):
    dot = sum(x * y for x, y in zip(u, v))
    return dot / (math.sqrt(sum(x * x for x in u)) * math.sqrt(sum(y * y for y in v)))

cosine((4, 3), (3, 4))    # 0.96, chunk A
cosine((4, 3), (4, -3))   # 0.28, chunk B

Precision and recall apply to retrieval too. Suppose the manual has 4 chunks that answer the question and the search returns 3 chunks, 2 of them relevant. Precision = 2/3 (relevant returned ÷ returned). Recall = 2/4 (relevant returned ÷ relevant that exist). Returning more chunks tends to raise recall and lower precision.

A common mix-up

"The model looks things up in the manual." The model sees only what your program puts in the window. If search_manuals returns the wrong chunk, the model answers from the wrong chunk, or from what it learned in training, and it will still sound confident.

The other method is just-in-time retrieval. Instead of searching ahead of time, the agent keeps lightweight identifiers, such as file paths, stored queries or links, and loads data at runtime through tools. The post describes a hybrid in Claude Code: some files are loaded up front, while search tools fetch the rest on demand. Its trade-off is that runtime exploration is slower than a ready-made lookup. Its advice: do the simplest thing that works (Anthropic).

In both methods, retrieval is a tool call like any other. For your assistant it might be search_manuals(machine, query) returning three chunks, each labeled with its manual and page. The labels let the model cite the page, and let a later step fetch the page again.

Worked example and practice 5 min

Worked example: sort the facts

Dana writes: "Book the laser cutter Friday at 3, and tell me the power setting for 3 mm acrylic. I like evening slots." For each fact, decide where it lives.

  1. The request itself is new this session, so it goes in the message list. It is in the context for every step.
  2. Friday at 3 availability changes constantly. Do not save it. A calendar tool reads it live, and the result sits in the context only while needed, then it can be cleared.
  3. Power setting for 3 mm acrylic is in a long manual. Retrieve it with search_manuals; only the matching chunk enters the context, labeled with its page.
  4. "I like evening slots" is a preference for later visits. Save it as a short note, and load it at the next session start.
  5. Whether Dana may use the laser cutter is a safety decision. Read the training record through a tool at the moment of booking. Do not rely on a note or on Dana's say-so. If the lookup fails, the answer is "not permitted yet" and a pointer to staff.
Your turn

Sam writes: "Book the 3D printer for tomorrow morning. How do I change the filament? Last time I mentioned I print only in PLA." Sort these four facts into context only, live tool, retrieval, or saved note: (a) tomorrow morning's availability, (b) the filament-change steps, (c) "I print only in PLA", (d) Sam's request text. Then say what the assistant must do before booking. Step (a) is done: it is a live tool, because availability changes.

Show a solution
  • (a) Live tool: the calendar tool reads availability at booking time.
  • (b) Retrieval: search the 3D printer manual; load the matching chunk with its page.
  • (c) Saved note: a stable preference, loaded at session start; the model may confirm it still holds.
  • (d) Context only: the request belongs to this session's message list.
  • Before booking: call the training-record tool for the 3D printer and decide from it. A note or Sam's say-so does not decide it; an unreadable record means "not permitted yet" with a pointer to staff.

Summary 2 min

  • The context window is everything the model sees in one call, and it is measured in tokens. The model keeps nothing between calls.
  • In an agent, memory is three things: the window (short-term, this session), saved notes (long-term, one student) and retrieval (a reference library of manuals).
  • Between steps, your program resends a growing message list, so input cost grows roughly with the square of the step count once the history outweighs the fixed prompt.
  • Clearing and compaction shrink the list, at the price of lost detail.
  • Between sessions, saved notes carry preferences, but a safety decision comes from the record, read through a tool.
  • Retrieval puts only the relevant chunks of a long manual into the window.
