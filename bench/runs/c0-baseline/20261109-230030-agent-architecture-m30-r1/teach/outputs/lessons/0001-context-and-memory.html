Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in a saved note, or in a searchable manual index, and say why.

Warm-up 2 min

Recall

From memory: in the agent loop, after the program runs a tool the model asked for, what does it do with the result? Answer in your head or on paper first.

Check your answer

It puts the result into the model's next input and calls the model again, so the model can choose its next step or write the final answer. That "next input" is exactly what today is about: what is in it, how big it can get, and what happens to it afterwards.

The context window: what the model sees 6 min

Start with a concrete case. A student types: "Can I use the laser cutter for acrylic, and is it free Friday?" Your program does not send just that sentence to the model. It sends a bundle of text, and the model reads all of it, every time it is called:

  • the system prompt: your standing instructions ("You are the makerspace assistant. Never book without checking the calendar.");
  • the tool descriptions: the name, purpose and parameters of check_calendar, search_manuals and the rest;
  • the message history: the student's question and everything that has happened since, including the model's earlier tool requests and the tool results.

That bundle is the context. The context window is the limit on how much text the model can take in and work with in one call. Text is counted in tokens, small chunks of text, roughly a short word or a piece of a long one. Anthropic's engineering team describes context as a finite resource and names the whole job of managing it context engineering: "curating and maintaining the optimal set of tokens" for the model at each call (Anthropic, Effective context engineering for AI agents).

Two facts about this box drive most design choices.

It has a size limit. Beyond it, the call fails or older text must be dropped.

Bigger is not simply better. The same Anthropic article describes context rot: as the number of tokens in the window grows, the model's ability to recall information from it gets worse. They treat attention as a limited "budget" that each extra token uses up, and recommend "the smallest possible set of high-signal tokens." Some models degrade more gently than others, but the effect shows up in all of them.

A third fact matters for your sponsor's money: you pay per token sent and received, and the whole context is sent again on every call. A 3,000-token context that runs for 5 calls costs you 15,000 input tokens, before the history even grows.

Rule of thumb: many people use about 4 characters per token for English. The exact count depends on the model, so measure with your provider's token counter before you budget.
A common mix-up

"A model with a huge window can just hold everything, so memory is solved." It is tempting because "fits" sounds like "works". But a window that fits the whole manual still costs you tokens on every call, and recall gets worse as it fills. Fitting is a limit, not a goal.

What is kept between steps 6 min

Here is the surprise that explains the rest of the lesson: the model itself keeps nothing between calls. Each call starts blank. The only reason step 3 "remembers" step 2 is that your program pasted step 2's request and result into the context for step 3. The memory between steps is a list in your program.

In Python terms it is exactly what you already know: a list of dicts that you append to.

messages = [{"role": "user", "content": "Is the laser cutter free Friday?"}]

while True:
    reply = call_model(system_prompt, tools, messages)   # model sees ALL of messages
    messages.append(reply)                               # keep its tool request
    if reply is final_answer: break
    result = run_tool(reply)                             # your program runs the tool
    messages.append(result)                              # keep the result for next call

(The names here are placeholders for the structure, not a real library.) Notice what this means: you decide what stays in messages. Nothing forces you to keep it all.

When the list gets too long

A manual search can return 2,000 tokens in one result. After a few of them, the context is crowded and expensive. Anthropic's article lists two tactics you can apply to messages (same article):

  • Clearing old tool results: once the model has used a result, replace the bulky text with a short stub such as "[manual page 14 read]". This is the lightest option.
  • Compaction: when the conversation nears the limit, have the model summarize it, then start a fresh context with that summary in place of the full history. You lose detail, so the summary must keep what matters, such as decisions made and facts still needed.
A common mix-up

"The assistant remembers the conversation, the way a person does." It does not remember at all; your program re-sends the transcript. That is why a cut or a summary silently deletes things: if the summary leaves out "the student wants acrylic, not wood", the model cannot know it ever existed.

What is kept between sessions: notes 6 min

A session is one conversation, from the first message to when it ends. Everything above, the messages list, dies with the session unless you save it. A new session starts with an empty list. So by default your assistant has never met the student before, and cannot know that Dana passed laser cutter training last week.

The fix is simple and not magic: write facts to storage outside the model, and read them back into the context next time. Anthropic calls this structured note-taking or agentic memory: the agent writes notes outside the context window and pulls them back in later. Their examples are a to-do list and a NOTES.md file (same article). It is the same way this tutoring workspace remembers you from session to session.

Worked case: the training record

Two designs for the training status:

DesignHow it worksWeakness or strength
Assistant writes notes freelyThe model decides to save "Dana is trained on the laser cutter" to a text file.Flexible, but the model might save something wrong or forget to save it.
Program owns a recordA database table training(student_id, machine, date). The assistant reads it with a tool, and only staff or a sign-off flow writes it.Reliable and checkable, which matters because it gates safety.

For safety-relevant facts, use the second design and treat the record as the source of truth. Use free-form notes for soft things: "Dana prefers morning slots", "last time asked about acrylic settings".

Notice the cost link: do not load every note about every student at the start. Load only what the current student needs, and keep the notes short. Everything you load is paid for on every call and takes room from the window.

A common mix-up

"Memory between sessions comes built in with the model." It does not. Unless you build a store and load from it, a new session knows nothing. This was also the idea behind quiz 0001's distractor about automatic memory of earlier conversations.

Retrieval: finding the right page 7 min

Now the third problem. Your machine manuals might total hundreds of pages. Do they go in the context?

Anthropic gives a clear first test: if your knowledge base is smaller than about 200,000 tokens (roughly 500 pages), you can include all of it in the prompt, and prompt caching can make that cheaper and faster (Anthropic, Contextual Retrieval). Check your total first; a small set of manuals might not need retrieval at all. But with a small budget, sending hundreds of pages on every call may still cost more than fetching only the page you need, and the context-rot point from earlier still applies.

When the manuals are too big, or too costly to send each time, use retrieval: search the manuals for the few passages relevant to the question, and put only those into the context. The usual recipe:

  1. Chunk the manuals: split them into passages, usually no more than a few hundred tokens each.
  2. Index the chunks so they can be searched.
  3. At question time, search, take the top few chunks, and place them in the context. In an agent this is just another tool: search_manuals(query).

Two ways to search

Embedding search: a model turns each chunk into a list of numbers (a vector) that captures its meaning; chunks about similar things get similar vectors, so a question can find a chunk that uses different words. Keyword search (the standard version is called BM25) ranks chunks by the exact words they share with the query. Each fails where the other works. Anthropic's example: a query for "Error code TS-999" is found by exact-word matching, where embeddings may miss it (Contextual Retrieval).

Student asksBetter at finding itWhy
"Why does the cutter keep stopping with E-47?"KeywordThe exact code appears in the manual's error table.
"My cut is burning the edges"EmbeddingThe manual says "scorching" and "reduce power"; the meaning matches, not the words.

The same article reports that combining both, and then reranking the results with a model, reduced failed retrievals by 49% and then 67% in their tests, so a hybrid is a good default if plain search disappoints. That is a vendor's own benchmark across their chosen datasets, so treat the numbers as a direction, and test on your own manuals.

Retrieval on demand versus loading up front

There is a second style. Instead of indexing everything first, the agent keeps lightweight pointers (file names, page titles, saved queries) and loads the material itself with tools when needed. Anthropic calls this "just in time" retrieval, notes it is slower and needs good tool guidance, and says Claude Code mixes both styles. Their advice: "do the simplest thing that works" (Effective context engineering).

A common mix-up

"Retrieval means the model looks things up in the manual itself." The model asks for a search, as it asks for any tool; your program runs the search and puts the chunks in the context. And if the right chunk is not in the top results, the model cannot see it, however good the model is. Retrieval quality limits answer quality.

Worked example and practice 6 min

Worked example

Sort these three facts for the makerspace assistant: (1) the laser cutter's power settings for 3 mm acrylic, (2) "Priya has completed laser cutter training", (3) the question Priya just asked and the calendar result for Friday.

  1. Ask how long the fact lives. (3) lives for this session only; (1) is permanent but about the machine; (2) is permanent and about a person.
  2. Ask who can be trusted to write it. (2) gates safety, so it lives in a program-owned record. (1) comes from the manuals, so no one writes it at runtime.
  3. Ask how big it is and how often it is needed. (1) sits somewhere in hundreds of pages and is needed only for some questions, so index the manuals and retrieve it on demand. (2) is tiny, so a quick lookup is cheap. (3) is current, so it stays in the context, and can be cleared once used.
  4. Result: (1) retrieval index, loaded into the context when searched; (2) saved record, loaded when needed; (3) context only, dropped or compacted later.

Summary 3 min

  • The model sees only its context: system prompt, tool descriptions, message history. It has a size limit, it costs tokens on every call, and a fuller window can recall worse.
  • Between steps, memory is a list your program re-sends. Clear old results or compact to keep it small, and know that a summary deletes whatever it omits.
  • Between sessions, nothing survives unless your program saves it. Use notes for soft facts and a program-owned record for facts that gate safety.
  • For long manuals, check whether they fit first; if not, chunk, index and retrieve a few passages per question, using keyword search for exact terms and embedding search for meaning.
