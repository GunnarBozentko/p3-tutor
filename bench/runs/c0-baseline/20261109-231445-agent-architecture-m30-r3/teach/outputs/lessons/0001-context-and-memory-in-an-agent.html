The context window: everything the model sees 6 min

Start with an example. A student types: "Is the laser cutter free tomorrow at 3 pm?" Your assistant calls the model. What does the model receive?

Not just the question. The program sends a bundle of text:

  1. the system prompt, the standing instructions you wrote ("You are the makerspace assistant. Be brief. Never book without confirming.");
  2. the tool descriptions;
  3. the conversation so far, including earlier tool requests and their results;
  4. the student's new message.

All of that, plus the reply the model writes, is the context window: all the text the model can refer to when it produces a response, including the response itself. Anthropic's documentation describes it as the model's "working memory" (Claude Platform docs: context windows). Text is counted in tokens, small chunks of text, roughly three-quarters of an English word each. A window has a maximum size in tokens. Text outside it does not exist for the model.

Notice what Figure 1 implies. The model does not carry anything from one call to the next. Between calls it has no memory of its own: if a piece of text is not in the input of this call, the model cannot use it. Your program must resend everything the model should still know. The platform docs say the same thing in terms of turns: each turn's input is all previous history plus the new message, and the model's output becomes part of the next input (context windows).

Why do chatbots seem to remember? The chat app resends the earlier messages each time. The "memory" lives in the app, not in the model.
A common mix-up (M3)

"The model remembers earlier conversations by itself." It is tempting because chatbots feel continuous. But when a session ends and a new one begins, the new input holds only what your program puts in it. A student who spoke to your assistant last week is a stranger to the model today, unless your program loads something about them.

Why a long context costs money 5 min

Your sponsor gave you a small budget, so let us count. Say the system prompt and tool descriptions take 2,000 tokens. The student's question is tiny, so ignore it. Each tool result adds 1,000 tokens. The agent makes four model calls: three tool requests and the final answer.

Worked example: input tokens
  1. Call 1 input: 2,000 (system and tools only).
  2. Call 2 input: 2,000 plus the first result, 3,000.
  3. Call 3 input: 4,000.
  4. Call 4 input: 5,000.
  5. Total input processed: 2,000 + 3,000 + 4,000 + 5,000 = 14,000 tokens, not the 5,000 you might guess from the last call alone.

Model usage is billed by tokens, and input is re-read on every call, so every token that stays in the context is paid for again at every later step. A big tool result at step 1 is the expensive kind: it rides along on every call after it. (Some providers discount repeated prefixes with caching; that lowers the price per token but does not remove the growth. Check your provider's pricing page for the real numbers.)

There is a second cost, and it is about quality. Anthropic's engineers call it context rot: as the number of tokens in the window grows, the model's ability to accurately recall information from it decreases. They describe an "attention budget" that every new token draws down (Effective context engineering for AI agents). Their rule is to find the smallest set of high-signal tokens that gets the job done.

A common mix-up (M7)

"With a big enough window, I can paste in everything and stop worrying." A big window sets a ceiling, not a target. Pasting all manuals into every request costs more at every call and makes the model worse at finding the one line that matters.

Check yourself

The third. Inputs are 2,000, 8,000 and 8,000, so 18,000, of which 12,000 is the chapter read twice.

Between steps: what to keep, trim or summarize 6 min

Inside one session, the agent loop keeps adding to the context. You have three levers, from lightest to heaviest. These are the techniques Anthropic describes for long tasks (Effective context engineering).

LeverWhat it doesMakerspace example
Make tools return lessReturn a short, useful result instead of a dump.check_calendar returns "free 2 to 5 pm", not the whole week's raw table.
Clear old tool resultsOnce a result has been used, drop its bulky text from later inputs. This is the lightest form of trimming.After the answer cites the safety page, remove the 3,000-token page text.
CompactionWhen the window nears its limit, summarize the conversation and continue with the summary in a fresh window.A long booking chat with many back-and-forths becomes: "Student wants the laser cutter Friday; 2 to 4 pm free; awaiting confirmation."

Compaction trades detail for room. The article says a good summary preserves decisions, unresolved problems and key details while discarding redundant tool output. The art is choosing what to keep: summarize too hard and you lose something you needed later.

Show the answer

The third. Clearing a used result is the lightest lever; the quoted sentence survives.

Between sessions: notes as memory 5 min

When a session ends, the context window is gone. Compaction does not help here, because a summary lives in the window too. To remember anything for next week, your program must write it outside the window and load it back later. Anthropic calls this structured note-taking, or agentic memory: the agent regularly writes notes to storage outside the context window and pulls them back in when needed, for example a to-do list or a NOTES.md file (Effective context engineering). You are looking at this idea in action: this learning workspace keeps a NOTES.md that your tutor reads at the start of every session.

For the makerspace, take this scenario. On Monday, Sam finishes the laser cutter training. Wednesday, Sam asks to book it. In between, the model has been called thousands of times for other students, and none of those calls contained Sam.

students/sam.json
{
  "trained": ["laser_cutter", "3d_printer"],
  "training_date": {"laser_cutter": "2026-11-09"},
  "preferences": "afternoons"
}

Two small tools make this memory: read_student_record(name) and save_student_note(name, note). On Wednesday the program (or the model, through the first tool) loads Sam's record into the context, so the model can answer "yes, you are trained". Memory is not magic: it is a file or database you write, plus a rule for when to read it.

What deserves a note?

  • Save: stable facts the assistant cannot easily re-derive, such as training status, stated preferences and open requests.
  • Do not save: things that change fast and have a source of truth, such as the booking calendar. A saved "laser cutter free Friday" goes stale; call the calendar tool again instead.
  • Be careful: notes about students are personal data. Save the minimum and ask your university what rules apply.
A common mix-up (M8)

"If the assistant retrieves a page or reads a note, the model has learned it." Reading puts text in the window for this call. Nothing changes inside the model. Next session, the text must be loaded again, or it is gone. (Changing the model itself is training, which is out of scope for your project.)

Retrieval: finding the right page 5 min

The manuals are long. Putting them all in every request is too costly (section 2) and hurts accuracy. So the assistant retrieves only the few passages it needs for this question and places them in the context. This is also memory, a kind that holds knowledge instead of facts about a student.

Two timings exist, and Anthropic's article names both:

  • Up front: before the model runs, a search finds likely passages and adds them to the input. This is the classic "RAG" setup (retrieval-augmented generation), often built on embedding search.
  • Just in time: the agent holds light pointers, such as file names or search queries, and uses a tool to load content only when it decides it needs it.

Their advice for choosing is to do the simplest thing that works, and many real systems mix the two (Effective context engineering).

Take the example "How do I change the blade on the band saw?" A search tool search_manuals(query) returns the three best-matching passages, each a few hundred tokens with its manual title and page. The model reads them, answers, and cites the page. One more point from Anthropic's work on retrieval: when you cut a manual into pieces (chunks), a chunk like "Turn the knob two rotations" loses which machine it belongs to. Adding a line of context to each chunk, such as "Band saw manual, blade change", improved retrieval in their tests (Introducing Contextual Retrieval). Cheap for you to copy: store the machine name and section with every chunk.

Worked example and practice 5 min

Worked example: sorting the information

A student writes: "Hi, it's Sam. Can I use the laser cutter Friday afternoon, and what settings for 3 mm plywood?" Where does each piece of information live?

  1. The system prompt and tool descriptions: in the context on every call. Short and fixed, so keep them lean.
  2. Sam's training status: a saved note, loaded with read_student_record("Sam"). It is stable and personal, so it belongs in storage between sessions.
  3. Friday's availability: not saved. Call check_calendar each time, because the answer changes and the calendar is the source of truth.
  4. Plywood settings: retrieved from the laser cutter manual with search_manuals. Only the matching passages enter the context.
  5. The conversation so far: in the context for this session. If the chat gets long, clear old tool results first, and compact only if needed.

Show a solution

(c) It was only needed to produce the summary; clear it from later inputs and keep "free 1 to 3 pm" in the context. Left in place, the 8,000 tokens would be re-read on every later call.

Summary 2 min

  • The context window is everything the model sees on one call. The model keeps nothing between calls; your program resends it all.
  • Every token that stays in the context is paid for again at each later call, and a longer context can make recall worse. Keep the smallest set of useful tokens.
  • Within a session: return short tool results, clear used ones, and compact when the window nears its limit.
  • Between sessions: write stable facts to notes outside the window and load them next time. Do not save things the calendar can tell you.
  • Long manuals: retrieve a few passages per question, and keep each chunk labeled with its machine and section.
