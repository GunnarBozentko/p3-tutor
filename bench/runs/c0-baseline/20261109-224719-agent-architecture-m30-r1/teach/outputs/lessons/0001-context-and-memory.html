Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in a saved note, or in a searchable manual, and say why.

Warm-up 2 min

Two questions from the agent-loop session. Answer in your head first, then open the answer.

Recall

In one sentence: what happens to a tool's result after the program runs the tool the model asked for?

Check your answer

The program adds the result to the conversation and calls the model again, so the model can see it and decide the next step. That "adds it to the conversation" step is today's topic: where does everything the model sees actually live?

Recall

How many times is the model called if it requests three tools in a row and then writes a final answer?

Check your answer

Four. Every step is a separate model call. Keep that in mind: it will matter when we talk about what each call has to carry.

The context window 5 min

Start with an everyday case. You hire a helper who has a desk the size of one sheet of paper and no filing cabinet. Whatever they need for a job must be written on that sheet. When you give them the next job, they only know what is on the sheet in front of them. They are clever, but they cannot use anything that is not on the page.

A language model works like that helper. The context window is all the text the model can look at when it writes a response, including the response itself. Anthropic's documentation calls it a "working memory" for the model (Claude Platform docs: context windows). The same text, in the same request, is called the context. It is measured in tokens, the small chunks of text (roughly a short word or part of a word) that a model reads and writes.

What is in the context

For the makerspace assistant, one model call carries these parts. The docs say everything in the request counts toward the window: the system prompt, every message including tool results, and your tool definitions.

  • The system prompt: your instructions ("You are the makerspace assistant. Never book a machine for an untrained student.").
  • Tool definitions: the names and descriptions of check_calendar, search_manuals and the rest.
  • The message history: the student's questions, the model's earlier replies, the tool calls it made and their results.
  • Anything else you choose to add: a note about this student, a retrieved manual page.

It is finite, and more is not always better

Every model has a maximum window size. Current Claude models list windows of up to 1 million tokens, depending on the model, and a request whose input alone exceeds the window is rejected (context windows docs). That is large. It is still not the whole story, for two reasons.

First, quality. The same docs page says that as token count grows, accuracy and recall degrade, a phenomenon called context rot, and that "more context isn't automatically better." Anthropic's engineering team describes context as "a finite resource with diminishing marginal returns" and says the goal is "the smallest possible set of high-signal tokens" (Effective context engineering for AI agents). It describes this as a gradient, not a hard cliff: the model does not break at a certain size, it gets gradually less reliable at finding the one fact that matters.

Second, cost. You pay for the tokens you send. Your fixed parts (system prompt and tool definitions) are sent on every call, and so is everything in the history. Prompt caching can lower the price of repeated prefixes, but the docs are clear that cached tokens still occupy the window: caching changes what you pay, not whether they count.

A common mix-up

"A bigger window means I can just paste in all the manuals." It is tempting because a 1-million-token window sounds like it fits a library. But the manuals would be sent, and paid for, on every one of the model's calls, and the model would be searching a huge pile for one sentence while quality drops. A big window is headroom, not a plan. The rest of this lesson is the plan.

Check yourself

Your assistant's system prompt and tool definitions together take 3,000 tokens. A student's conversation takes five model calls. Roughly how often is that 3,000-token block sent?

Show the answer

On every call. The model keeps nothing between calls, so the program resends the fixed parts each time. This is why a short system prompt and a few well-chosen tools save real money.

What is kept between steps 5 min

Here is the key fact, and it surprises many people. The model itself keeps nothing from one call to the next. Each call starts blank. The only reason the assistant seems to "remember" the previous step is that your program writes it down and sends it again.

The docs say it directly: each user message and assistant response accumulates within the context window, and the input for each turn is all the previous conversation history plus the current message; on a tool-use turn, that includes every block of the first turn and the tool_result (context windows docs). In Python terms, the agent loop you met earlier owns a list, and that list is the memory between steps:

messages = [{"role": "user", "content": question}]
while True:
    reply = call_model(system_prompt, tools, messages)   # a fresh call, every time
    messages.append(reply)                               # keep what the model said
    if reply is a final answer:
        break
    result = run_tool(reply)                             # the program runs the tool
    messages.append(result)                              # keep what came back

That messages list is the message history. The Anthropic docs' own memory-tool example loop does the same thing: it appends the assistant turn and the tool results before each new call.

Worked trace: the list grows

A student asks: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" Count what the model sees on each call (sizes are made-up round numbers to show the shape).

CallWhat is sentApprox. tokens
1Fixed part (3,000) + question (30)3,030
2Fixed + question + call 1's request + calendar result (200)3,300
3All of the above + search request + a manual page (1,500)4,900
4All of the above + training-record request and result (100)5,050

Total tokens processed across the four calls: about 16,300, even though the "new" information was only about 1,800. Each step re-sends everything before it. Cost grows faster than the number of steps, which is why long agent runs get expensive, and why a bulky tool result (a whole manual chapter) hurts: it is re-sent on every later call.

A common mix-up

"The model remembers what it did in the earlier steps." It is tempting because the assistant behaves as if it did. But it only appears to remember because your program re-sent the earlier steps. Delete a tool result from the list, and the model has genuinely never heard of it. This is also good news: you control what the model "remembers", which means you can trim it.

Check yourself

Your loop has a bug: after running a tool, it forgets to append the tool's result to the message list. What does the model most likely do on the next call?

Show the answer

It asks again or guesses. A missing result is invisible to the model, which can lead to the repeated-call loop you saw earlier, and a step limit is the safeguard.

When the window fills up 4 min

A long run keeps growing the list, so sooner or later you must decide what to throw away. There are three standard moves. All three are described in Anthropic's engineering post on context (Effective context engineering for AI agents).

  1. Clear old tool results. The lightest touch. Once the assistant has used a calendar listing, the raw listing rarely needs to be re-sent. The post calls this the "safest lightest touch".
  2. Compaction: when the conversation nears the limit, ask the model to summarize it, then start a fresh window containing the summary. You keep decisions and open problems and drop the bulk. The post warns that too-aggressive compaction can lose context that turns out to matter later.
  3. Sub-agents with their own windows. A helper explores a big task in a clean window and hands back a short summary (the post says often 1,000 to 2,000 tokens). You will meet this properly in the multi-agent lesson, so just note it exists.

For the makerspace assistant, most conversations are short: a question or two and a booking. Compaction is rarely needed within one chat. What does matter is the next topic, because a student comes back next week.

Check yourself

A student's chat has a 4,000-token calendar listing from ten steps ago, never needed again. Which move fits best?

Show the answer

Clear the old result. It costs nothing, keeps the rest intact, and trims the bill on every later call.

What is kept between sessions: notes 6 min

A session is one conversation, from the first message to the last. When it ends, the message list is gone. Next week the same student opens a new chat and the model has an empty context: it does not know their name, their training, or what they asked before. Nothing carries over unless you save something and load it again.

The standard answer is notes: text the agent writes to storage outside the context window, and reads back later. Anthropic's engineering post calls this structured note-taking, or agentic memory, with examples like a to-do list or a NOTES.md file (Effective context engineering for AI agents). This very workspace works that way: I have no memory of earlier sessions with you, but I read your NOTES.md every time.

How a memory tool works

Anthropic's memory tool is a concrete model. The docs say it "operates client-side: Claude requests file operations, and your application runs them." It is a directory of files under /memories that your own handler maps onto real storage, such as a per-user folder or database keys. The commands are view, create, str_replace, insert, delete and rename (Memory tool docs).

Notice what that means: memory is just another tool, in the same loop you already know. The model asks to view a file, your program runs it, the file's text comes back as a tool result and lands in the context. Memory is not a magic extra brain. It is a tool that reads and writes files, and the model has to decide to use it.

Worked design: the training record

Riley's makerspace need: "remember each student's training status." Two options.

  • Notes the agent writes freely. After a chat, the model writes "completed laser cutter safety class" into the student's file. Flexible, but a model can mis-write or forget, and a safety rule should not depend on that.
  • A real record your program owns, exposed through a tool like check_training_record, which you already have. Exact, auditable, and the model only reads it.

The sensible split: facts that must be exactly right (training status, bookings) live in a database behind a tool. Soft preferences that merely help ("prefers morning slots", "is working on a drone frame") can live in a short per-student note. Either way, the load step is the same: at the start of a session, the program (or the model, via a tool) puts the relevant bit in context.

A common mix-up

"A long context window is the same as long-term memory." It is tempting because both involve the model "knowing" things. But a window lasts one session at most and is reset when the chat ends, while saved notes persist. A larger window gives you a bigger desk, not a filing cabinet.

Memory is also a safety job. Anything saved will be read back into the model later, so decide what must never be saved (passwords, personal details you do not need) and who can read it. The memory-tool docs put these safeguards on your application, including blocking paths like /memories/../../secrets.env that escape the memory folder.
Check yourself

Tomorrow the assistant should greet a returning student with their last machine, "the 3D printer". Where must that fact be stored today?

Show the answer

In a saved note or record. The context is rebuilt from scratch each session, so only stored text can be loaded into it.

Retrieval: finding the right page 5 min

Last piece. The manuals are long, and you now know why you cannot paste them all in. Retrieval means fetching only the few passages that matter for this question and putting those, and only those, in the context. It is memory in the library sense: a big store you look things up in.

Everyday version: you do not read a whole textbook before an exam question. You use the index, find page 212, and read that.

Two ways to arrange it

Anthropic's post contrasts them (Effective context engineering for AI agents).

Retrieve firstRetrieve just in time
HowBefore the model is called, the program searches (often with embeddings) and adds the top passagesThe model is given a search tool and keeps lightweight pointers, then loads pages itself when it needs them
Good forPredictable questions, fast and cheap: one model callOpen-ended questions needing several lookups
RiskWrong passages are fetched and the model never sees the right oneSlower, with more model calls, and the model can waste context if the tool is poorly described

The post also describes hybrids, and its advice is plain: "do the simplest thing that works." For a makerspace Q&A, a search tool over manual sections (search_manuals(machine, query)) that returns a few short, labeled passages is the likely starting point, with the machine name and section title on each result so the model can judge relevance.

An embedding, in one paragraph

An embedding turns a piece of text into a list of numbers so that texts with similar meaning get similar lists. You embed every manual section once and store the lists. At question time you embed the question and find the closest sections. This catches "how do I stop the laser cutter catching fire" even if the manual says "flame suppression". Long-term memory in agents is often described as exactly this: an outside store with fast lookup (Weng, LLM Powered Autonomous Agents). Keyword search still works well for exact terms like part numbers, so many systems use both. Chopping manuals into sections of sensible size (one procedure each) matters more than most people expect.

A common mix-up

"Retrieval means the model has learned the manual." It is tempting because answers sound informed. But nothing changes inside the model. The passage is pasted into the context for this one call, and on the next question it is gone unless fetched again. If retrieval picks the wrong page, the model will fluently answer from the wrong page, so test your search separately from your model.

Check yourself

A student asks, "What is the maximum material thickness for the bandsaw?" The assistant answers confidently with a value from the drill press manual. What most likely went wrong?

Show the answer

The search returned the wrong page. Always debug retrieval first: look at exactly what was placed in the context.

Worked example and practice 6 min

Worked example

Problem: Sort three pieces of information for the assistant: (a) "Never book a machine for an untrained student", (b) the laser cutter manual's 40 pages, (c) "Sam was trained on the 3D printer last month".

  1. (a) A rule that applies to every call. It is short and always needed, so it goes in the system prompt, in context every time. The few tokens are worth it.
  2. (b) A large reference, needed in small pieces. Pasting 40 pages into every call would be costly and noisy. Put it in a searchable store and retrieve the one or two relevant sections when asked.
  3. (c) A fact about one person that must outlive the chat. It must be stored outside the context. Because it is a safety-relevant fact, keep it as an exact record behind a tool, not a free-form note.
  4. Check the cost: the system prompt line costs tokens on all calls, retrieval costs only on calls that search, and the record costs only when looked up. Each item sits where it is paid for only when needed.
Your turn

Sort these three the same way, and say what you would do about size: (d) "Prefers to work in the evening", (e) the 12 tool-result calendar rows from earlier in today's chat, (f) the shop's opening hours, 5 lines long. First step given: ask for each one, "Is it needed on every call, only sometimes, or after this session ends?"

Show a solution

(d) A soft preference needed after the session ends: a short per-student note, loaded at the start of a session. (e) Needed only for this chat, and probably stale soon: keep in context while useful, then clear it. (f) Short and asked often: either put it in the system prompt, because 5 lines is cheap, or serve it through the manual search if it changes often. In both cases the rule is the same: pay for tokens only on the calls that need them.

Summary 2 min

  • The context window is everything the model sees in one call. It is finite, you pay for it every call, and more is not automatically better (context rot).
  • The model keeps nothing between steps; your program keeps the message list and resends it each call. Trim it with clearing, compaction or sub-agents.
  • Between sessions, only text saved outside the context survives. Notes and records are a tool the model uses, and the program loads them back in.
  • Retrieval puts only the few relevant passages in the context. Debug the search before blaming the model.

Say it in your own words: without looking, explain to a teammate why the assistant "forgets" a student between visits, and name one thing you would save and one thing you would retrieve.
