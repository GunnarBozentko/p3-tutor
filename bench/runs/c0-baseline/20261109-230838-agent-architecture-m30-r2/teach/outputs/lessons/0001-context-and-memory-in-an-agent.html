Context and memory in an agent

By the end of this lesson you can say what your makerspace assistant keeps in its context, what it saves between sessions, and how it finds the right page in a long manual.

Objective O3: context and memory in an agent About 30 minutes Builds on the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three come down to one question: what goes in front of the model, and when. At your design review you will be asked to defend those choices.

Warm-up 2 min

Recall

From memory: in the agent loop, after the model asks for a tool, who actually runs the tool, and what happens to the result?

Check your answer

The program around the model runs the tool, not the model. The result is sent back to the model as the next piece of input, and the model is called again. That "called again" is today's topic: each call needs the model to be shown everything it should know.

The context window 5 min

Start with a concrete case. A student types: "Is the laser cutter free tomorrow, and what settings do I use for 3 mm acrylic?" The model has no eyes on the booking system and has not memorised your manuals. Everything it can use for this one answer has to arrive as text in its input.

That input is called the context: all the text the model is shown for one call. It usually holds the system prompt (your rules for the assistant), the tool descriptions, the conversation so far, and any tool results. The context window is the limit on how much text the model can take in (and write) in one call. Text is measured in tokens, small chunks of text, roughly a short word or part of a longer one. If something is not in the context, the model cannot see it, so for that call it does not exist.

Two things limit you. First, the window has a fixed size, and the model's answer must fit too. Second, and closer to your budget: model providers typically bill by tokens, and each call is billed for everything you send. A long context makes every call more expensive, and an agent makes many calls per request (Anthropic notes that agents with many tool results can exhaust their context windows). Anthropic's engineering team describes context as a finite resource and says the aim is the smallest set of high-signal tokens that gets the result you want (Effective context engineering for AI agents).

Window sizes differ by model and change often, so look up the current figure for the model you choose rather than memorising one. The lesson's ideas hold at any size.
A common mix-up

"A bigger window means we can paste in all the manuals and be done." It is tempting because it sounds simple. But you pay for those tokens on every call, and a very long context can still bury the one relevant paragraph. Having room is not the same as using it well; the sections below are about choosing what goes in.

What is kept between steps 6 min

You learned that each step of the loop is a separate model call. Here is the consequence. The model itself does not remember the previous call. What carries the work forward is a plain Python list that your program keeps, and re-sends each time.

A message list is that list: the student's question, then the model's request for a tool, then the tool's result, then the next request, and so on. Before each call the program appends the newest item and sends the whole list.

messages = [{"role": "user", "content": "Is the laser cutter free tomorrow?"}]
while True:
    reply = call_model(system_prompt, tools, messages)   # sees the WHOLE list
    messages.append(reply)                               # program keeps it
    if reply is a final answer:
        break
    result = run_tool(reply.tool_request)                # program runs the tool
    messages.append(result)                              # result joins the list

This is a sketch, not a real library call; the point is the list. "Memory between steps" is just this list growing.

Because the list only grows, long requests can fill the window and cost more with every step. Three ways to keep it under control are in common use. Clearing old tool results removes bulky results the model has already used. Compaction replaces a long history with a short summary. Memory, covered next, saves facts outside the window. Anthropic's context-management announcement describes context editing, which prunes old tool results, and a memory tool as two such tools for long-running agents (Anthropic: context management).

A common mix-up

"The model remembers the earlier steps on its own." It feels that way because chatbots do continue a conversation. But the continuing is done by the program re-sending the history. If your program forgot to append the calendar result, the next call would not know the calendar was ever checked.

Check yourself

In a request, the assistant calls search_manuals and gets back a 3,000-token page it no longer needs. What is the cost if nothing removes it?

Show the answer

The first option: it stays in the list until your program clears or summarises it.

What is kept between sessions 4 min

A session is one conversation: one run of your program, starting from an empty message list. When it ends, the list is gone. If Priya trained on the laser cutter on Monday and returns Thursday, a fresh session has no idea about Monday.

So by default, nothing is kept between sessions. The model's own knowledge was fixed in training and does not change from talking to your students. Anything that must survive has to be written to storage you control (a file, a database) by your program, and loaded back into the context of a later session. Anthropic's description of its memory tool follows this idea: information is stored outside the context window in a file-based store, on the client side, so the developer controls where it lives (Anthropic: context management).

A common mix-up

"The assistant will just remember each student." It would not, unless you build it: nothing is saved automatically. This is also a privacy point. Whatever you save is a record you are responsible for, so save the minimum, such as "trained on laser cutter, 3 March", not the whole chat.

Notes as memory 5 min

The simplest working memory is a notes file. The agent gets a tool such as save_note(student_id, text) and a tool or a start-up step to read the notes back. Anthropic calls this structured note-taking: the agent writes notes outside the context window and pulls them in at later turns (Effective context engineering for AI agents).

A concrete example. Priya finishes the laser-cutter training. The agent saves:

{"student": "priya", "trained": ["laser_cutter"], "date": "2026-03-03",
 "prefers": "afternoon slots"}

On Thursday, the program starts a new session and puts those few lines into the system prompt or the first message. Now the model knows Priya is trained, for about 40 tokens instead of a replayed conversation of thousands.

What makes a good note

  • Short and factual. Facts you will need later: status, preferences, decisions. Not a transcript.
  • Written by a rule. Decide when notes are saved (for example, when a training is completed) rather than leaving it to chance.
  • Checked before use. A note can go stale. If Priya's training expires after a year, store the date so the program can check it.
Notes work the same way for one long task. An agent that writes a to-do list to a file can lose most of its context and still pick up where it left off.

Retrieval: finding the right page 6 min

Notes cover small facts about people. Manuals are different: hundreds of pages, far more than you want in every call. The answer is retrieval: keep the manuals in storage outside the context, and bring only the few relevant passages in when a question needs them.

This is "just in time" loading. Anthropic describes agents that keep light references and use tools to pull data into context when needed, instead of loading everything up front (Effective context engineering for AI agents).

How a search tool finds the page

  1. Split each manual into chunks: passages of a few paragraphs, ideally one topic each, labelled with machine and section.
  2. Index them so they can be searched. The simplest way is keyword search; another is an embedding search, where text is turned into numbers so passages with similar meaning score as close. You will look at that choice in a later lesson; for now, "search" means a function that returns the best few chunks.
  3. Expose it as a tool, search_manuals(machine, query). The model writes the query; the program runs the search and returns, say, the top three chunks.
  4. The chunks go into the message list like any tool result, and the model answers from them.

Three design choices decide how well it works. Chunk size: too small and a chunk loses the surrounding context (a setting with no machine name); too large and you spend tokens on irrelevant text. How many chunks: more chunks catch the answer more often but cost more. Metadata: filtering by machine name before searching stops a band-saw paragraph answering a laser-cutter question. These are the knobs you will tune against your budget.

A common mix-up

"Retrieval means the model has learned the manuals." No. The model reads the retrieved chunks as ordinary input for that call, just like a tool result. If the search returns the wrong chunk, the model works from the wrong text, and may sound confident, as you may have noticed with chatbots and outdated facts. Check what was retrieved before blaming the model.

Worked example and practice 6 min

Worked example

Priya (trained on the laser cutter on 3 March) starts a new session and asks: "Can I book the laser cutter Friday, and what power for 3 mm acrylic?" Decide what is in the context at each step.

  1. Start of session. The program loads Priya's note into the system prompt: trained on the laser cutter, 3 March. Reason: status must come from saved memory, since the session starts empty.
  2. Call 1. Context: system prompt (with note), tool descriptions, the question. The model requests check_calendar(laser_cutter, Friday).
  3. Call 2. The program appends the calendar result (a few lines). The model requests search_manuals(laser_cutter, "3 mm acrylic power").
  4. Call 3. The program appends the top three chunks. Reason: only the chunks come in, not the 80-page manual. The model writes the answer: Friday is free; here is the setting.
  5. After the answer. If Priya books a slot, the program saves "booked Friday" as a note. The message list is discarded when the session ends; the note is not.
Your turn

A student, Sam, has never trained on the 3D printer. Sam asks: "Can I use the 3D printer today, and how do I change filament?" Step 1 is given: the program loads Sam's note, which says "no training recorded". Write out what happens in the next calls, and say which memory carries each piece: the message list, the notes store, or the manuals store.

Show a solution

Call 1: context has the system prompt with Sam's note, the tools and the question. The model requests search_manuals(3d_printer, "change filament") and may check the policy for untrained users. Call 2: the program appends the chunks (manuals store, brought into the message list). The model can now see both that Sam has no training (notes store, loaded at the start) and the filament steps. The answer should say that Sam needs training before using the printer, and may still share the filament steps. Should Sam book a training slot, the program saves that as a note. During the request, everything is carried by the message list; only the note and the manuals persist.

Summary 2 min

  • The context window is everything the model sees in one call; it is limited, and you pay for it on every call.
  • Between steps, your program keeps a message list and re-sends it; the model itself remembers nothing.
  • Between sessions nothing survives unless you save it, as short checked notes, and load it back.
  • Retrieval keeps big sources outside the window and brings in only the best few chunks, through a search tool.

Say it in your own words: without looking, explain to a teammate why the assistant needs a notes store and a manuals search rather than one very large prompt.
