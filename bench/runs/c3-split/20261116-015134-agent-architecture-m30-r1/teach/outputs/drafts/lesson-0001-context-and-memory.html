Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in a saved note, or in a searchable manual, and justify the choice with a token count (a token is the chunk of text a model reads and writes; the context is the text sent to the model on one call; Section 1 defines both).

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small budget. The context window and what it costs 5 min

Example: the assistant makes 4 calls. Call 1 sends 2,100 tokens and call 4 sends 6,600, because every call also resends everything added by earlier calls. General idea: the model keeps no state between calls, so the program resends the whole context each time, and the cost grows with every step.

A language model keeps no state between calls: it sees only the text sent in that call and writes the next text. The context window is the maximum amount of text, counted in tokens, that the model can handle per call, input and output together. A token is the chunk of text the model reads and writes, commonly quoted as roughly three-quarters of an English word.

The context is whatever you actually put into that window on a given call: the system prompt (the fixed instructions sent at the start of every call), the tool descriptions (the written list of tools the model may request), the conversation so far, and every tool result. The program keeps the conversation as a list of messages and sends the whole list on every call, so every call re-reads everything that came before it.

Think of a soccer coach who gets amnesia at every whistle. Before each play, an assistant (the program) hands the coach a briefing sheet with the game plan and everything that has happened so far. The coach is only as informed as the sheet, and a longer sheet costs more to read. That sheet is the context. A clipboard left in the locker room between matches will later play the part of saved notes, and the team doctor's filing cabinet will play the retrieval store (a large collection searched for the few relevant pieces, Section 5).

This matters for cost because the loop calls the model once per step, and each call resends the whole context. Let S be the tokens present at the start (system prompt, tool descriptions, the student's question), and let r be the tokens each step adds (the model's request plus the tool's result). Call number k reads S + (k−1)r input tokens, so over n calls the total input is:

total = n·S + r·n(n−1)/2

Why n(n−1)/2 (proof): call k adds (k−1)·r beyond the start. Let T = 0 + 1 + … + (n−1). Write the sum again in reverse under itself and add column by column: each of the n columns sums to n−1, so 2T = n(n−1) and T = n(n−1)/2. For n = 4 the columns are 0+3, 1+2, 2+1, 3+0, each 3, so 2T = 12 and T = 6. The growing part is 6r = 6 × 1,500 = 9,000, and with S = 2,100 the total is 4 × 2,100 + 9,000 = 17,400.

A common mix-up

"The context window is the assistant's memory." It is only the text sent on this one call. It is empty again on the next session, and the program must send any text again for the model to see it.

The second term is an arithmetic series (a sum in which each term grows by the same amount), so total input grows with the square of the number of steps. Input tokens are only one part of the bill: output tokens are billed too, usually at a higher rate per token, and providers may discount repeated input through caching (the provider stores a repeated start of the input and charges less to re-read it). The formula gives the uncached input, the worst case, so check the sponsor's actual pricing before you defend a number. Anthropic frames context as a finite resource with diminishing returns (Anthropic, context engineering).

Worked numeric case

The assistant starts with S = 2,100 tokens (system prompt, tool descriptions, question). Each step adds r = 1,500 tokens (the model's request plus a tool result such as a few manual pages). It makes n = 4 calls. The practice section later uses a smaller S, because its example has a shorter system prompt.

  1. Fixed part: 4 × 2,100 = 8,400 tokens.
  2. Growing part: 1,500 × 4 × 3 / 2 = 9,000 tokens.
  3. Total input = 17,400 tokens, which matches the figure. Only 8,400 of them were there at the start.

Why more context is not always better 3 min

Example: place the rule "never run the saw without a spotter" on the first line of a long prompt, or bury it in the middle of 40 pages of other text. The study below found the buried version is the one models are most likely to miss. General idea: a bigger window does not mean the model uses all of it equally well.

Context rot is Anthropic's name for the finding that as the number of tokens grows, the model's ability to accurately recall information from the context decreases; the same post frames this as an "attention budget" (the limited focus the model can spread across all tokens) that each added token draws on (Anthropic). The goal is therefore the smallest set of high-signal tokens that still lets the model do the job.

Think of signal-to-noise ratio: the signal is the tokens the answer needs, and the noise is everything else. With a 1,000-token relevant passage inside the whole 48,000-token manual plus a 1,300-token fixed start, the signal is 1,000 / 49,300 ≈ 2% of the context. With retrieval it is 1,000 / 2,300 ≈ 43%.

Position matters too. In a controlled study, accuracy was often highest when the relevant information was at the beginning or end of the input, and degraded significantly when it was in the middle, even for models built for long contexts (Liu et al., "Lost in the Middle"). Plotted against position, accuracy looks like a U. As an illustration only, not a finding: a coach tends to remember the first and last minute of a briefing better than minute twelve.

A common mix-up

"If the window can hold a whole manual, put the whole manual in and the answer will be found." This is tempting because the window is the visible limit. It is wrong on two counts: the manual is resent and billed on every call (Figure 1), and an answer buried in the middle of a long input is the position the study found models handle worst. (Its tests used short passages, not 80-page manuals, so test your own case.) A window sets what fits, not what works well.

Check yourself

You must put a safety rule ("never run the saw without a spotter") into a long prompt that also holds many other items. Where is it most likely to be used reliably?

Show the answer

Near the start or the end; the middle of a long context is the weakest position.

What is kept between steps 4 min

Between steps of one request, the only thing that carries over is the message list the program sends on every call: if it is not in the list, the model does not know it. In code:

messages = [{"role": "user", "content": question}]
while True:
    reply = call_model(system=SYSTEM, tools=TOOLS, messages=messages)
    messages.append(reply)                      # keep the model's turn
    if reply.is_final:
        break
    result = run_tool(reply.tool_name, reply.tool_args)   # your program runs it
    messages.append({"role": "tool", "content": result})  # keep the result

The list grows with each step, so long runs need a policy for what to drop. Anthropic's post describes these techniques for long tasks (Anthropic):

  • Compaction: summarize the contents of a conversation nearing the limit and reinitiate a new context window with the summary. Its lightest form is tool-result clearing: removing old tool outputs that are no longer needed, which the post calls one of the safest, lightest-touch forms of compaction.
  • Structured note-taking: covered in the next section.
  • Sub-agents: do a side task in their own clean context and return only a condensed summary, often 1,000 to 2,000 tokens; a later lesson covers them.

Numbers for the list, with S = 2,100 and r = 1,500:

  • The list holds 2,100 tokens at call 1, 3,600 at call 2, 5,100 at call 3 and 6,600 at call 4. Before a fifth call it would hold 8,100.
  • Clear the step-1 result before call 3: calls 3 and 4 each drop by 1,500, saving 3,000 of the 17,400.
  • Compact before call 5 into an 800-token summary: call 5 reads 2,100 + 800 = 2,900 instead of 8,100, saving 5,200 on that call alone.
  • Cost: details the summary left out are gone.
A common mix-up

"Clearing old results is free." It is tempting because the saving is visible and the loss is not. Anything cleared is gone unless it was saved elsewhere, and a summary can drop a detail that a later step needs. Decide what to save as a note before you clear.

Check yourself

The assistant read a 1,500-token manual page at step 1 and has since moved on to booking. Which policy removes the page's cost while keeping the booking details?

What is kept between sessions: notes 4 min

When a session ends, the message list is discarded. The next session starts with the system prompt and nothing else, so the model does not remember the student unless your program puts something back. Memory in an agent therefore means information saved outside the context window and loaded back when needed. The simplest form is notes: Anthropic describes structured note-taking as the agent regularly writing notes persisted outside the context window, such as a to-do list or a NOTES.md file, and reading them back later (Anthropic).

One documented implementation is a memory tool: Claude requests file operations under a /memories directory and your application runs them, so storage is yours to design (Memory tool docs). This is the same pattern as any tool in your loop: the model asks, your program acts.

For the makerspace, a per-student file could look like this, loaded at the start of each session:

{"student": "s-1042",
 "training": {"laser_cutter": "passed 2026-10-03", "3d_printer": "not started"},
 "notes": "prefers evening slots; working on a capstone enclosure"}

Notes cost tokens like everything else, so keep them short and structured. At roughly 60 tokens, this record is far cheaper than replaying a past conversation of thousands. Numbers: loading the 60-token record on all 4 calls costs 4 × 60 = 240 input tokens; replaying a 3,000-token past conversation on all 4 calls costs 4 × 3,000 = 12,000, which is 50 times more.

A common mix-up

"The assistant learns from each student and gets smarter." This is tempting because chat products feel like they remember you. The model's weights (the numbers inside the model that training sets) do not change during use; changing them would be training (adjusting the weights on data), which is out of scope for you. Any apparent memory is text your program saved and re-inserted into the context.

Check yourself

On Monday a student tells the assistant their laser-cutter training was completed. On Thursday a new session begins and the assistant does not know. What is the most direct fix?

Show the answer

Save a record outside the context and load it into the next session. Also decide who is trusted as the source of truth (the one record trusted when sources disagree): a student's own claim should not replace an official record.

Retrieval: finding the right page 4 min

Retrieval means searching a large collection for the few pieces relevant to the current question and putting only those into the context. It is the opposite of loading the whole manual: instead of paying for 80 pages on every call, you pay for the two pages that matter. A manual is first split into chunks (for example, one section each), and a retriever scores each chunk against the question and returns the top k.

Retrieval is also a form of memory. A store too large to load every time, such as every past student record or years of notes, is searched the same way: chunk, score, return the top k. Section 4's notes suit small facts that are always loaded; retrieval suits large stores searched on demand.

Everyday analogy: a cook asked how long to roast a chicken does not read the 400-page cookbook aloud. The cook looks the dish up in the index (the retriever), opens the two matching pages (the top k = 2 chunks, where k is the number of chunks you keep), and reads only those on the counter (the context). A wrong index entry means the cook reads the wrong page.

Two scoring approaches are common. Keyword search counts words shared between the question and a chunk; the code below counts distinct shared words, and production systems use weighted versions such as TF-IDF or BM25 (scoring methods that give rare shared words more weight than common ones). Embedding search uses an embedding, a list of numbers that represents the meaning of a text, so that similar meanings get similar lists; chunks are ranked by a similarity measure such as cosine similarity (a number from −1 to 1 that is 1 when two lists point the same way). So "cut acrylic" can match a chunk that says "laser-safe plastics".

Anthropic also distinguishes retrieving everything before inference (a model run that produces an answer) from just-in-time retrieval, where the agent keeps lightweight identifiers such as file paths and loads data with tools at runtime (Anthropic). Retrieval then becomes one more tool in your loop.

def search_manuals(query, k=2):
    # no punctuation stripping: remove "?" and "." from the query first
    words = set(query.lower().split())
    scored = [(len(words & set(c.text.lower().split())), c) for c in CHUNKS]
    scored.sort(key=lambda t: t[0], reverse=True)
    return [c.text for score, c in scored[:k] if score > 0]

Worked scoring example. The query is "maximum thickness acrylic laser", with the word set {maximum, thickness, acrylic, laser}.

  • Chunk A, "Cleaning the laser lens with isopropyl": shares {laser}, score 1.
  • Chunk B, "Maximum material thickness is 6 mm for acrylic": shares {maximum, thickness, acrylic}, score 3.
  • With k = 2, B is returned first and A second.

In classification terms, retrieval labels each chunk relevant or not. Chunk B is a true positive for the thickness question. Chunk A (score 1, returned because k = 2) is a false positive. A relevant chunk that scores 0, such as B for "how thick can I cut", is a false negative. Raising k raises recall and lowers precision, and each extra chunk costs 500 input tokens.

Token cost, with numbers:

  • Whole manual: 80 pages × about 600 tokens = 48,000 tokens (600 is an assumption; measure a real page with a tokenizer, a program that splits text into tokens and counts them).
  • Retrieval: two 500-token chunks add 1,000 tokens on calls 2 to 4 (ignoring other step results): 3 × 1,000 = 3,000 extra input tokens.
  • Whole manual on all four calls: 4 × 48,000 = 192,000 extra input tokens.
A common mix-up

"Retrieval means the model searches the manual itself." Your program runs the search, or the model requests it as a tool call as in the loop. Either way the model can only answer from the chunks that come back, and keyword search can miss: the query "how thick can I cut" shares no word with chunk B, because "thick" is not "thickness", so B scores 0. Test retrieval on real student questions before trusting it.

Worked example and practice 6 min

Worked example

Classify each piece of information for the assistant, and estimate its per-request cost.

  1. System prompt and tool descriptions (about 1,200 tokens): needed on every call, so it stays in the context permanently. Keep it short, since it is resent each time.
  2. The 80-page laser cutter manual (48,000 tokens): too large and mostly irrelevant per question, so it is retrieved. Two 500-token chunks cost 1,000 tokens.
  3. A student's training status (about 60 tokens): must outlive the session, so it is saved as a note and loaded at session start.
  4. The calendar result for Friday (about 300 tokens): needed for this request only, so it lives in the context and may be cleared afterwards.

Resulting context at call 3 (after the manual search and the calendar check): 1,200 + 60 + 40 (question) + 1,000 + 300 = 2,600 tokens, instead of about 49,600 with the whole manual loaded.

Worked example 2: what does retrieval save per request?

Simplification: this ignores the model's own requests and other tool results (for example the 300-token calendar result). They add the same tokens to A and B, so the real ratio is somewhat below the one computed here. It is a ceiling, not a forecast.

  1. Fixed part: system prompt and tools 1,200, training note 60, question 40, so S = 1,300 tokens.
  2. Option A, whole 48,000-token manual in the context on all 4 calls: 4 × (1,300 + 48,000) = 197,200 input tokens.
  3. Option B, retrieval: call 1 reads 1,300; calls 2 to 4 each add two 500-token chunks and read 2,300. Total = 1,300 + 3 × 2,300 = 8,200 input tokens.
  4. Ratio: 197,200 / 8,200 ≈ 24, so B is up to about 24 times cheaper on input.
  5. Budget view, at an assumed illustrative price of $3 per million input tokens: A costs 197,200 × 3 / 1,000,000 ≈ $0.59 per request and B ≈ $0.025. Over 1,000 requests that is about $592 against $25, as an upper bound on the saving. Use your sponsor's real price.

Summary 2 min

  • The model is stateless (it stores nothing between calls): the context, rebuilt and resent on every call, is all it knows. Total input over n calls is n·S + r·n(n−1)/2 (17,400 for S = 2,100, r = 1,500, n = 4).
  • More context costs more and can be used worse (context rot, lost in the middle).
  • Between steps the message list is all that carries over; trim it by clearing old tool results or compacting.
  • Between sessions only saved notes survive; the program writes and reloads them.
  • Retrieval puts only the relevant chunks of a long manual into the context.
