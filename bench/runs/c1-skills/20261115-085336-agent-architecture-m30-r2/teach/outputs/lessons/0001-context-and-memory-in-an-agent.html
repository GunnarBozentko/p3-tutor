Warm-up 2 min

Check your answer

The program around the model runs the tool; the model only writes a request naming it. The program then puts the result into the model's next input and calls the model again. That last step is today's subject: "the model's next input" is the context, and what the program chooses to put in it is the whole design question.

The context window 6 min

A language model has no memory of its own. It sees only the text handed to it on each call, and Anthropic defines context as "the set of tokens included when sampling from a large-language model" (Anthropic, Effective context engineering for AI agents). A token is the unit the model reads and writes: a word or a piece of a word, so a page of manual text is a few hundred tokens. The context window is the maximum number of tokens one call can hold, input and output together. Anything outside it does not exist for the model.

Two limits follow, and you need both. The first is a hard limit: past the window, the call fails or the oldest text is dropped. The second is soft: Anthropic's post describes context rot, the observed decline in the model's ability to recall information accurately as the token count grows, and treats context as "a finite resource with diminishing marginal returns" (same source). It describes the decline as a gradient, not a cliff. Research agrees: a study of long inputs found that accuracy is highest when the relevant passage sits at the beginning or end, and drops when it sits in the middle, even in models built for long contexts (Liu et al., Lost in the Middle).

A third limit is cost. You pay per token the model reads and per token it writes, so every token in context costs money on every call that includes it. For a sponsor with a small budget, this is the limit that bites first.

A common mix-up

"A bigger window means I can paste in every manual and stop worrying." This is tempting because a window that holds a whole textbook sounds like unlimited knowledge. It is wrong for two reasons: you pay for every token on every call, and recall degrades as the window fills, particularly for material in the middle. A larger window raises the hard limit; it does not remove the soft one or the cost.

What is kept between steps 6 min

Within one request, the agent loop from the earlier session runs several model calls. The model keeps nothing between those calls. What looks like memory is the program re-sending the whole message history, the list of everything said and done so far, with each new item appended. Here is the idea in code:

messages = [{"role": "user", "content": question}]
while True:
    reply = call_model(system_prompt, tools, messages)   # model sees ALL of messages
    messages.append(reply)                               # keep its output
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_request)                # program runs the tool
    messages.append(tool_result(result))                 # keep the result

The list messages is the only thing that carries information from one step to the next. Delete an item from it and the model has never seen that item. This is also why cost grows faster than the number of steps: call 1 sends the base context, call 2 sends the base plus step 1, call 3 the base plus steps 1 and 2, and so on. With a base of b tokens, each step adding a tokens and n calls, the total input tokens billed are

total = n·b + a·(0 + 1 + … + (n−1)) = n·b + a·n(n−1)/2

The second term is quadratic in n. A long loop with large tool results is therefore expensive, and a bloated first call is paid for on every step.

The program can edit the history. Anthropic's post names two ways, both tools for keeping the window small during one long task. Compaction means summarizing a conversation that is nearing the limit and starting a new window with the summary. Tool result clearing means deleting old tool outputs once they have been used, which the post calls "one of the safest lightest touch forms of compaction" (Anthropic). For the makerspace assistant, a long manual excerpt that has already produced its answer is a good candidate for clearing: the answer stays, the 3,000 tokens of excerpt go.

What is kept between sessions 7 min

A session is one conversation or task, from the first message to the end. When it ends, the message history is gone unless your program saved it. A fresh session starts with an empty context. So a student who was certified on the laser cutter last week is, to a new session, a stranger. The model cannot remember them; only your program can, by saving information outside the context window and loading it back in.

Anthropic calls one pattern structured note-taking (also called agentic memory): the agent regularly writes notes to storage outside the context window, and those notes are pulled back in at later times. Its examples include a to-do list and a NOTES.md file, and it describes an agent playing a game that kept tallies and maps across thousands of steps (Anthropic). The platform provides a memory tool built on this idea: Claude can create, view, edit and delete files under a /memories directory, and checks that directory before starting a task (Memory tool documentation).

Notice how this fits what you already know. Memory is just another tool. The model writes a request ("create the file /memories/riley.md with this text"), and your program carries it out and returns a result. The documentation is explicit that the operations are client-side: the application executes them against storage you control, and Anthropic does not store the files (same source). What you build is the storage and its rules.

What to save, and what to leave out

Notes are only useful if they are small, durable and correct. Save facts that stay true across visits and are cheap to store: "Riley: laser cutter certified 2026-10-02; 3D printer not certified." Do not save raw conversation or manual text; the manuals already exist elsewhere and belong to retrieval. The documentation also lists cautions you must handle in your own code: validate every file path so it stays inside /memories, cap file sizes, and expire files nobody reads (Memory tool documentation). A training status is a fact that should come from the booking system's records, not only from a note the model wrote; notes can be wrong, and a wrong note about safety training is a real hazard. That is a design-review argument.

A common mix-up

"The assistant will just remember the student from last time." Tempting because chatbots in a product often seem to do this. But remembering is a feature someone built: a program saved something and loaded it again. Without that, a new session knows nothing about earlier ones, however capable the model.

Retrieval: finding the right page 6 min

Retrieval means fetching only the pieces of a large body of text that a question needs and placing just those in the context. The manuals are the case: one 300-page manual is far too large to include every call, and a question needs maybe two paragraphs of it. The usual method is to split the manual into chunks of a few hundred tokens, convert each into an embedding, which is a list of numbers (a vector) produced by a model so that texts with similar meaning get vectors pointing in similar directions, and store them. At question time you embed the question the same way and rank chunks by similarity.

The standard similarity is cosine similarity: the cosine of the angle between two vectors,

cos(q, c) = (q · c) / (|q| · |c|)

It is 1 when the vectors point the same way, 0 when they are unrelated (perpendicular), and ignores the vectors' lengths, as correlation ignores scale. You take the top few chunks and add them to the context. This is the retrieval that happens before the model is called.

Anthropic's post describes an alternative it says is growing: just-in-time retrieval. The agent keeps lightweight references, such as file paths or search queries, and loads data into context at runtime through tools. Claude Code, for example, uses grep and glob instead of pre-built embeddings. The trade-off the post names is that runtime exploration is slower and can waste context without good tools. It also notes hybrids, and says that "do the simplest thing that works" will likely remain the best guidance (Anthropic).

For your assistant that suggests a plan. Give the model a tool such as search_manuals(machine, query) that returns the top three chunks, each labelled with machine and page. The model decides when to call it, and the result enters the context like any tool result, so the earlier rules apply: keep results short, and clear them once used. Retrieval is thus not separate from the agent loop; it is one more tool.

A common mix-up

"Retrieval is the same thing as memory." They share a mechanism, text loaded into context on demand, but they hold different things. Notes hold what the agent learned about particular students or tasks, written by the agent. Retrieval holds a corpus that existed before the conversation, such as manuals. Mixing them leads to storing manual text in student notes, or training status in the manual index.

Worked example and practice 3 min

Worked example: the cost of one request

A student asks a question that needs 5 model calls. The base context (system prompt, tool descriptions, question) is 3,000 tokens, and each step adds 1,500 tokens (the model's request plus the tool result). How many input tokens are billed in total?

  1. Write the input of each call: 3,000; 4,500; 6,000; 7,500; 9,000, because each call includes everything before it.
  2. Sum them: 3,000 + 4,500 + 6,000 + 7,500 + 9,000 = 30,000.
  3. Check with the formula: n·b + a·n(n−1)/2 = 5·3,000 + 1,500·10 = 15,000 + 15,000 = 30,000.
  4. Interpret: half the bill is re-reading history, not new information. Shrinking b by 1,000 tokens saves 5,000 per request; clearing a used 1,500-token result before call 5 saves 1,500.
Your turn

Another request needs 6 calls, with a base of 2,000 tokens and 2,000 added per step. Step one is given: the call inputs are 2,000; 4,000; … Finish: list all six inputs, sum them, and confirm with the formula.

Show a solution

Inputs: 2,000; 4,000; 6,000; 8,000; 10,000; 12,000. Sum = 42,000. Formula: 6·2,000 + 2,000·15 = 12,000 + 30,000 = 42,000.

Your turn, retrieval

The question vector is q = (3, 4). Three chunk vectors are D = (6, 8), E = (4, 3) and F = (0, 5). Compute the cosine similarity of each with q and rank them. (Hint: |q| = 5, and the cosine of D is computed as 48 / (5 · 10).)

Show a solution

D: 48 / (5·10) = 1.00. E: (12 + 12) / (5·5) = 0.96. F: (0 + 20) / (5·5) = 0.80. Rank: D, E, F. D points the same direction as q even though it is twice as long, which is why cosine is preferred to raw dot product.

Summary 2 min

  • The model sees only its context window on each call, limited by a hard size, by recall that weakens as it fills, and by cost per token.
  • Between steps, the only memory is the message history your program re-sends; cost grows as n·b + a·n(n−1)/2, and you control it with clearing and compaction.
  • Between sessions, nothing survives unless your program saves notes and loads them back; memory is a tool you build the storage for.
  • Retrieval fetches the few chunks of a large corpus a question needs; notes hold agent-learned facts. They are different stores.
