The context window and why it costs money 9 min

The general idea: a language model remembers nothing between calls. Everything it can use to answer must be written into the text you send it on that call. A token is the unit of text the model reads and writes, roughly a short word or a piece of a longer word; a page of a manual is on the order of several hundred tokens. The context window is the maximum number of tokens the model can take into account in one call, counting what you send and what it writes. It limits how much the model can see at once, and, because model usage is typically billed per token, the tokens you send are also what you pay for.

An everyday analogy: a goalkeeper has no memory of the previous match. Before each match the coach hands over a sheet of paper, and the keeper plays using only that sheet. The sheet has a maximum size, and the coach pays by the page. Every call to the model is a new match, and the context is the sheet.

The concrete consequence is the part most beginners miss. In the agent loop, every step is a separate model call, and the program must resend everything that is still relevant on every call. Nothing is stored inside the model between steps.

What is in the context

At each call the context holds four kinds of content:

  • System prompt: the standing instructions that define the assistant's role and rules.
  • Tool definitions: the name, description and arguments of every tool, so the model knows what it may request.
  • Conversation so far: the student's messages, the model's earlier replies and tool requests.
  • Tool results: what each tool returned, such as calendar entries or manual text.

Anthropic's engineering team describes context as a finite resource: the model has a limited "attention budget", and as the number of tokens grows, its ability to accurately recall information from that context decreases, an effect they call context rot (Effective context engineering for AI agents). So a larger window does not mean "put everything in". The goal is the smallest set of high-signal tokens that gets the job done.

Worked example: the cost of one request

The student asks: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" Assume the system prompt, tool definitions and question total 2,050 tokens. Each step adds 100 tokens (the model's tool request) plus 1,500 tokens (the tool's result), so 1,600 per step. The model makes 3 tool requests and then writes the final answer, which is 4 calls.

  1. Input size of call 1: 2,050.
  2. Call 2 resends everything and adds one step: 2,050 + 1,600 = 3,650.
  3. Call 3: 3,650 + 1,600 = 5,250.
  4. Call 4: 5,250 + 1,600 = 6,850.
  5. Total input tokens processed: 2,050 + 3,650 + 5,250 + 6,850 = 17,800, not the 2,050 + 3 × 1,600 = 6,850 you might expect by adding only the new content once.
  6. At a made-up price of $3 per million input tokens, this is 17,800 × 3 / 1,000,000 ≈ $0.053 for one student question, before counting the output tokens.

The math behind it: with a fixed base of B tokens and s tokens added per step, call k has input B + (k−1)s. Over n calls the total is nB + s·n(n−1)/2. The first term is linear in the number of calls; the second grows with the square of the number of calls. Long agent runs therefore get expensive faster than they get long. For a Statistics graduate: this is an arithmetic series, and the quadratic term is what your budget must control.

Some providers discount input that repeats exactly from the previous call (prompt caching), which softens the cost of the fixed grey block. Check your provider's pricing before relying on it; the lesson's arithmetic is the undiscounted worst case. Anthropic's contextual-retrieval write-up, cited below, uses prompt caching for exactly this reason.
A common mix-up

"The model remembers the conversation, so I only need to send the new message." It is tempting because chat apps feel like talking to someone who remembers. The model has no memory between calls: the chat app silently resends the earlier messages every time. If your code sends only the newest message, the model will not know what the student said a minute ago.

What is kept between steps 7 min

Between steps of one run, the thing that is kept is a plain list in your program: the message history, an ordered list of everything said so far (student message, model request, tool result, model request, and so on). The program appends to this list after each step and sends the whole list on the next call. This is the entire mechanism of "working memory" in an agent. It is not inside the model; it is a Python list that you own.

messages = [{"role": "user", "content": question}]

while True:
    reply = call_model(system_prompt, tool_definitions, messages)   # a fresh call every step
    messages.append(reply)                                          # keep what the model said
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_name, reply.tool_args)             # the program runs the tool
    messages.append({"role": "tool", "content": result})            # keep what came back

This code is schematic: real provider libraries use their own message formats, but the shape is the same everywhere. Notice what you control. Because you own the list, you can decide what to append, what to shorten and what to drop before the next call. Every strategy in this lesson is a decision about that list.

What this means for the loop you already know

  • Each model call sees the system prompt, the tools and the full list, then writes one new message.
  • The model "knows" what a tool returned only because the program appended the result.
  • If the program forgets to append a result, the model has no way to know the tool ran.
  • A step limit (from the agent-loop session) also limits cost, since each extra step is more expensive than the last.

When the context grows too large 9 min

Because the list grows each step, long runs hit two limits: the window's hard maximum, and the budget. Three standard remedies exist, in order from simplest to most complex. In each, the program edits the list before the next call.

RemedyWhat the program doesWhat is lost
Clearing old tool resultsReplace a stale, bulky tool result with a short placeholder such as "[result cleared]".The raw text; the model can call the tool again if it needs it.
Summarizing (compaction)Ask the model to write a short summary of the history, then start a new list from the summary.Detail; whatever the summary leaves out is gone from this run.
Noting outside the contextHave the model write key facts to a file or database, then reread them when needed.Nothing immediately; but it costs a tool call to read it back.

Anthropic's announcement of its context-management features describes the first and third remedies as products: context editing automatically clears stale tool calls and results as the limit nears, and a memory tool lets the model store and read information outside the context window using a file-based system that runs client-side in a directory the developer controls (Managing context on the Claude Developer Platform). The post reports gains from combining them on an internal agentic-search evaluation; treat such numbers as the vendor's own measurements, and test on your own task.

Which tool results should be cleared?

A good rule: clear results that are bulky, already used and cheap to fetch again. In the makerspace assistant, a 1,500-token page from the laser-cutter manual was needed to answer one question and is unlikely to be needed after the answer is written. The student's calendar result, by contrast, is short and may be needed to complete the booking. Soccer analogy: a coach does not keep every pass from the first half in front of them at the final whistle; they keep the score and the substitutions.

Worked example: clearing pays off

Take a run like the one in Section 1, with a base of 2,050 tokens and 4 calls. Here step 1 is a manual search (100-token request plus a 1,500-token page, so 1,600), and steps 2 and 3 are short calendar and training-record lookups (100 plus 300, so 400 each). The program clears the page, replacing it with a 20-token placeholder (so step 1 shrinks to 120), once the model has read it, which is from call 3 onward.

  1. Call 1: 2,050.
  2. Call 2 sees step 1 in full, because the model has not yet read the page: 2,050 + 1,600 = 3,650.
  3. Call 3 sees step 1 cleared (120) and step 2 (400): 2,050 + 120 + 400 = 2,570.
  4. Call 4: 2,050 + 120 + 400 + 400 = 2,970.
  5. Total: 2,050 + 3,650 + 2,570 + 2,970 = 11,240. Without clearing, calls 3 and 4 would carry 1,600 for step 1 instead of 120, which is 2 × 1,480 = 2,960 more: 14,200.

The saving comes from not paying repeatedly for one bulky result after it has done its job.

A common mix-up

"A bigger context window removes the need to manage context." It is tempting because the limit stops being the visible problem. But you still pay for every resent token, and the model's recall of facts buried in a very long context gets worse (context rot, cited above). A big window raises the ceiling; it does not remove the cost or the accuracy decline.

What is kept between sessions 10 min

A session is one conversation or run, from the student's first message to the end. When the program exits, the message list is gone. By default, nothing is kept between sessions: the next time the same student opens the assistant, the model has never met them. To remember anything across visits, the program must write it to storage (a file or a database) during or after one session, and load it into the context at the start of the next. That stored information is what we call long-term memory; the message list is short-term memory or working memory.

Two kinds of things to save

The design choice that matters for your assistant is what form the saved information takes.

  • Structured records: facts with a fixed shape and a single correct value, such as "student 4412 completed laser-cutter training on 2026-10-03". These belong in a database the program (or a tool) reads and writes exactly. The model should look them up, not recall them, and should never be the only place such a fact is stored.
  • Notes: free-text observations the model writes for its future self, such as "the bandsaw manual's blade-change section is under 'Maintenance', not 'Operation'", or "this student prefers evening slots". They are fuzzier, may be wrong, and are good for what you could not predict in advance.

The memory tool in Anthropic's announcement is of the second kind: the model reads and writes files through tool calls, and the developer chooses where they are stored (Anthropic, context management). The same post describes the principle you can apply to any provider: the model decides what to write down, the program stores it, and later sessions read it back.

Notes as memory: an example

Suppose the assistant keeps a file notes.md. At the end of each session, it appends a line. At the start of the next, the program loads the file into the context. In code:

def start_session(student_id):
    record = db.get_training_record(student_id)      # structured, exact
    notes  = read_file(f"notes/{student_id}.md")     # free text, may be empty
    system = BASE_PROMPT + "\nTraining record: " + str(record) + "\nNotes:\n" + notes
    return system, []                                # fresh, empty message history

The loaded memory costs tokens on every call of the session, like the grey block in Figure 1. Therefore memory must stay short. A notes file that grows without limit is a context problem arriving by another route. Keep notes short, dated and edited, and load only the ones relevant to the current request.

A common mix-up

"The assistant learns from each student and gets smarter over time." It is tempting because the assistant's answers improve when notes are loaded. But the model's parameters did not change: it is the same model reading a longer or better prompt. Remove the notes and the "learning" disappears. Memory in an agent is text that is stored and reloaded, not training.

Retrieval: finding the right page in a long manual 12 min

The general idea: when the knowledge is too large to fit in the context, or too costly to send on every call, keep it outside and bring in only the few pieces that bear on the current question. Retrieval is that act of searching an external collection and putting the best matches into the context. A manual of 400 pages is perhaps 200,000 tokens; sending it on every call would be both too large and, by the arithmetic of Section 1, ruinous. The usual pattern, called retrieval-augmented generation (RAG), prepares the collection once, in advance.

The three steps

  • Chunk: split the manuals into pieces, called chunks, of a few hundred tokens, ideally along section boundaries, so each chunk is about one thing.
  • Index: make each chunk searchable. Two common ways, often combined: a keyword index (such as BM25, which scores chunks by how many of the query's words they contain, weighting rare words more heavily), and an embedding index, which turns each chunk into a list of numbers (a vector) so that chunks with similar meaning have similar vectors.
  • Search: turn the question into the same kind of representation, score every chunk, and return the top k chunks (for example, the top 5). The program puts them in the context, or the model requests them with a tool such as search_manuals(query).

Similarity, with numbers

For embeddings, "similar" is usually measured by cosine similarity: the cosine of the angle between two vectors, cos = (a·b) / (|a| |b|), where a·b is the dot product (multiply matching entries and add) and |a| is the vector's length. It is 1 when vectors point the same way, 0 when they are at right angles. Real embeddings have hundreds or thousands of entries; use two to see the mechanics.

Worked example: ranking three chunks

Toy two-dimensional "meaning" axes: first entry = lasers, second entry = woodworking. The question "How do I focus the laser?" has vector q = (1, 0). Three chunks: A = (3, 4) (a mixed page), B = (1, 1) (an overview of both), C = (0, 2) (a woodworking page).

  1. |q| = 1. |A| = √(9+16) = 5. |B| = √2 ≈ 1.414. |C| = 2.
  2. q·A = 3, so cos(q, A) = 3 / (1 × 5) = 0.60.
  3. q·B = 1, so cos(q, B) = 1 / 1.414 ≈ 0.71.
  4. q·C = 0, so cos(q, C) = 0.
  5. Ranking: B (0.71), A (0.60), C (0). With k = 2, chunks B and A go into the context and C stays out.

Note that A has the largest raw dot product with q (3), but B ranks higher. Cosine ignores vector length and compares direction, which is the point: it asks "same topic?", not "bigger?".

Why retrieval fails, and what helps

Retrieval can return the wrong chunks, and then the model answers confidently from the wrong text. Two typical causes. First, a chunk loses its surroundings: a chunk reading "Set the power to 40%" does not say which machine or material. Second, the embedding misses exact strings such as an error code "E-47", where keyword matching does better. Anthropic's contextual retrieval work addresses both: it prepends a short explanation of where the chunk comes from to each chunk before indexing, and it combines embeddings with BM25. In their tests, the rate of failing to find the right chunk in the top 20 fell from 5.7% with plain embeddings to 3.7% with contextual embeddings and to 2.9% when combined with contextual BM25 (Introducing Contextual Retrieval). Those are measurements on their datasets, not guarantees for your manuals; the method to copy is to measure on your own questions.

Retrieval as a tool

Two designs exist. In upfront retrieval, the program searches before the first model call and inserts the top chunks. In just-in-time retrieval, the model gets a search tool and decides when and what to search, and can search again if the first results miss. Anthropic's context-engineering post describes agents that keep light references and load data at runtime with tools, at the price of being slower than precomputed retrieval, and notes that a hybrid is often best (Effective context engineering for AI agents). For your assistant, which already runs a tool loop, search_manuals as a tool is the natural fit. The tool's description is what tells the model when to use it, which you have already studied.

A common mix-up

"Retrieval lets the model read the whole manual." It does not. Retrieval selects a handful of chunks, and the model sees only those. If the answer is on a page that was not retrieved, the model cannot see it, and may answer from guesswork. Test retrieval by asking whether the right chunk was in the top k, separately from whether the final answer was good.

Worked example and practice: designing the assistant's memory 8 min

Now apply all three tools, context, saved storage and retrieval, to the makerspace assistant. The question for each piece of information is: how often is it needed, how large is it, how exact must it be, and does it change?

Worked example: where does each fact live?

For each item, pick a home.

  1. "You are a makerspace assistant; never book without confirming the time." Needed on every call, small, fixed. Home: system prompt, in the context every call. Cost: paid per call, so keep it short.
  2. The laser-cutter manual, 120 pages. Large, needed in small parts for each question. Home: retrieval index; search returns the top 3 to 5 chunks.
  3. Student 4412 completed laser training on 2026-10-03. Small, exact, changes over time, needed across sessions. Home: database, read by a tool such as check_training_record or loaded at session start.
  4. "This student's last booking request was for Friday afternoon." Small, helpful but not critical, fuzzy. Home: notes, loaded at session start, with a size cap.
  5. The page returned by the manual search, once the answer is written. Large, used up. Home: cleared from the history; the search can be repeated.

The pattern is a decision, not a rule: the more often an item is needed and the smaller it is, the closer it sits to the context; the larger and rarer, the further out.

A common mix-up

"Put the training status in the system prompt for every student, so it is always there." Tempting for simplicity. It does not scale: with 2,000 students, the prompt is huge and every call pays for it. Load only the current student's record, or let the model look it up with a tool when it needs it.

Summary 2 min

  • The model keeps nothing between calls; the context window is everything it can see in one call, and you pay for every token you send.
  • Between steps, memory is the message list your program resends; its cost grows roughly with the square of the number of steps, so clear or summarize what is bulky and finished.
  • Between sessions, nothing persists unless the program saves it: exact facts in a database, loose observations as short notes, loaded into the next context.
  • Retrieval keeps large knowledge outside the context: chunk, index (keyword and embeddings), return the top k; test whether the right chunk was found before judging the answer.
