Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it lives in the context window, in a saved note, or in a searchable store, and defend the choice by its cost.

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, on a small budget. Both problems are memory problems, and every choice you make about them shows up in the cost of each request. At your design review you will be asked where information lives and why.

Recall

The model produces text one token at a time. What is a token, roughly?

Check your answer

A token is a small chunk of text, often a short word or part of a word. Models read and write in tokens, and usage is measured and billed in them. Hold onto that: today every limit and every cost is counted in tokens.

The context window, and what it holds at each step 6 min

The context window is everything the model can see when it produces its next output: the instructions, the tool descriptions, the conversation so far and every tool result. It has a maximum size measured in tokens. Nothing outside it exists for the model. The model does not "look things up" in the background; it reads this one block of text, and writes the next piece.

An analogy from soccer: the context window is the pitch, not the whole squad. A player on the bench has no effect on the play. Whatever you want the model to use must be on the pitch for that call, and the pitch has a fixed size.

For the makerspace assistant, one model call might contain these parts, in this order:

  • System prompt: the standing instructions ("You answer questions about makerspace machines; never book without confirming the time").
  • Tool descriptions: the name, purpose and parameters of check_calendar, search_manuals and book_machine.
  • The conversation: the student's messages and the assistant's earlier replies.
  • Tool calls and tool results so far in this request.

Two consequences follow, and both matter for your budget.

  • Cost scales with window size, per call. You pay for the tokens the model reads and writes. A request with five model calls reads the fixed prefix five times, plus each result every time after it arrives. Anthropic notes that repeated prefixes can be cached to cut cost and latency, reporting reductions of up to 90% in costs for its own example (Anthropic, Contextual Retrieval). Caching lowers the price of the repeated part; it does not make the window smaller.
  • More is not better. Anthropic describes context rot: as the number of tokens in the window increases, the model's ability to accurately recall information from it decreases, so the window is a finite resource with diminishing returns. The stated goal is the smallest possible set of high-signal tokens (Anthropic, Effective context engineering for AI agents).
A common mix-up

"A bigger window means I can paste in everything and skip the rest." It is tempting because a large window does fit a whole manual. But you pay for those tokens on every call of every request, and recall degrades as the window fills. Size is a ceiling on what fits, not a reason to fill it. A statistician's version: the window is a sample budget, and adding noisy observations lowers the signal you can extract per token.

What is kept between steps 5 min

Here is the fact that surprises most newcomers: the model keeps nothing between calls. Each call is a fresh reading of the window. What looks like the model "remembering" step one at step four is the program having appended step one to the window and sent the whole thing again. The message history (the list of everything said and every tool result so far) is a Python list your program owns. If you forget to append a result, the model never sees it.

messages = [{"role": "user", "content": question}]
while True:
    reply = call_model(system_prompt, tools, messages)   # one model call
    messages.append(reply)                               # keep the model's output
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_request)                # the program runs the tool
    messages.append(tool_result_message(result))         # keep the result

This is the loop from the last session, with the memory made visible. The "memory between steps" is exactly the list messages. It is cleared when the function returns, unless you save it somewhere (next section).

That list grows with every step, so a long request can fill the window. A long-running agent therefore needs a way to shrink it. Anthropic describes two techniques that act inside one session:

  • Compaction: when the window nears its limit, summarize its contents and start a new window with the summary. Anthropic advises starting by maximizing recall (keep everything that might matter) and then trimming for precision.
  • Clearing old tool results: once a tool result was used, it can be dropped from the window. Anthropic calls this one of the safest, lightest-touch forms of compaction.

Both are in Anthropic's context-engineering post. For the makerspace assistant, a 20-page manual section returned by search_manuals is useful for one answer; after the student's question is answered it can be dropped, and only the one-line fact ("laser cutter, Friday 2 pm free") needs to stay.

What is kept between sessions: notes 6 min

A session is one conversation or task, from the first message to the end. When it ends, the window is gone. A student who returns next week meets an assistant that knows nothing about them, unless the program stored something and loads it back. The model has no automatic memory of earlier conversations; the system's builder creates it.

The simplest design is structured note-taking, which Anthropic also calls agentic memory: the agent regularly writes notes to storage outside the context window and reads them back when needed. Anthropic's examples are a to-do list and a NOTES.md file, and it also mentions a file-based memory tool (Anthropic). Your tutor works this way: this workspace's own NOTES.md is how it remembers you from one session to the next.

For the makerspace assistant, a note is a record per student, stored in a file or a database:

{
  "student_id": "s-1042",
  "trained_on": ["laser_cutter", "3d_printer"],
  "last_booking": "2026-11-12 laser_cutter",
  "preferences": "mornings"
}

The design questions are then three: what to write (facts that are expensive to rediscover, such as training status), when to write (after a verified event, such as a completed training, not after every chat), and when to read (at the start of a session, or only when a tool call needs it).

A common mix-up

"The assistant remembers a student because it talked to them before." It is tempting because chatbots in an app often do appear to remember. But what you see is a product that stores history and reloads it. In your assistant, no storage means no memory; and saving everything and reloading all of it fills the window with old chat. Save the few facts that matter and load only those.

Retrieval: finding the right page in a long manual 7 min

Notes are small. Manuals are not: a long manual can run to hundreds of pages, and the answer to a question is on one of them. Retrieval means selecting the few passages relevant to the question and placing only those in the window. This pattern is often called RAG, retrieval-augmented generation: retrieve first, then let the model generate an answer from what was retrieved.

First, check whether you need it. Anthropic's advice is that if your knowledge base is smaller than 200,000 tokens (about 500 pages), you can include the whole thing in the prompt, using prompt caching to keep the cost down (Anthropic, Contextual Retrieval). That figure is from a 2024 post, and the cost trade-off from context rot above still applies, so test it on your own manuals before committing. A fixed set of a few machine manuals may be small enough to skip retrieval entirely.

When retrieval is needed, the standard recipe has these steps:

  • Chunk: split each manual into chunks, passages of a few hundred tokens. Where you cut matters, because a chunk should hold a complete idea.
  • Embed: an embedding turns a chunk into a list of numbers (a vector) so that chunks with similar meaning lie close together. Statistician's view: each chunk becomes a point in a high-dimensional space, and "relevant" means nearest to the query's point, for example by cosine similarity.
  • Search: embed the question the same way and find the nearest chunks. Embeddings match meaning ("how do I cut thick acrylic" finds the passage on "material thickness limits") but can miss exact strings.
  • Add keyword search: BM25 is a keyword-ranking method that scores chunks by how often the query's words appear, weighted by how rare the words are. It is strong for unique identifiers: Anthropic's example is the error code "TS-999". Your manuals have many (error codes, part numbers), so the combination matters. The two result lists are merged with rank fusion.
  • Rerank (optional): retrieve more candidates, say 150, score them with a more careful model, and keep the best 20 (Anthropic's setup). It adds a little latency.

Anthropic's measurements show how much each step buys. It measured the share of questions for which the right chunk was missing from the top 20 results: 5.7% for plain embeddings, 3.7% after adding to each chunk a short generated note saying where it sits in its document ("contextual embeddings"), 2.9% with contextual BM25 as well, and 1.9% with reranking. These are Anthropic's own results on its own datasets, so treat them as direction, not as a promise for your manuals. The reason for the chunk note is plain: a chunk saying "the limit is 6 mm" does not say which machine it is about, and a one-line prefix ("Laser cutter manual, cutting section") fixes that.

Retrieval as a tool the agent calls

There are two ways to wire retrieval in. Up front: the program searches before the first model call and pastes the results in. Just in time: search_manuals is a tool, so the model decides when and what to search, and can search again if the first results miss. Anthropic describes agents that keep lightweight identifiers (file paths, queries) and load data at runtime with tools, at the price that runtime exploration is slower than precomputed retrieval, and recommends a hybrid: some data up front, the rest on demand (Anthropic). Your design is already the second kind, because search_manuals is in your tool list.

A common mix-up

"Retrieval means the model has learned the manuals." It has not. Retrieval changes what is in the window for one call; the model's training is unchanged and nothing is stored in it. If the search returns the wrong page, the model answers from the wrong page, fluently. This is why retrieval quality (the failure rates above) is the number to watch.

Worked example and practice 6 min

Worked example: what does one request cost?

A student asks, "Can I use the laser cutter on 6 mm acrylic Friday?" The assistant makes five model calls. The fixed prefix is 3,000 tokens, and every step adds 1,500 tokens (illustrative numbers). Compare two designs: (A) paste the whole 50,000-token manual in the prefix; (B) retrieve 3 chunks of 400 tokens, which arrive as one tool result at step 2. Count input tokens read, ignoring caching.

  1. Count window size per call without the manual. Call k reads 3,000 + 1,500 x (k - 1): 3,000, 4,500, 6,000, 7,500, 9,000. The sum is 30,000 tokens.
  2. Design A: the 50,000-token manual is in every call, so add 5 x 50,000 = 250,000. Total: 280,000 tokens.
  3. Design B: the 1,200 retrieved tokens appear at step 2, so they are read in calls 3, 4 and 5 (assume they replace part of that step's 1,500): add 3 x 1,200 = 3,600. Total: 33,600 tokens.
  4. Compare: 280,000 / 33,600 is about 8.3, so design A reads roughly eight times as many tokens for this request, before any caching discount.
  5. Interpret: caching (up to 90% off the repeated prefix, per Anthropic) narrows the gap but A still reads a much larger window, with more context rot. B is also cheaper to run on a 50-manual library, where A no longer fits.

Show a model answer

Saving transcripts does not change the model; it only gives the assistant text it could load, and loading old chats fills the window, which raises cost per call and lowers recall. Better to save a few verified facts per student and retrieve manual passages on demand, so each call carries only what it needs.

Summary 2 min

  • The context window is everything the model sees in one call. It is finite, paid for in tokens on every call, and recall falls as it fills.
  • The model keeps nothing between calls; the program's message list is the memory between steps. Compaction and clearing old results keep it small.
  • Between sessions, memory exists only if you save it: small structured notes, written when a fact is verified and loaded when needed.
  • For long manuals, retrieval puts only the best chunks in the window: embeddings plus BM25 keyword search, optionally reranked. Skip it if the whole knowledge base is small enough to fit and be cached.
