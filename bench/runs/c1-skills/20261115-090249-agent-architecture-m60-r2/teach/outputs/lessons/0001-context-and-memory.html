The context window 8 min

The context window is everything the model can read when it writes its next output: the instructions, the tool descriptions, the conversation so far and any tool results. It is the model's entire working view. The model keeps no hidden copy of earlier calls: if a fact is not in the window of this call, the model does not have it (Claude docs: context windows).

The window is measured in tokens, the pieces of text a model reads and writes; a token is a short chunk of characters, often a word or part of a word. English text averages somewhere around three-quarters of a word per token, so a 1,000-word page is roughly 1,300 tokens. The window has a fixed maximum size, and what you put in it counts against that maximum. Tokens also determine cost: you pay for the tokens you send in and the tokens the model writes out.

An analogy from soccer: the window is the pitch, not the squad. Only the players on the pitch can take part in this play. Players on the bench (your manuals, last week's bookings) exist, but they affect nothing until you bring them on. Choosing who is on the pitch for each play is the job.

Your learner file says you have heard "token" and "context window" but could not say what they limit. They limit two things: how much the model can read at once (the maximum), and how much each call costs (every token in the window is billed on every call). The second one is the one your budget feels.
A common mix-up

"The model remembers what I told it earlier." It is tempting because a chat app feels continuous. But the model itself is stateless between calls: the chat app resends the earlier messages each time, and that resending is what looks like memory. If your program forgets to send a message, the model has never seen it. Likewise, a new session starts with an empty window unless your program fills it. Nothing is remembered automatically between conversations.

What is kept between steps 8 min

Because the model keeps nothing, the agent loop works by appending: after each step, your program adds the model's tool request and the tool's result to a list of messages, and sends the whole list on the next call. Step 4 therefore carries steps 1 to 3 inside it. This is what "kept between steps" means: not a model feature, but a growing list that your code maintains and resends.

This has a direct consequence for cost. Let S be the fixed part (system prompt and tool descriptions), q the question, and a_i the size of the model's request plus the tool result added at step i. The input the model reads on call n is

input_n = S + q + a_1 + a_2 + ... + a_(n-1)

and the total input over a run of N calls is the sum of these. The total grows faster than linearly in the number of steps, because early results are paid for again on every later call. If each step adds about the same amount a, total input is roughly N(S+q) + a·N(N-1)/2, a quadratic term. Two ways to lower cost follow: take fewer steps, and keep each result small.

The model's output is billed too, but in an agent it is usually short (a tool request), while the input grows. This lesson tracks input; check your provider's pricing page for rates, which change. Some providers also discount repeated, identical prefixes through a feature called prompt caching; that is worth a look when you build, but it does not change what the model sees.

Worked example: what a request costs 8 min

Worked example

The system prompt plus tool descriptions take 2,000 tokens (S). The student's question takes 50 tokens (q). The run is: check_calendar, search_manuals, check_training_record, final answer, which is 4 model calls (the loop from learning record 0002). Each model tool request takes 100 tokens, and each tool result takes 1,000 tokens. How many input tokens does the whole run read?

  1. Call 1 reads S + q = 2,000 + 50 = 2,050.
  2. Call 2 adds the first request and result: 2,050 + 100 + 1,000 = 3,150.
  3. Call 3 adds the second pair: 3,150 + 1,100 = 4,250.
  4. Call 4 adds the third pair: 4,250 + 1,100 = 5,350.
  5. Total input = 2,050 + 3,150 + 4,250 + 5,350 = 14,800 tokens.
  6. Compare with a naive guess that each call reads only its own new content plus the fixed part: 4 × 2,050 = 8,200. The difference, 6,600, is the cost of resending history.

Notice that no single call is large. The run is expensive because four moderate calls each include the earlier ones. A fixed workflow that made the same three lookups in a fixed order inside one program, then called the model once with the three results, would read about 2,050 + 3,300 = 5,350 tokens. That is the argument you will make at your design review for putting predictable steps in code and not in the loop.

Show a solution

Call 2: 2,050 + 100 + 1,000 = 3,150. Call 3: 3,150 + 100 + 4,000 = 7,250. Call 4: 7,250 + 100 + 500 = 7,850. Total: 2,050 + 3,150 + 7,250 + 7,850 = 20,300 tokens. The manual page (4,000 tokens) is the costliest: it is read on call 3 and again on call 4, so it is billed twice, which is 8,000 tokens of the 20,300. Had it come last, it would have been read once. Order matters, and so does shrinking that result, which is what retrieval, later in this lesson, does.

In code, the loop is a list that grows. Here is the part that matters, with the model call left as a placeholder because you have not called a model from code yet:

messages = [{"role": "user", "content": question}]

for step in range(MAX_STEPS):               # the stopping limit
    reply = call_model(system=SYSTEM, tools=TOOLS, messages=messages)
    messages.append({"role": "assistant", "content": reply})   # keep the model's turn
    if reply.is_final:
        break
    result = run_tool(reply.tool_name, reply.tool_args)         # the program runs it
    messages.append({"role": "user", "content": result})        # keep the result

# 'messages' is the agent's whole short-term memory.
# It is resent in full on every pass through the loop.

The exact message format differs between providers; the pattern does not. Every decision about "what the assistant keeps in its context" is a decision about what your code does to messages before each call.

When the window fills or degrades 7 min

A longer list has three problems. First, cost, as computed above. Second, the hard maximum: a long run can overflow the window, and then the call fails or old content must be removed. Third, quality: Anthropic reports that as the number of tokens in the window grows, the model's ability to recall information from it decreases, a pattern they call context rot, so the goal is the smallest set of high-signal tokens that makes the right behavior likely (Anthropic: effective context engineering). A bigger window raises the maximum but does not remove the second and third problems.

The practice of choosing what goes into the window at each call is context engineering. Three common tools for it:

  • Trim tool results. Have the tool return only what the model needs: three calendar slots, not the whole week's JSON. This is the cheapest fix and you control it in your tool code.
  • Clear old results. Once the model has used a large result, replace it with a one-line placeholder such as "[manual page for laser cutter: removed]". Anthropic's platform offers this as context editing, and reports it as one of two techniques that improved results on a long agent task (Anthropic: context management).
  • Summarize. When the list nears the limit, ask the model to write a short summary of the conversation and start a new window with that summary instead of the full history. This is called compaction. It is lossy: details not in the summary are gone.

Each tool trades something. Trimming costs you detail at the source. Clearing costs you the ability to look at the result again without calling the tool a second time. Summarizing costs you whatever the summary leaves out, and the model chooses what that is.

A common mix-up

"A bigger window solves the memory problem." It is tempting because a window that holds a whole manual seems to make retrieval unnecessary. But you pay for every token in it on every call, the model's recall of details can fall as the window grows, and the window still empties when the session ends. A big window is a bigger pitch; it does not help you remember last week's match.

What is kept between sessions: notes 8 min

A session is one conversation, from the first message until your program discards its message list. When it ends, the window is gone. To remember a student's training status next week, the program must persist something: write it to storage that outlives the session, such as a file or database, and load it into the next session's window. Memory in an agent is exactly this: save, then load. The model never "holds" it.

The simplest form is notes: short, structured facts the agent writes to storage and reads back later. Anthropic describes structured note-taking, where the agent regularly writes notes persisted outside the context window and pulls them back in later, as a technique for long tasks (Anthropic: effective context engineering). Its memory tool makes this a file-based system the model operates through tool calls such as create and edit (Anthropic: context management). Whether you use that tool or your own, the structure is the same: notes are written by a tool call, so the model decides when to write, and your program decides what is allowed.

For the makerspace assistant, the natural record is a small structured file per student, keyed by student ID:

{
  "student_id": "s123456",
  "trained_on": ["laser_cutter", "3d_printer"],
  "training_dates": {"laser_cutter": "2026-10-02"},
  "notes": "Prefers evening slots; asked twice about acrylic settings."
}

Two kinds of memory appear here, and they need different handling. The training status is a fact with authority: a safety decision depends on it, so it should be written by your booking or training system and read by a tool such as check_training_record, not be left to the model's note-taking. The "prefers evening slots" line is a soft note: convenient if right, harmless if stale. Rule of thumb: anything that gates access or safety is data in a system of record, read by a tool; anything that merely helps is a note.

Retrieval: finding the right page 12 min

A machine manual of 80 pages is perhaps 40,000 tokens. Putting it all in the window for every question would cost that much on every call and invite context rot. Retrieval fixes this: search the manuals first, and put only the few most relevant passages into the window. Giving the model the retrieved text with the question is called retrieval-augmented generation (RAG). In an agent, retrieval is simply a tool: search_manuals(query) returns a few passages, as in your three-tool example. Anthropic describes this as just-in-time retrieval: the agent keeps lightweight references and loads data into context only when needed, instead of pre-loading everything (Anthropic: effective context engineering).

How a retrieval index is built

  • Chunk. Split each manual into chunks, pieces of a few hundred tokens, often along headings. A chunk must be small enough to be cheap and large enough to make sense alone.
  • Index. Prepare the chunks for search. There are two common ways, and many systems use both.
  • Query. At question time, score chunks against the question, take the top k and return them to the model.

The first index type is keyword search, such as BM25, a scoring formula that ranks chunks by how often and how rarely the query's words appear in them. It is excellent for exact strings such as an error code or a part name like "Epilog Zing 24". The second is embedding search. An embedding is a list of numbers (a vector) that a model produces from text so that texts with similar meaning get similar vectors. You embed every chunk once, embed the question at query time, and rank chunks by cosine similarity, the cosine of the angle between two vectors:

cos(u, v) = (u · v) / (|u| |v|), between -1 and 1; larger means more similar in direction.

This matters because students do not use the manual's words: "my cut doesn't go all the way through" should find the section titled "Power and speed settings for thick material". Keyword search misses this; embeddings often catch it. Keyword search wins on exact identifiers. That is why a hybrid of both is common.

Worked example

Toy two-dimensional embeddings: the question is q = (1, 1). Chunk A (power settings) is a = (2, 1). Chunk B (cleaning the lens) is b = (0, 3). Which does cosine similarity rank first?

  1. Dot products: q·a = 1·2 + 1·1 = 3. q·b = 1·0 + 1·3 = 3.
  2. Lengths: |q| = √2 ≈ 1.414; |a| = √5 ≈ 2.236; |b| = 3.
  3. cos(q, a) = 3 / (1.414 × 2.236) ≈ 0.949. cos(q, b) = 3 / (1.414 × 3) ≈ 0.707.
  4. Chunk A is closer in direction, so it ranks first. Note that the raw dot products are equal: dividing by length is what removes the effect of a vector's size.
import math

def cosine(u, v):
    dot = sum(x * y for x, y in zip(u, v))
    return dot / (math.sqrt(sum(x*x for x in u)) * math.sqrt(sum(y*y for y in v)))

def top_k(query_vec, chunks, k=3):
    # chunks: list of (text, vector) pairs, embedded once in advance
    scored = sorted(chunks, key=lambda c: cosine(query_vec, c[1]), reverse=True)
    return [text for text, _ in scored[:k]]

Real embeddings have hundreds or thousands of dimensions and come from an embedding model, but the ranking step is exactly this. The retrieval result enters the window as one tool result, so every earlier rule applies: three chunks of 300 tokens is about 900 tokens, against 40,000 for the whole manual.

Why retrieval fails, and a fix

Retrieval can return the wrong chunk, and then the model answers from the wrong text. Statistically, think of each question as a trial that fails if the right chunk is not among the top k; the retrieval failure rate is the share of failing trials, and 1 minus it is recall at k. Anthropic observed that a chunk often loses the context it had in its document, such as which machine it is about, so they prepend a short model-written note situating the chunk before indexing. In their tests, this reduced the top-20 failure rate from 5.7% to 3.7% with embeddings, to 2.9% when combined with keyword search, and to 1.9% with reranking, a second step that reorders the candidates (Anthropic: contextual retrieval). These numbers are from Anthropic's own datasets, so treat them as an illustration of direction, not a promise for your manuals; you should measure on questions your students ask.

For your manuals the cheap version of the same idea is free: put the machine's name and section title at the top of every chunk, so that a chunk reading "Set power to 80%" is stored as "Laser cutter manual, Settings for acrylic: Set power to 80%".

A common mix-up

"Retrieval gives the model the whole manual to search." It does not: the search runs in your program, outside the model, and the model only ever sees the few chunks that come back. So if the index misses the right page, the model cannot recover it; it will answer from whatever it was given, and may do so confidently. This is also why a failed retrieval looks like the model "making things up".

Design the makerspace assistant 12 min

Now apply all three layers to your assistant. The question for each piece of information is: where should it live, and when does it enter the window? A useful order of questions:

  • Needed on every call? Put it in the fixed part (system prompt, tool descriptions). Keep it short, because it is paid for on every call.
  • Needed only for some requests? Put it behind a tool and fetch it just in time (calendar, training record, manual search).
  • Needed again in a later session? Persist it, as a system-of-record fact or a note, and load it at session start only if the request needs it.
  • Large and already used? Trim it at the source, or clear it from the list.
Worked example

Request: "Book me the laser cutter Friday at 3 and tell me how to cut 3 mm acrylic." Decide, item by item, where each piece of information lives.

  1. The assistant's rules and tone are needed on every call: fixed part, about 500 tokens, written tightly.
  2. The student's training status gates a booking: a check_training_record tool reads the system of record. It returns one line ("laser_cutter: trained 2026-10-02"), not the whole profile.
  3. Friday's calendar is needed once: a check_calendar(machine, date) tool that returns only free slots near 3 pm, not the full day.
  4. Acrylic settings are somewhere in a long manual: a search_manuals tool returns the top 3 chunks, each labeled with machine and section. Once the answer is written, the chunks add nothing for a later booking step, so a long session may clear them.
  5. The booking is an action: a book(machine, slot) tool, whose success is returned as a short result and also becomes the record other sessions read through the calendar.
  6. Next week: the new session starts empty. The assistant loads the student's one-line profile and nothing else; the earlier chat is not replayed, since it is not needed.

One more design question belongs in your design review: what is the failure when memory is wrong? A stale note about preferences means a slightly wrong suggestion. A stale training record means a student on a laser cutter without training. Spend your engineering effort in proportion to that consequence, and give the safety-relevant data an authoritative source.

Summary 4 min

  • The model sees only the context window of the current call. Nothing persists unless your program puts it there.
  • Between steps, "memory" is the message list your code appends to and resends in full. Cost grows with every step, because early results are re-read on every later call.
  • Fight growth by trimming tool results, clearing used ones and summarizing; a bigger window raises the limit but not the cost or the risk of context rot.
  • Between sessions, memory is save then load: notes or records in storage. Safety-relevant facts belong in a system of record read through a tool.
  • Retrieval is a tool that searches an index outside the model and returns a few chunks; keyword, embedding and hybrid search each fail in different cases, and a missed page cannot be recovered by the model.
