Context and memory in an agent

By the end of this lesson you can decide, for the makerspace assistant, what goes into the model's context on each step, what is saved between sessions, and how it finds the right page in a long manual, and you can estimate what each choice costs.

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, on a small budget. Both problems are context problems: what the model sees costs money on every step, and what it cannot see, it cannot use.

Warm-up 2 min

Recall

A student asks, "Is the laser cutter free tomorrow?" The model decides to use check_calendar. From memory: who actually runs that tool, and what happens to its result?

Check your answer

The program around the model runs the tool; the model only outputs a request naming the tool and its arguments. The program then puts the result into the model's next input and calls the model again. That second sentence is today's topic: "the model's next input" is the context, and we now look at what it holds.

The context window 5 min

A language model reads text as tokens, chunks of text roughly three-quarters of an English word long. The context window is the maximum number of tokens the model can take in for one call, its input and its own output together. Everything the model uses to produce its next words must be inside that window, because the model has nothing else: it has no hidden notepad and no access to your files. The Claude API documentation on context windows describes it as the model's "working memory" for a request, as distinct from the large body of training data it learned from.

In an agent, the context for one call is assembled by your program from several parts. Figure 1 shows the parts for the makerspace assistant.

Why this matters for cost: you are billed per token, and the whole context is sent again on every call. A system prompt and tool descriptions of 1,000 tokens cost 1,000 input tokens on call one, and again on call two, and again on call three. This is the "cost per request" lever in your mission, and the next section shows how fast it compounds.

Check yourself

The assistant's tool descriptions total 800 tokens. A request takes five model calls. About how many input tokens does that part cost for the request?

Show the answer

About 4,000: five calls times 800 tokens. Fixed parts of the context are paid for on every call.

What is kept between steps 5 min

The model itself keeps nothing between calls: each call is a fresh computation on whatever text it is given. What makes the loop feel continuous is your program, which keeps a list of messages and sends the whole list each time. The model's earlier requests and the tools' results are "remembered" only because the program appended them. If the program leaves something out, as far as the model is concerned it never happened.

messages = [{"role": "user", "content": "Is the laser cutter free Friday?"}]
while True:
    reply = call_model(system_prompt, tools, messages)   # whole list sent
    messages.append(reply)                               # model's output kept
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_request)                # program runs the tool
    messages.append(result)                              # result kept, sent next call

The list messages is the memory between steps. It is also the cost: step k sends everything accumulated in steps 1 to k−1. If the fixed part is B tokens and each step adds A tokens (the model's request plus the tool's result), call k has B + (k−1)A input tokens, so n calls cost

n·B + A·n(n−1)/2 input tokens.

The second term grows with the square of the number of steps. For a statistician: total cost is quadratic in the number of steps, with the per-step size A as the coefficient, so shrinking A pays off more than anything else you can tune.

A common mix-up

"The assistant remembers what I said earlier, so my program only needs to send the new message." This is tempting because chat products behave that way. They do so because the application resends the earlier messages. A model called from code starts blank each time: if your program sends only "And the 3D printer?", the model has no idea what "and" refers to.

Check yourself

Your loop has run three steps, and a tool result of 4,000 tokens came back at step one. What happens to those 4,000 tokens on steps two and three?

Show the answer

They are resent and rebilled on every later call, unless the program clears or shortens them.

Why more context is not better 4 min

You might think the answer to cost is irrelevant if you simply buy a bigger window. Two things argue against it. First, the cost above. Second, accuracy: Anthropic's engineering team describes an "attention budget" and "context rot", meaning that as the number of tokens grows, the model's ability to recall specific information from the context decreases, so the aim is "the smallest possible set of high-signal tokens" (Effective context engineering for AI agents). A published study of this, "Lost in the Middle" (Liu et al., TACL 2024), found that accuracy on question answering over documents is highest when the relevant passage is at the start or end of the input and drops when it is in the middle, even for models built for long inputs.

So the discipline is context management: deciding what stays in the context as the loop runs. Three common moves:

  • Clear old tool results. A manual page read at step one is rarely needed at step six. The API's context editing can drop old, re-fetchable tool results and keep a record that the call happened (context windows documentation).
  • Summarize. When the history grows long, replace the oldest part with a short summary written by the model.
  • Return less to begin with. Make a tool return the 600-token section you need rather than the 3,000-token chapter. This is the cheapest of the three because the tokens never enter.
Soccer analogy: the window is the pitch. Eleven players can be coordinated; thirty cannot. A coach substitutes, and does not widen the field.

What is kept between sessions: notes 5 min

When a session ends, your program's messages list is gone unless you save it. Next week the same student arrives and the context is empty: the assistant does not know the student passed laser-cutter training. A session here means one conversation, from first message to the end. Memory across sessions is therefore not something the model has; it is information your program stores outside the context window and loads back in. Anthropic's term for the simplest form is structured note-taking: the agent writes notes to storage outside the window and reads them in again later (Anthropic). Claude's API offers a memory tool built on this idea: the model asks to read or write files in a /memories directory, and your own program carries out those operations against storage you control (Anthropic: context management).

For the makerspace, a notes file per student is enough:

def load_notes(student_id):
    try:
        return open(f"notes/{student_id}.json").read()
    except FileNotFoundError:
        return "{}"

def save_notes(student_id, notes_json):
    open(f"notes/{student_id}.json", "w").write(notes_json)

# at session start, the notes enter the context as a few tokens:
system_prompt += "\nStudent notes: " + load_notes(student_id)

The design question is what deserves saving. Save facts that are needed later, small, and not stored elsewhere: training completed and the date, the machines the student is certified on. Do not save the whole transcript (large, mostly noise), and do not save facts that a tool can look up fresh, such as the calendar, because a saved copy goes stale, the same failure you noticed in chatbots stating outdated facts with confidence.

A common mix-up

"Memory means the model learns from our conversations." The model's weights do not change when your assistant runs. Memory is text your program saves and puts back in the context. If the notes file is not loaded, the model knows nothing of it.

Check yourself

A student tells the assistant, "I finished the band-saw training today." Which design makes the assistant know this next week?

Show the answer

Write it to the student's notes and load them at the next session start. A larger window and "learning" both lose it when the session ends.

Retrieval: finding the right page 5 min

The manuals are too long to place in every context: ten manuals of 100 pages each would cost a fortune per call and would suffer the accuracy problem above. Retrieval is the answer: your program searches the manuals and puts only the few best-matching passages into the context. Anthropic calls the underlying idea just-in-time retrieval: the agent keeps lightweight references, such as file names or search handles, and loads data through tools only when it needs it (Anthropic).

The steps:

  • Prepare once, offline: split each manual into chunks, passages of a few hundred tokens, each tagged with its machine and section.
  • Search on request: the model calls search_manuals(query). Your code scores every chunk against the query, by keyword match or by comparing meaning-vectors, and returns the top k, say 3.
  • Answer: the model reads only those chunks and writes the answer, ideally citing the section.

Retrieval is a ranking problem, and you know how to evaluate rankings. Recall at k is the fraction of questions where the right chunk is among the top k; precision is the share of returned chunks that are relevant. Raising k raises recall but also adds tokens, raising cost and noise. That is a bias-variance-style tradeoff you can tune on a test set of real student questions. The critical failure: if the right chunk is ranked fifth and you return three, the model never sees it, and it will answer from the wrong chunks or from guesswork. The model cannot compensate for a page it was never shown.

A common mix-up

"The model searches the manuals itself." It does not read the manuals; it requests a search, as it requested the calendar, and your program runs it. Search quality is your design, not the model's ability.

Check yourself

The assistant answers a drill-press question wrongly. Logs show the correct section existed but was ranked seventh, and you return the top four chunks. What is the most direct fix?

Show the answer

Improve the ranking. The model cannot use a chunk it was never shown; neither a better prompt nor a larger window changes what retrieval returns.

Worked example and practice 6 min

Worked example

The fixed part (system prompt and tools) is 1,000 tokens. A request needs two tool calls, so the model is called three times. Option 1 returns whole manual chapters: each step adds 3,000 tokens. Option 2 returns retrieved chunks: each step adds 600. Compare input tokens.

  1. Calls: 2 tool calls plus the final answer = 3 model calls, so n = 3.
  2. Input per call is B + (k−1)A. Option 1: 1,000, 4,000, 7,000. Total 12,000.
  3. Option 2: 1,000, 1,600, 2,200. Total 4,800.
  4. Check with the formula: 3(1,000) + A(3) = 3,000 + 9,000 = 12,000 for Option 1; 3,000 + 1,800 = 4,800 for Option 2. The retrieval option costs 40% as much, and it is also easier for the model to find the answer in 600 tokens than in 3,000.
Your turn

Fixed part 1,500 tokens; each step adds 2,000 tokens; the request takes three model calls. Step one is given: call one has 1,500 input tokens. Compute the total input tokens. Then compute it again if the tool results are trimmed so each step adds only 500.

Show a solution

Calls: 1,500, then 3,500, then 5,500, total 10,500. Trimmed: 1,500, 2,000, 2,500, total 6,000. Check: 3(1,500) + 2,000(3) = 10,500 and 4,500 + 1,500 = 6,000. Trimming saves 43%, with no change to the answer's content.

Summary 2 min

  • The context window is all the model sees on one call; your program rebuilds it and resends it on every step, so every token in it is paid for each time.
  • The model keeps nothing between calls or sessions; "memory" is text your program saves and loads.
  • More context costs more and can reduce recall, so trim stale tool results, summarize, and return less.
  • Notes carry small, durable facts across sessions; retrieval brings in a few passages from large documents; tools fetch fast-changing facts.

Say it in your own words: without looking back, explain to a teammate why the assistant needs a notes file and a search tool rather than a bigger context window.
