The program runs the tool, then adds the result to the model's input and calls the model again. Today's question follows from that: what exactly is in that input, and what happens to it as the loop repeats?

The context window 6 min

A language model has no memory of its own between calls. Everything it can use for one call must be written into that call's input. The context is that input: the set of tokens given to the model when it generates (Anthropic, effective context engineering). A token is a chunk of text, roughly three-quarters of an English word on average. The context window is the maximum number of tokens the model can take in one call, input and output together.

Think of a soccer coach who gets a fresh, amnesiac assistant at every substitution. The coach must hand over a written briefing each time: the formation, the score, who is tired. The briefing is the context. Whatever is not on the page does not exist for the assistant.

Three things follow, and each matters for your budget and your design.

  • Limit. The window is finite. A long manual plus a long conversation may not fit.
  • Cost. Usage is billed per token. Every token you put in the context is paid for on every call that includes it.
  • Quality. More is not better. Context rot is the finding that as the number of tokens grows, the model's ability to recall information from the context decreases; Anthropic describes this as a gradient, not a cliff, and as true of all models, so context is "a finite resource with diminishing marginal returns" (same source).

The design principle that follows is to give the model the smallest set of high-signal tokens that gets the job done. Deciding what goes in is called context engineering.

A common mix-up

"A bigger window solves the problem." It is tempting because a bigger window removes the hard limit. It does not remove the cost, since you pay per token, and it does not remove context rot, since recall still degrades as the window fills. A bigger window raises the ceiling; it does not make filling it a good idea.

Check yourself

The assistant's system prompt and tool descriptions total 2,000 tokens. A student sends a 50-token question. Roughly how many of those 2,000 prompt tokens are billed for this one call?

Show the answer

All 2,000, on every call. The model keeps nothing between calls, so the program resends the prompt each time. Some providers discount repeated prefixes, but the tokens are still part of every call's input.

What is kept between steps 6 min

Inside one request, the agent loop makes several model calls. What is "kept" between them is not held by the model: the program keeps a list of messages and sends the whole list again with every call. Each step appends its tool request and the tool's result to that list. This is short-term memory: the running context of the current task.

Statistics gives the right intuition. If step k adds ak new tokens and the fixed prompt is P, the input of call n is P + a1 + ... + an-1, and the total billed input is the sum of these partial sums. Total input grows roughly with the square of the number of steps, while the new information grows only linearly. Long loops are expensive because every old token is paid for again.

Because old results are resent, agents need ways to trim the list when a task runs long. Anthropic's post names three (source):

  • Tool-result clearing: drop the bulky output of old tool calls once the agent no longer needs it. The post calls it "one of the safest lightest touch forms of compaction."
  • Compaction: summarize a conversation nearing the limit and start a new context with the summary.
  • Sub-agents: a separate agent explores with its own clean context and returns only a short summary, often 1,000 to 2,000 tokens. Whether that pays off is a later lesson.

For the makerspace assistant, a typical request has three or four steps, so you will rarely need compaction. Your better lever is keeping each tool result small.

A common mix-up

"Each step only sees the newest message." It is tempting because the loop looks like a conversation of short turns. In fact each call sees the entire list so far; that is the only reason the model can use the calendar result when it later writes the answer.

Check yourself

A tool returns a 4,000-token manual page at step 2 of a 6-step request. What does that page cost, in input tokens, over the rest of the request?

Show the answer

16,000. The page is the result of call 2's tool request, so it first appears in call 3's input. It is then resent in calls 3, 4, 5 and 6: four times 4,000.

What is kept between sessions: notes 6 min

When a session ends, the context is gone. The model does not remember a student's visit next week; if the next session needs something, the program must put it back into the context. Long-term memory is therefore information stored outside the model, in a file or database, and loaded into a later context on purpose.

The simplest design is structured note-taking (also called agentic memory): the agent writes notes to storage outside the context window, and those notes are pulled back in later. Anthropic's examples are a to-do list or a NOTES.md file (source). This workspace works the same way: your tutor starts each session by reading NOTES.md.

A memory tool is just another tool. In Anthropic's memory tool, the model asks to view, create or edit files under a /memories directory, and, as the docs put it, "Claude requests file operations, and your application runs them" (memory tool docs). That is the loop you already know: the model asks, the program acts, and where the files live, and how long they are kept, is your decision. The docs also tell your code to validate every path so a request cannot escape the memory folder.

# What the program does at the start of a session (not the model)
notes = load_notes(student_id)          # e.g. "laser: trained 2025-09-12; 3D printer: not trained"
messages = [{"role": "user", "content": notes + "\n\n" + question}]
# ...run the agent loop...
save_notes(student_id, updated_notes)   # only what is worth keeping

The design questions for your assistant are what to save, and how much. Save facts that are stable and costly to rediscover: training status, equipment the student prefers. Do not save a transcript; that just refills the context with old tokens. Do not save what a tool can look up fresh: the booking calendar changes, so a saved copy goes stale, and the tool is the source of truth.

A common mix-up

"The model remembers returning students." It is tempting because chat products feel continuous. What you experience there is a product that stores earlier text and sends it again. For your assistant, nothing persists unless your program stores it and loads it into the next context.

Check yourself

A student books the laser cutter on Monday and returns on Thursday. Which design lets the assistant know on Thursday that the student passed the safety course?

Show the answer

Store a training note and load it at the start of the next session. A big window has nothing to hold once the session has ended, and full transcripts work but cost far more than the one fact needed.

Retrieval: finding the right page 7 min

A machine manual may run to hundreds of pages. Putting it all in every context is expensive and invites context rot. Retrieval instead keeps the manual in a store outside the context and puts only the few relevant pieces into it for each question. Retrieval is memory in the same sense as notes: the information lives outside the window and is loaded when needed. Notes hold what the agent has learned; retrieval holds reference material it should look up.

The usual pipeline has these steps:

  • Chunk the manual: split it into passages of a few hundred tokens, so each can be fetched alone.
  • Index the chunks. Keyword search (BM25) scores chunks by exact word overlap with the query, weighting rare words. Embedding search turns each chunk and the query into vectors of numbers, so that texts with similar meaning lie close together, and returns the nearest chunks by a measure such as cosine similarity.
  • Search at question time, take the top few chunks and place them in the context.

The two search types fail differently. Embeddings handle paraphrase: "my cuts keep catching fire" can match a chunk about "flame suppression and air assist." Keywords handle exact strings: an error code like E-42 or a part number carries almost no semantic meaning, but matches exactly. Anthropic recommends combining both and merging the rankings, and reports that adding context to each chunk before indexing cut top-20 retrieval failures from 5.7% to 2.9% in its tests (Contextual Retrieval). Those figures come from Anthropic's own datasets, so treat them as an illustration, not a guarantee for your manuals.

The contextual retrieval trick: a chunk saying "the limit is 40 mm" is ambiguous. Prepending a short generated line such as "From the band saw manual, section on stock thickness" before indexing restores what chunking removed. It adds model cost at indexing time, once, not per question.

There are two ways to wire retrieval into an agent. In pre-retrieval, the program searches before the model runs and inserts the chunks. In just-in-time retrieval, the model gets a search_manuals tool and decides when to call it, so it can search again with a better query. Anthropic notes that runtime exploration is slower than pre-computed retrieval, and that a hybrid often works best (source). For the assistant, a search_manuals tool that returns the top three chunks, not whole pages, fits the loop you already designed.

A common mix-up

"Embedding search finds the right page whenever one exists." It is tempting because "semantic" sounds like understanding. Embeddings can miss exact identifiers such as error codes, and they always return the nearest chunks even when none is relevant, so the assistant should be able to say the manual does not cover the question.

Check yourself

A student asks: "What does the laser cutter's code ERR-17 mean?" Which search finds the right chunk most reliably?

Show the answer

Keyword search. A combined keyword and embedding search is safer in general, since students also ask in loose language.

Worked example and practice 3 min

Worked example: billed input for one request

The question: "Is the laser cutter free Friday, and do I need training?" Fixed prompt and tools: 2,000 tokens. Question: 50. Each model output (a tool request): 60 tokens. Tool results: calendar 300, manual search 3,000 (a whole page), training record 200. The model makes four calls: calendar, manual search, training record, final answer.

  1. Call 1 input: 2,000 + 50 = 2,050.
  2. Call 2 input: call 1's input, plus its 60-token output, plus the 300-token calendar result = 2,410.
  3. Call 3 input: 2,410 + 60 + 3,000 = 5,470.
  4. Call 4 input: 5,470 + 60 + 200 = 5,730.
  5. Total billed input: 2,050 + 2,410 + 5,470 + 5,730 = 15,660 tokens, although only about 3,600 tokens of new text appeared. The 3,000-token page is paid for twice.
Your turn

Redo the example with search_manuals returning only the top chunk, 1,000 tokens, not 3,000. Call 1 and call 2 are unchanged (2,050 and 2,410). Compute calls 3 and 4 and the total. What did retrieval save?

Show a solution

Call 3: 2,410 + 60 + 1,000 = 3,470. Call 4: 3,470 + 60 + 200 = 3,730. Total: 2,050 + 2,410 + 3,470 + 3,730 = 11,660 tokens. Saving: 15,660 − 11,660 = 4,000 tokens: the 2,000 tokens trimmed from the page are saved in each of the two calls that carried it. Shorter results also reduce context rot.

Summary 2 min

  • The model keeps nothing between calls: the context is everything it sees, resent and billed every call, and limited by the window and by context rot.
  • Between steps, the program keeps the message list and resends it, so total input grows roughly with the square of the steps; keep tool results small.
  • Between sessions, nothing survives unless your program saves notes and loads them again; save stable facts, and fetch changing ones with tools.
  • Retrieval is memory for reference material: chunk, index (keyword and embedding), and put only the top few chunks in context.
