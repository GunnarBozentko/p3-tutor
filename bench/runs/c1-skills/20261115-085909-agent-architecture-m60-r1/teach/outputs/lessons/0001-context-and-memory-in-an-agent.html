Context and memory in an agent: what the model sees, what is kept, what is found

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in saved notes, or in a searchable manual index, and you can estimate what that choice costs per request.

Objective O3: context and memory in an agent About 60 minutes Builds on your work on the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three are context and memory decisions. This is the lesson that gives you the vocabulary and the arithmetic to defend them at your design review.

Warm-up 3 min

Retrieve before you read. Answer from memory, then check.

Recall 1

In the agent loop, after the model asks for a tool, who actually runs the tool, and what happens to the result?

Check your answer

The program around the model runs the tool. It then puts the result into the model's next input and calls the model again. That last phrase, "the model's next input", is today's topic: what exactly goes into it, and what happens when it grows.

Recall 2

A model produces text one token at a time. What is a token, roughly, and what did the model learn its patterns from?

Check your answer

A token is a small chunk of text, often a word or part of a word. The patterns come from training on large amounts of text, which ended at some date. After that date the model knows nothing new unless the input supplies it. This is why you noticed chatbots stating outdated facts.

The context window 9 min

The context window is the maximum amount of text, counted in tokens, that the model can take in for one call: everything you send, plus the answer it writes. A token is the unit the model reads and writes, roughly three-quarters of an English word. The context is the text actually placed in that window for a given call. Think of a soccer coach's whiteboard at half-time: it has a fixed size, the coach can only reason from what is written on it, and anything not on it does not exist for the players. The model does not look anywhere else.

For a tool-using agent, the context is assembled by your program, and it usually holds five things (Anthropic, Effective context engineering):

  • the system prompt: standing instructions, such as the assistant's role and rules;
  • the tool descriptions: the names, purposes and parameters of every tool, as in your quiz 0001 work;
  • the conversation so far: the student's messages and the model's replies;
  • the tool results returned by earlier steps;
  • any retrieved or saved information that your program chose to add.

The fixed part of the context is also a cost

The system prompt and tool descriptions are sent on every call, so they are a fixed tax on every request. Suppose your assistant has six tools, each described in 150 tokens, and a 600-token system prompt. That is 1,500 tokens before the student has typed a word. A request with 4 model calls pays this tax 4 times: 6,000 tokens of input that carry no information about the question. This is why Anthropic advises tool sets that are minimal and descriptions that are clear but not bloated, and notes that overlapping tools confuse the model about which to use (Anthropic). The same trade appears in your earlier work on tool descriptions: a description must be long enough that the model picks the right tool, and no longer.

A useful habit is to keep a context budget: a table that lists each part of the context, its tokens per call, and how many calls pay for it. When someone proposes adding a paragraph to the system prompt, you can say what it costs per request, and decide whether it earns its place. Sponsors respond well to that kind of number.

Why the window matters for your budget

Two facts make the window a cost issue. First, model providers typically bill per token, counting both the input you send and the output the model writes, so a bigger context costs more on every call. Second, a bigger context is not automatically better: Anthropic describes context rot, where the model's ability to recall information from the context drops as the number of tokens grows, so the goal is the smallest set of high-signal tokens that still gets the job done (Anthropic). A window is a budget, not a storage room.

You can estimate tokens in Python before you ever call a model. A rule of thumb is four characters per token for English prose:

def rough_tokens(text: str) -> int:
    return len(text) // 4          # crude estimate, fine for budgeting

manual_page = "x" * 2400              # a 2,400-character manual page
print(rough_tokens(manual_page))      # about 600 tokens
Real counts depend on the model's tokenizer, and providers publish a counting tool. Use the rule of thumb for design-review estimates and the real counter before you trust a budget.

The third option. Fitting in the window is necessary, not sufficient. You pay for all 150,000 tokens on every call, and long contexts show context rot. Retrieval, later in this lesson, sends only the relevant pages.

What is kept between steps 10 min

Here is the idea that most changes how you think about agents: the model itself keeps nothing between calls. Each call is independent. The model has no hidden notebook; it only knows what is in the input of the call in front of it. When an agent seems to remember the previous step, it is because your program put the previous step into the new input. Statisticians would call each call memoryless, like an i.i.d. draw: the output depends only on the input you supply, not on earlier calls.

So the agent loop you already know has a precise shape. The program keeps a list, usually called messages, and every step does the same thing: append, send the whole list, append the reply.

messages = [{"role": "user", "content": question}]

while steps < MAX_STEPS:
    reply = call_model(system_prompt, tools, messages)   # the model sees ALL of messages
    messages.append(reply)                               # keep the model's request
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_name, reply.arguments)  # the program runs the tool
    messages.append(tool_result(result))                 # keep the result for the next call
    steps += 1

The variable messages is the only thing carried from step to step. If you deleted a tool result from that list, the model would behave as if the tool had never been called. (call_model and run_tool are placeholders for code you will write later; the structure is what matters.)

The cost arithmetic

Let C0 be the starting context (system prompt, tools and the question), d the tokens added by each step, and n the number of model calls. Call k sends C0 + d(k − 1) input tokens. Summing over the run gives the total input tokens billed:

T = n·C0 + d·n(n − 1)/2

The second term grows with the square of n. This is the central cost fact about agents: long runs cost disproportionately more than short ones, because each added step is re-sent on every later call. Providers can reduce the price of the re-sent prefix with caching, but the tokens still occupy the window, and checking current pricing is a task for your team.

A common mix-up

"The model remembers what happened earlier in the run." It is tempting because the assistant's answers at step 4 clearly use what happened at step 2. But the memory is your messages list, not the model. The practical consequence: whatever your program drops from that list is gone for the model, and whatever it keeps is paid for again on every call. This is also why the same belief, extended across days, is wrong: nothing is remembered between conversations unless your program saves it and puts it back (see the sessions section).

Check yourself

9,000. The five calls send 1,000 + 1,400 + 1,800 + 2,200 + 2,600 = 9,000 input tokens. Output tokens are billed too, but they are small here.

When the context gets too big 8 min

Because every step adds tokens, a long run eventually costs too much or approaches the window limit. Three techniques manage this, and all three are decisions your program makes about the messages list (Anthropic; Anthropic, context management):

  • Trimming old tool results (called context editing or tool-result clearing): once the assistant has used a manual page to answer, the raw page can be removed from the list, leaving at most a one-line note that the lookup happened. Raw results are usually the largest and least reusable part of the context.
  • Compaction: when the context nears its limit, the model is asked to summarise the conversation so far, and the summary replaces the old messages. You keep the decisions and unresolved issues and discard the verbatim history.
  • Sub-agents: a separate model call with its own fresh context does a messy sub-task, such as searching a manual, and returns only a short result. The main context never sees the mess. Whether to use this is a later lesson; here you only need to know it is a way to protect context.

All three trade information for space, so the question is always what the next step needs. For a booking, the model needs the confirmed slot and the student's name; it does not need the 600-token calendar dump that produced them. Compaction loses detail by design, so anything that must survive exactly, such as a confirmation number, belongs in notes (next section), not only in a summary.

What is kept between sessions: notes 10 min

A session is one conversation, from the student's first message to the end of the run. When it ends, your program's messages list is gone, and the model never held anything anyway. So a student who was certified on the laser cutter last Tuesday is a stranger on Friday, unless something outside the model recorded it. That something is memory in the agent sense: information your program saves outside the context window and loads back in later. The model never "stores" it; your program does.

The simplest design is notes in files or a database. Anthropic's memory tool is a worked example: the model is given a tool to create, read, update and delete files in a memory directory, and your own code carries out those operations against storage you control, so the files persist between sessions (Claude Platform Docs, memory tool). This is just the agent loop again: the "tool" is reading and writing notes. Anthropic's engineering post calls the same pattern structured note-taking: the agent writes notes outside the context window and pulls them back in later (Anthropic).

For the makerspace assistant, a note per student could be as small as this:

# students/s1234567.json  (saved by your program, outside any context)
{
  "name": "Alex",
  "trained": ["laser_cutter", "3d_printer"],
  "last_visit": "2026-11-10",
  "preferences": "prefers evening slots"
}

# At the start of a session, the program loads it into the context:
note = load_note(student_id)
system_prompt += f"Student record: {note}"

Two design choices matter. When is memory loaded? Loading the record at session start costs a few hundred tokens on every call, which is fine for a small record. A growing pile of notes should instead be read on demand through a tool, so that unrelated notes do not occupy the window. Who writes memory? If the model decides what to save, it may save wrong or sensitive details; for training status, the record should be written by your program from the authoritative source, not from what the student said in chat. Never trust a note more than the system that produced it.

Keeping notes healthy

Notes are not free of problems; they trade one risk for another. Four rules keep them useful:

  • Keep notes small and structured. A record with named fields, like the one above, can be loaded cheaply and read reliably. A long free-text diary of every chat grows without bound and brings back the cost problem you were trying to avoid.
  • Notes go stale. A student's training may expire, or a machine may be retired. Store a date with each fact, and decide what happens to old entries. A stale note is worse than no note, because the model will treat it as true.
  • Write only what a later session needs. Ask of each candidate note: will a future visit change its answer because of this? Training status, yes; the student's joke about the printer, no.
  • Treat student data as private. Notes about people are personal data. Your team should decide with the makerspace and the university what is stored, who can read it, and how a student asks for it to be deleted. This is a design-review question, not a coding detail.

The memory tool documentation makes a related security point: because your code executes the file operations, your code must validate paths, so that a request to read or write cannot escape the memory directory (Claude Platform Docs). The model proposes; your program disposes.

A common mix-up

"A larger context window gives the assistant a memory of past visits." The window only holds what you put in it for one call. It is wiped between sessions. Consumer chatbots that appear to remember you do so because the product saves notes or past chats and re-inserts them, which is exactly the design above.

Retrieval: finding the right page 10 min

Notes answer "what do we know about this student?". Retrieval answers a different question: "which small part of a very large body of text is relevant to this question?" The standard design is called retrieval-augmented generation (RAG): before or during the model call, search the documents, and put only the best few passages into the context. This matches your manuals problem: 150,000 tokens of manuals, but a question usually needs two paragraphs.

The pipeline has an indexing stage done once and a query stage done per question (Anthropic, Contextual Retrieval):

  • Chunk: split each manual into chunks, passages of a few hundred tokens, ideally cut at section boundaries.
  • Index: turn each chunk into a searchable form. An embedding is a list of numbers that represents the meaning of a text, so that texts with similar meaning have vectors that point in similar directions. BM25 is a classic keyword-scoring method that ranks chunks by how often the query's words appear in them, adjusted for how rare the words are.
  • Search: embed the question, find the chunks nearest to it (cosine similarity, the angle between vectors, which you know from statistics), and take the top k chunks.
  • Answer: put those k chunks into the context, and let the model answer from them.

Why a simple search can miss

Embeddings capture meaning but can blur exact strings; BM25 matches exact strings but ignores meaning. A question such as "What does error E-47 mean on the laser cutter?" contains an exact code that BM25 finds easily and an embedding may not. Anthropic's recommended improvement combines both, then merges the two rankings, and also prepends a short explanation of where each chunk sits in its document before indexing it, because a chunk like "it must be replaced every 40 hours" has lost what "it" refers to. In Anthropic's own tests, the share of cases where the right chunk was missing from the top 20 fell from 5.7% with embeddings alone to 2.9% with both techniques combined (Anthropic). That figure comes from Anthropic's own datasets, so treat it as a sign of direction rather than a promise for your manuals; you will need to test on your own questions.

A second design: instead of retrieving before the call, give the model a search_manuals tool and let it decide when and what to search. Anthropic calls this just-in-time retrieval; the model keeps lightweight pointers, such as file paths, and loads content only when needed. It adds calls but avoids loading text that turns out irrelevant (Anthropic). Which to pick is a later lesson on workflows versus agents.

Choosing k is a cost and quality tradeoff. A small k is cheap but risks missing the passage; a large k costs tokens on every call and invites context rot. With 400-token chunks, k = 4 adds 1,600 tokens, around 1% of the full manual.

Measuring whether retrieval works

Retrieval fails silently: if the right chunk is not retrieved, the model answers from the wrong text or from its general training, and sounds equally confident. So test it. Build a small test set of real questions, each paired with the manual section that answers it, and measure how often that section appears in the top k. This is a recall measure, familiar from statistics: of the questions that have a known right chunk, the fraction where it was found.

test_set = [
    ("How tight should the chuck key be?",   "drill_press.md#chuck"),
    ("What does error E-47 mean?",           "laser_cutter.md#errors"),
    ("Max thickness for acrylic?",           "laser_cutter.md#materials"),
]

def recall_at_k(search, test_set, k=4):
    hits = 0
    for question, right_section in test_set:
        found = [chunk.section for chunk in search(question, top_k=k)]
        hits += right_section in found
    return hits / len(test_set)

With 30 real student questions you get a number you can defend: "the right section is in the top 4 for 27 of 30 questions", which is 90%. Change one thing at a time, such as chunk size, k, or keyword plus embedding search, and rerun. This is the same discipline as comparing two models in a statistics course: one change, same data, compare. It also gives your team an honest answer when a reviewer asks "how do you know it finds the right page?".

Retrieval has typical failure modes, worth naming in a design review. Chunks cut in the wrong place split a step from its warning. Missing context in the chunk makes "replace it every 40 hours" unsearchable. Exact codes and part numbers defeat pure embeddings. Outdated manuals in the index produce confident, wrong answers: whoever owns the manuals must also own the index. For a makerspace, a wrong answer about a machine can be a safety issue, so for safety-critical instructions the assistant should quote the retrieved passage and cite the manual section, so that the student can check it.

Choosing where information lives 5 min

You now have three places to put information, and each answers a different need. Use this table as the decision rule.

PlaceLastsCostUse for
ContextOne call; one run if kept in messagesBilled on every call it is inInstructions, tool descriptions, the current request, results still needed
Notes (memory)Across sessionsStorage is cheap; tokens only when loadedPer-student facts: training status, preferences, past bookings
Retrieval indexAs long as the documentsOne-time indexing; k chunks per questionLarge, mostly-static text: machine manuals, safety rules

A question to ask for each piece of information: does it have to be seen on every call? If yes, it belongs in the context. If it is needed only sometimes, store it and load it when needed, by notes if it is about a person and by retrieval if it is about a document. The booking calendar is neither: it changes by the minute, so it must be fetched by a tool at the moment of the question, not saved.

One request, traced through all three places

A student writes, "Can I use the vinyl cutter Thursday afternoon? I'm Alex, ID 1234567." Follow where each piece of information lives:

  • Session start: the program builds the context from the system prompt and the tool descriptions (fixed), the student's question, and Alex's note, loaded from the notes store (memory). The context is now about 2,200 tokens.
  • Call 1: the model sees that Alex's note lists only the laser cutter and 3D printer as trained. It requests search_manuals for "vinyl cutter training requirement" (retrieval). The program runs it and appends 4 chunks, about 1,600 tokens.
  • Call 2: the chunks say the vinyl cutter needs a short orientation. The model requests check_calendar for Thursday (live data, never stored). The program appends the result, about 500 tokens.
  • Call 3: the model writes the answer: the slot is free, but orientation is required first. Before the next call the program may clear the raw calendar dump (trimming).
  • Session end: the context is discarded. The program saves a one-line note, "asked about vinyl cutter, orientation needed", only if the design says such notes help later visits.

Notice that every one of the three places did a job the others could not: notes knew Alex, retrieval knew the manual, and a tool knew the calendar. The context was just the place where they met for a moment.

A common mix-up

"With a big enough window, retrieval and notes are unnecessary." Size removes only the hard limit. You would still pay for every token on every call, and recall may weaken as the context fills. Nor would a bigger window make anything persist between sessions.

Worked example and practice 13 min

Worked example

A student asks: "Am I trained on the laser cutter, and what is the maximum material thickness?" The assistant uses three model calls: first it calls get_training_record (adds 300 tokens), then search_manuals returning 4 chunks (adds 1,700 tokens including the request), then it writes the final answer. The starting context (system prompt, tools, question) is 2,000 tokens. Compare this with pasting the whole 150,000-token manual into the starting context. Estimate total input tokens for both designs.

  1. Find what each call sees under retrieval. Call 1: 2,000. Call 2: 2,000 + 300 = 2,300. Call 3: 2,300 + 1,700 = 4,000.
  2. Add them. 2,000 + 2,300 + 4,000 = 8,300 input tokens. Check with the formula: n = 3, but the steps differ in size, so add directly rather than using d.
  3. Find what each call sees under pasting. The start is 152,000 tokens. Call 1: 152,000. Call 2: 152,300. Call 3: 154,000. Total 458,300.
  4. Compare. 458,300 / 8,300 is about 55. The pasted design costs about 55 times as much input per request, for the same answer, and then the student's training record still has to come from a tool because it is not in the manual.
Your turn

The assistant is asked, "Book me the 3D printer for Saturday and tell me how to change the filament." It makes 6 model calls. The starting context is 2,500 tokens, and each of the first 5 steps adds 800 tokens (the sixth call writes the final answer). Step 1 (given): call k sees 2,500 + 800(k − 1) tokens. Now (a) add up the input tokens for all 6 calls, (b) say which single change in the design would shrink this most if each tool result were cleared after use, and (c) say which fact from this request should be written to notes after the booking.

Show a solution

(a) Calls see 2,500, 3,300, 4,100, 4,900, 5,700 and 6,500. The sum is 27,000. Check with the formula: 6 × 2,500 + 800 × (6 × 5 / 2) = 15,000 + 12,000 = 27,000.

(b) Clearing each result after the model has used it. Without clearing, results that are already used are re-sent on every later call, the quadratic term. With clearing, the term shrinks toward a small constant per call. (The exact total depends on how much of each step you keep.)

(c) The booking itself: machine, date and the student's id, written by your program after the calendar tool confirms it. It is a per-student fact that a later session may need, for example to answer "what did I book?". The filament instructions are not saved; they are in the manual and can be retrieved again.

Summary 3 min

  • The model keeps nothing between calls. The context is whatever your program sends, and it is billed and read on every call.
  • Between steps, memory is the messages list. It grows each step, so total cost rises roughly with the square of the number of steps. Trim, compact or delegate to control it.
  • Between sessions, memory is notes your program saves and loads. The model does not store them, and authoritative facts should be written from authoritative sources.
  • Retrieval finds the few relevant chunks of a large document. Combining embeddings and keyword search misses less than either alone.
  • For each fact ask: must it be seen on every call? If not, store it and bring it in when needed.
