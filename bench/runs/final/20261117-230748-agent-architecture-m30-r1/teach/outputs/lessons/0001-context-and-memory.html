Context and memory in an agent: what the model sees, and what survives

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in saved notes, in the manuals it searches, or in a record it reads through a tool.

Objective O3: context and memory in an agent About 30 minutes Builds on learning record 0002, "An agent is a model called in a loop, with tools and a way to stop"
Why this matters for you

Your assistant must answer from long machine manuals and handle each student's training status between visits. Both are context and memory decisions, and every token (a small chunk of text) you keep in the context (the text the model is given in each call) costs money on every step. You will defend these decisions at your design review.

The context window 6 min

The model reads and writes tokens, small chunks of text, roughly a short word or part of a longer word. The context window is all the tokens the model can use in one call, and that includes the reply it is writing (Claude documentation on context windows). Think of the whiteboard beside a soccer pitch at halftime. The coach can use only what is written on it, and the board has a fixed size. In the makerspace assistant, 1,500 tokens of standing instructions, a 50-token question and a 3,000-token manual page together use 4,550 tokens of it.

In agent terms, the context window is working memory: it holds only this call's text. Notes and searchable stores are long-term memory, kept outside the window and brought in when needed. Window sizes vary by model, up to 1,000,000 tokens for current Claude models. A big window changes what fits, not what it costs, as the next paragraphs show.

Everything the call carries counts toward the window: the system prompt, every message so far, and the tool definitions. The system prompt is the standing instructions you write for the assistant. A tool definition is the name and description of a tool that you give the model. The model's own output counts too (same documentation page). Anthropic's engineers define context the same way: it is "the set of tokens included when sampling" (generating the model's reply) (Anthropic, effective context engineering).

A model call keeps nothing of its own from one call to the next. For the model to follow a conversation, the program sends the whole history again in each call. The documentation says the input holds "all previous conversation history plus the current user message." So each agent step is billed on everything that has accumulated, not only on what is new.

An everyday version: a friend forgets the conversation between texts, so before each reply they re-read the whole thread from the top. The friend is the model, each text they answer is one call, and the thread is the history. The re-reading is the input tokens billed, and the reply they write is the output tokens. The longer the thread, the more re-reading before every reply.

If the input alone exceeds the window, the API rejects the request with a "prompt is too long" error. A long-running agent must therefore clear or compact its history before that point.

Worked example: how tokens add up across one request

A student asks, "Book me the vinyl cutter on Friday, and what blade setting should I use?" The system prompt and tool definitions are 1,500 tokens. The question is 50 tokens. Each model output is short.

  1. Call 1 input: 1,500 + 50 = 1,550. The model outputs 60 tokens requesting search_manuals. The result is a 3,000-token manual page.
  2. Call 2 input: 1,550 + 60 + 3,000 = 4,610. The model outputs 80 tokens requesting check_calendar. The result is 200 tokens.
  3. Call 3 input: 4,610 + 80 + 200 = 4,890. The model outputs 70 tokens requesting check_training_record. The result is 100 tokens.
  4. Call 4 input: 4,890 + 70 + 100 = 5,060. The model outputs 60 tokens requesting book_slot. The result is 50 tokens.
  5. Call 5 input: 5,060 + 60 + 50 = 5,170. The model writes a 150-token final answer.

Total input across the five calls: 1,550 + 4,610 + 4,890 + 5,060 + 5,170 = 21,280 tokens. The new text in the whole run was only 5,320 tokens (the 5,170-token final context plus the 150-token answer). The input bill is about 4 times the new text in the run (21,280 / 5,320), because history is paid for again at every step.

Why this holds in general. Let S be the first call's input and xi the tokens added after call i (the model's output plus the tool result), for a run of n calls. Call j has input S + x1 + ... + xj-1. Each xi appears in every call after call i, which is n - i calls. So total input = nS + the sum over i = 1 to n-1 of (n - i) xi. Text added early therefore costs the most.

Check with the example: S = 1,550, n = 5, and x = 3,060; 280; 170; 110. Total = 7,750 + 4 x 3,060 + 3 x 280 + 2 x 170 + 110 = 7,750 + 12,240 + 840 + 340 + 110 = 21,280. The 3,000-token page alone is counted in calls 2 to 5, which is 4 times and 12,000 of the 21,280 tokens.

Prompt caching is a provider feature that stores a repeated start of the input, such as the system prompt, and bills repeats at a lower rate. It lowers the price, but the documentation states that it "changes what you pay for those tokens, not whether they count" toward the window.
A common mix-up

"A bigger context window means the assistant can simply hold everything, so I do not need to choose." It is tempting because the window sizes in model announcements are large. But the documentation warns that "more context isn't automatically better": as the token count grows, the model finds and uses information in the window less accurately, an effect called context rot. Anthropic's engineers describe an "attention budget" (the limited focus the model spreads over all tokens in the window) that every new token depletes. A large window raises the ceiling but removes neither the cost nor the loss of focus.

7,500 tokens. The prompt is part of the input to every call, so the bill is 5 x 1,500. This is why a short, precise system prompt and few tools pay off.

What is kept between steps 5 min

Within one request, the default is to keep everything. In the worked example, the 3,000-token manual page returned after call 1 stays in the history through call 5, because the program appends and resends it. That is simple and correct, but the history only grows. Two things go wrong. The cost climbs, as Figure 2 shows, and the model finds and uses the early material less reliably as the window fills.

Managing this is called context engineering: curating the set of tokens given to the model (Anthropic). The stated goal is "the smallest set of high-signal tokens" (tokens that carry information the model needs) that gets the outcome you want.

There are three standard moves, from lightest to heaviest. Each throws away something, so choose what to throw away on purpose.

  • Clear old tool results. Once a result has been used, the raw text rarely needs to be seen again. The Anthropic post calls this one of the safest, lightest-touch ways to trim context. In the example, after the model reads the 3,000-token manual page, the program can replace it with a one-line stub (a short placeholder) such as "manual page 12 read".
  • Compaction. Compaction means summarizing the conversation so far and starting a fresh context window with the summary. The post says a good summary preserves decisions, unresolved problems and key details, and drops redundant tool output.
  • Sub-agents. A sub-agent is a separate model loop with its own clean context. It does a focused task and returns only a short summary, which the post says is often 1,000 to 2,000 tokens. When splitting work across agents pays off is a later lesson.

A numeric case for clearing. Suppose that before call 4 in the worked example, the program replaces the 3,000-token page with a 20-token stub. Call 4 input becomes 5,060 - 3,000 + 20 = 2,080 tokens instead of 5,060, a saving of 2,980 tokens for that call and again for call 5. The risk is real: if the final answer needs a detail from the page, the model no longer has it. Clear only what the next steps will not need, or keep the key fact in the stub.

A common mix-up

"Summarizing is free, so compact at every step." It is tempting because the summary is shorter. But each summary is a lossy copy (a copy that loses some information): whatever it leaves out is gone from the model's view. The post advises first keeping everything that might matter, then trimming the irrelevant material. In soccer terms, a halftime recap that skips the injured defender's name is quicker to read and worse to play from.

What is kept between sessions 5 min

A session is one conversation, from the student's first message to the last. When it ends, the context window is gone: if a student says on Monday that they prefer evening slots, the assistant starts Thursday's session without knowing it. To remember it, the program must save it outside the context window and load it back at the start of the next session. Anthropic calls this structured note-taking: "the agent regularly writes notes persisted to memory outside of the context window" (Anthropic).

In soccer terms: the whiteboard is wiped after the match, but the scouting notebook stays on the coach's desk.

A minimal version in Python needs only two functions. The dictionary stands in for a database; a real assistant would write to storage that survives a restart.

NOTES_DB = {}   # student_id -> list of short notes

def load_notes(student_id):
    return NOTES_DB.get(student_id, [])

def save_note(student_id, note):
    NOTES_DB.setdefault(student_id, []).append(note)

# Start of a session: put the notes into the context.
notes = load_notes("s-1042")
system_prompt = "You are the makerspace assistant.\n" + \
                "Notes from earlier visits:\n" + "\n".join(notes)

# End of a session: save what is worth remembering.
save_note("s-1042", "Prefers evening slots; works mostly in acrylic.")

Notes cost tokens when loaded, so keep them short and useful. A good note records a preference, a project in progress or a question left open. Anthropic also describes a file-based memory tool, which lets the model itself read and write such notes outside its context (same post).

Safety rule: a note is not a permission

A note that says "trained on the laser cutter" is a copy of a fact that may have changed. The student's own claim is only what they believe. Neither may decide whether a student can use a machine. The assistant must call a tool such as check_training_record(student_id, machine) that reads the makerspace's training database at the moment of the booking. In soccer terms, a referee checks the official registration list, not the player's word or last week's lineup sheet.

  • If the tool fails or the student is not found, the answer is "not permitted yet", with a pointer to the staff member who can confirm.
  • A note may remind the assistant to run the check, but the answer comes from the record.

Retrieval: finding the right page in a long manual 5 min

Retrieval means fetching a small, relevant piece of a large store and placing only that piece in the context. It counts as memory in the sense of an external store the program searches, not a memory inside the model. Anthropic describes the basic building block as a model "enhanced with augmentations such as retrieval, tools, and memory" (Anthropic, building effective agents).

Suppose your manuals total 200 pages at about 800 tokens each, which is 160,000 tokens. Pasting them all into every call would cost 160,000 tokens of input per call, and context rot would hurt accuracy. Instead, use three steps:

  • Split the manuals into chunks, pieces of about half a page (about 400 tokens).
  • Score each chunk against the question.
  • Pass only the best few chunks to the model.

The scoring function decides quality. The simplest is keyword overlap. A stronger one uses embeddings, lists of numbers that place a text by meaning so that similar texts sit close together. Here is the keyword version:

def score(question, chunk):
    q = set(question.lower().split())
    c = set(chunk.lower().split())
    return len(q & c) / len(q)

def retrieve(question, chunks, k=2):
    ranked = sorted(chunks, key=lambda ch: score(question, ch["text"]),
                    reverse=True)
    return ranked[:k]      # only these go into the context

Numeric case: the question "laser cutter focus height" has 4 distinct words. A chunk containing 3 of them scores 3 / 4 = 0.75. A chunk containing 1 scores 0.25. The top k chunks, here k = 2, are what the model sees. At 400 tokens per chunk, that is 800 tokens instead of 160,000.

You can judge a retriever with two ratios you already know from statistics. Recall is the share of the relevant chunks that were retrieved. Precision is the share of the retrieved chunks that are relevant.

Example: a question needs 2 chunks and the retriever returns 3, of which 1 is relevant. Recall is 1/2 = 0.5 and precision is 1/3 = 0.33. Raising k tends to raise recall and lower precision. In this design, missing the chunk that holds the answer is the worse failure, because the model then answers without it.

There is a second design choice: when to retrieve. Retrieving up front means the program searches before the model starts. Just-in-time retrieval means the model gets a search tool and fetches what it needs during the loop, keeping only light references such as a page number or query.

The Anthropic post notes that searching during the loop is slower than retrieving up front, and that a hybrid is often best: fetch some data up front for speed and let the agent search for the rest. It also advises: "do the simplest thing that works." Your search_manuals tool in the worked example is the just-in-time form.

A common mix-up

"Retrieval makes the model remember the manuals." It is tempting because the answers come out right. But the model learns nothing from a retrieval. The program fetches text and puts it in the context for that call, and when it is removed, the model has no trace of it. Retrieval is a lookup, so the right page must be found again each time.

Check yourself

A question about the 3D printer needs 4 specific chunks. The retriever returns 5 chunks, and 3 of the 4 needed chunks are among them. What are recall and precision?

Show the answer

Recall 3/4 = 0.75 and precision 3/5 = 0.60. Recall asks how much of what was needed was found; precision asks how much of what was returned was useful.

Worked example and practice 5 min

Worked example: placing four facts

For the makerspace assistant, decide where each fact belongs: the context, saved notes, retrieval from the manuals, or a record read through a tool.

  1. "The booking the student just asked for." It matters only in this session, so it stays in the context. Cost: a few tokens per call.
  2. "This student likes mornings." It is small and durable across visits, and being out of date does no harm. Save it as a note and load it at the start of each session.
  3. "The cutting speed for 3 mm acrylic." It sits in a long manual and is needed only sometimes. Retrieve it with search_manuals when asked. Do not copy it into notes.
  4. "Is this student cleared for the laser cutter?" It is a safety permission. It comes from the training database through check_training_record, read at the moment of booking, never from a note or the student's word.

The test for each fact is the same: how long does it stay true, how big is it, and who is accountable for it?

Your turn: cost of a shorter run

A student asks, "Is the laser cutter free Friday, and what focus height should I use?" The system prompt and tools are 1,500 tokens and the question is 50 tokens. The run has three model calls. Call 1 outputs 60 tokens and its tool result is 200 tokens. Call 2 outputs 80 tokens and its tool result is 3,000 tokens. Call 3 writes the final answer. Step 1 is given: call 1 input is 1,550.

Find the total input tokens across the three calls. Then find how much smaller that total would be if the second tool result were 1,000 tokens instead of 3,000.

Show a solution
  1. Call 1 input = 1,550.
  2. Call 2 input = 1,550 + 60 + 200 = 1,810.
  3. Call 3 input = 1,810 + 80 + 3,000 = 4,890.
  4. Total = 1,550 + 1,810 + 4,890 = 8,250 tokens.
  5. With a 1,000-token result: call 3 input = 1,810 + 80 + 1,000 = 2,890, and the total = 1,550 + 1,810 + 2,890 = 6,250.
  6. The difference is 2,000 tokens, the same as the size difference of the result. The result enters only call 3 here, so it is paid for once. In a longer run it would be paid for at every later call.
Your turn: price the saving

Assume an illustrative price of $3 per 1,000,000 input tokens, and ignore output tokens. (a) Price the 21,280-token run from the worked example. (b) Price it again if the 3,000-token page is replaced by a 20-token stub before call 4. (c) How many dollars does the stub save over 1,000 requests? Step 1 is given: price = tokens x 3 / 1,000,000.

Show a solution
  1. (a) 21,280 x 3 / 1,000,000 = $0.0638, about 6 cents.
  2. (b) The stub saves 2,980 tokens at call 4 and again at call 5, so 21,280 - 5,960 = 15,320 tokens. That costs 15,320 x 3 / 1,000,000 = $0.0460.
  3. (c) The saving per request is 5,960 tokens, or $0.0179. Over 1,000 requests that is about $17.88, a 28% cut of the input bill (5,960 / 21,280).

The price is illustrative, not a real rate. Use your provider's current price when you budget for the design review.

Summary 2 min

  • The context window is all the tokens in one call: instructions, tool definitions, history and the reply. The program resends the history at every step, so input cost accumulates.
  • Between steps, the default is to keep everything. Clear used tool results, compact or use sub-agents when it grows, and accept that each one drops something.
  • Between sessions, nothing survives unless the program saves it. Notes hold small durable facts. A note never decides a safety permission; a record read through a tool does.
  • Retrieval puts a few relevant chunks in the context instead of the whole manual. Judge it with recall and precision, and retrieve up front, just in time, or both.
