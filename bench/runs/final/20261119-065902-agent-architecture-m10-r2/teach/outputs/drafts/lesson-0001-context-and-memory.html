Context and memory in an agent

By the end of this lesson you can say what the assistant sees at each step, what survives between steps (one model call after another in a run) and between sessions (separate conversations), and where notes and retrieval fit.

Warm-up 1 min

Recall

After a tool runs, the agent loop calls the model again. List what that next call contains, in order, starting with the instructions.

Check your answer

The instructions, then the earlier messages, then the model's tool request, then the tool result. The program resends this whole list on every call, and that repeated resending is today's topic.

The context window 1.5 min

A token is a small chunk of text, about three-quarters of an English word by a common rule of thumb (not from the sources below). The context is the set of tokens sent to the model in one call, and the context window is the maximum number of tokens one call can hold. Anthropic's engineering team defines context as the tokens included when the model generates its reply. The model sees nothing outside them.

Think of a substitute coach who walks in before every decision knowing nothing. Whatever is printed on the single sheet handed over is all the coach knows, and the sheet has limited space. The model is the coach, the sheet is the context, and the program is the assistant who prints the sheet each time.

The window is also a quality limit, not only a size limit. The same source reports that the model's accuracy at recalling details from the context gets worse as it grows, which it calls context rot. It advises treating context as a finite resource. For you the cost is concrete, because you pay for the tokens you send.

Between steps 2 min

Between steps, the model keeps nothing by itself. The program keeps a list of messages and sends it, with the instructions (the system prompt, the standing text that opens every call), on every call. Each step appends two entries, the tool request and its result.

Pseudocode:

messages = [{"role": "user", "content": question}]
while True:
    reply = call_model(system_prompt, messages)   # sends everything so far
    messages.append(reply)                        # the program remembers
    if reply.is_final: break
    result = run_tool(reply.tool_request)         # the program runs the tool
    messages.append(result)                       # and appends the result

Because the whole list is sent again, each call is larger than the last. Example: instructions and question take 2,000 tokens, and each step adds 3,000 (a request plus a manual page).

  • Input per call: 2,000, 5,000, 8,000 and 11,000 tokens.
  • Total billed: 26,000 input tokens, though the final context holds only 11,000.
  • At an illustrative $3 per million input tokens: 26,000 × $3 / 1,000,000 = $0.078, against $0.033 for 11,000 sent once.
  • General form, with base b, step s and n calls: total = n·b + s·(0 + 1 + … + (n − 1)) = n·b + s·n(n − 1)/2. Check: 4 × 2,000 + 3,000 × 6 = 26,000.
  • The n² term is why total input grows roughly with the square of the number of steps.

Fewer steps and shorter results lower the bill.

When the window nears its limit, the program can use compaction, which shrinks the list in two ways:

  • Summarize the conversation and start a new window with that summary.
  • Clear old tool results, the lightest form (Anthropic); the platform feature is called context editing, which removes stale tool results automatically.
A common mix-up

It is tempting to think the model remembers the conversation the way a person does. It does not: it is sent the transcript again each call. If the program drops a message, the model has no trace of it.

Check yourself

The program deletes the second tool result from the list. What does the model do with that result on the next call?

Show the answer

Nothing. The model sees only the list it is sent, so the result no longer exists for it.

Between sessions: notes 2 min

A session is one conversation from first message to last. When it ends, the message list is gone. Anything that must outlive it has to be written somewhere outside the window and read back later. Structured note-taking means the agent regularly writes notes to storage outside the context window and reads them in at a later turn (Anthropic). Anthropic's memory tool does this with files that the model creates, reads, updates and deletes through tool calls, in storage you control.

Analogy: the club keeps a scouting file in the office. The coach (the model) asks the assistant (the program) to fetch one page through a tool, and that page goes on the sheet. File is notes, sheet is context.

For the makerspace, a note such as "Prefers mornings; asked about laser cutter settings twice" is a good use. Notes cost tokens only when they are read in, so keep them short.

A common mix-up: notes as permission

A note saying "trained on the laser cutter" is a copy, and a copy can go stale. Permission comes from the training database, read with check_training(student, machine) at booking time. If the call fails, the answer is "not permitted yet; ask the makerspace staff".

Check yourself

A student returns after a month and asks to book the 3D printer. Where should the assistant get the student's training status?

Show the answer

The third option. A note may remind the assistant to check, but only the record, read through a tool now, decides.

Retrieval from a long manual 1.5 min

Retrieval means finding the few pieces of a large store that matter for this question and placing only those in the context. A laser cutter manual of 200 pages at about 600 tokens a page is 120,000 tokens. Sending it all every step is costly and invites context rot. Retrieving 3 pages sends about 1,800 tokens, which is 1.5% of the manual.

The 3 pages are picked in these steps:

  • Split the manual into pages.
  • Turn each page and the question into a vector, a list of numbers that encodes meaning (an embedding).
  • Score each page by cosine similarity, a number from −1 to 1 for how closely two vectors point the same way.
  • Keep the 3 highest-scoring pages and put them in the context.
scores = [cosine(q_vec, p_vec) for p_vec in page_vecs]
top3 = sorted(range(len(scores)), key=lambda i: scores[i], reverse=True)[:3]

Statistics view: this is k-nearest-neighbors with k = 3. The question is the query point, the pages are the stored points, and cosine similarity plays the role of distance (higher means closer). This is standard practice, not taken from the sources below.

Anthropic describes two styles. Pre-inference retrieval selects pages by that similarity before the model runs (inference is one run of the model); in the analogy, it is the assistant choosing 3 pages before the coach starts. Just-in-time retrieval keeps lightweight identifiers, such as file paths or stored queries, and lets the model load data with tools as it works. The source suggests the most effective agents might use a hybrid of the two, and notes that runtime exploration is slower than precomputed lookup (Anthropic).

A common mix-up

Retrieval is not a one-time saving. The retrieved pages join the list and are resent on every later call. Over 4 more calls, 1,800 × 4 = 7,200 tokens, still far below 120,000 × 4 = 480,000.

Check yourself

A student asks for the blade speed for 3 mm acrylic. The full 200-page manual is 120,000 input tokens; 3 retrieved pages are 1,800. How many tokens does retrieval save on that call?

Show the answer

120,000 − 1,800 = 118,200 tokens.

Worked example and practice 1.5 min

Worked example

A student asks, "Is the laser cutter free Friday, and do I need training?" The instructions and question take 1,000 tokens. Each step adds 2,000 tokens. The model is called 3 times. How many input tokens are sent in total?

  1. Call 1 sends the instructions and question: 1,000.
  2. Call 2 adds one step: 1,000 + 2,000 = 3,000.
  3. Call 3 sends 1,000 + 4,000 = 5,000.
  4. Total: 1,000 + 3,000 + 5,000 = 9,000 input tokens.
Your turn

Instructions and question are 1,500 tokens and each step adds 2,500 tokens. The model is called 4 times. Call 1 sends 1,500. Find the total input tokens sent.

Show a solution

Call 2: 1,500 + 2,500 = 4,000. Call 3: 1,500 + 5,000 = 6,500. Call 4: 1,500 + 7,500 = 9,000. Total: 1,500 + 4,000 + 6,500 + 9,000 = 21,000 tokens.

Summary 0.5 min

  • The model sees only the context sent in one call, and the window limits its size and quality.
  • Between steps, the program keeps and resends the messages, so total input grows roughly with the square of the steps.
  • Between sessions, only notes in storage survive; they never replace a record check for permission.
  • Retrieval puts a few relevant manual pages in context instead of the whole manual.

Say it in your own words: for one student request, what does your assistant keep in context, what does it save, and what does it retrieve?
