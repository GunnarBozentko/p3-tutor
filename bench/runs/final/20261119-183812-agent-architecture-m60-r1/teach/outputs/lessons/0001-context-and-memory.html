Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in saved notes, or behind a retrieval step (a search that fetches only the relevant text into the context), and defend the choice by counting tokens, the small units of text a model reads.

The context window 9 min

The context window is all the text a model can reference when it writes a response, including the response itself (Claude Platform docs). Example: a call holding a 1,550-token base (system prompt, tool definitions and question) and a 3,000-token manual page shows the model those 4,550 tokens and nothing else. Think of a soccer coach's whiteboard in the dressing room. The coach can only work from what is written on it, and the board has a fixed size. The model has no other view of the world during a call.

Text is measured in tokens, the small chunks of text a model reads and writes: a short word is often one token, and a long or rare word is several. As a rough rule for English, 100 tokens is about 75 words; real counts vary with the text. The window is a limit on tokens, and, as the cost section below shows, tokens are also what you pay for.

Everything in a request counts toward the window. The system prompt is the standing instructions the program puts at the top of every call. The tool definitions are the name, description and arguments of each tool, which the model reads at every call. Every message and every tool result counts as well, and so does the model's own output (Claude Platform docs).

The model does not remember; the program resends

A model call is stateless: the model keeps nothing from the previous call. What feels like memory within a conversation is the program sending the whole conversation again. The docs say each turn's input is the full history plus the new message, and the output becomes part of the input of the next turn (Claude Platform docs). Here is the loop from your agent-loop session, with that fact made visible:

messages = [{"role": "user", "content": "Is the laser cutter free Friday?"}]
while True:
    reply = call_model(system_prompt, tools, messages)  # the WHOLE list goes in, every call
    messages.append(reply)                              # the model's output joins the context
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_request)               # the program runs the tool
    messages.append(result)                             # the result joins the context too

The list messages is the context. Each pass through the loop makes it longer. Nothing is stored inside the model.

A common mix-up

It is tempting to think the model remembers the earlier steps on its own, because it answers follow-ups sensibly. It does not. Delete the first tool result from messages and the next call has no trace of it. Anything the model needs at step 5 has to be in the list sent at step 5.

Cost grows faster than the conversation

Because every call resends the history, the input tokens (the tokens sent to the model at a call, as opposed to the output tokens it writes) that you pay for add up across calls. Let the base be the system prompt, tool definitions and question, and let ak be the tokens added after call k (the model's request plus the tool result). Then call n carries

input(n) = base + a1 + ... + an-1

Numeric case:

  • Base: 1,550 tokens (system prompt, tool definitions, question).
  • check_calendar adds 460 tokens (a 60-token request and a 400-token result).
  • search_manuals adds 3,060 tokens, and check_material_stock adds 260.
  • The four calls carry 1,550, 2,010, 5,070 and 5,330 input tokens, a total of 13,960.
  • The final context is 5,330 tokens, so on average each token was paid for 13,960 / 5,330 = 2.62 times.

Why the total grows faster than the history. Addition ak first appears in call k+1 and is resent in every later call, so over N calls it is carried N − k times. Therefore total(N) = N·base + Σ (N − k)·ak, summed over k = 1 to N−1. Check with the case above: 4·1,550 + 3·460 + 2·3,060 + 1·260 = 6,200 + 1,380 + 6,120 + 260 = 13,960. If every addition equals a, the sum is a·N(N−1)/2, which is quadratic in N, while the context itself grows only linearly. An early large result is multiplied by the most remaining calls.

Providers offer prompt caching, which makes a repeated prefix cheaper to process. A cached prefix (the unchanged start of the request) still occupies the window, so caching lowers the price but not the size (Claude Platform docs).

What sits in the window, and who controls it

Four kinds of content compete for the window. You control some of them directly, and others only indirectly. Knowing which is which tells you where to look when a request is too large or too expensive.

ContentWho decides its sizeMakerspace example
System prompt and tool definitionsYou, once, at design timeRules for the assistant and the description of each tool: about 1,500 tokens
The user's messagesThe studentA one-line question, usually under 50 tokens
Tool resultsThe tool you wroteA calendar listing, or a manual page of several hundred tokens
The model's own outputThe model, within a limit you setTool requests and the final answer

The table shows why tool results are the usual cause of bloat. The system prompt is fixed and the student's message is short, but a tool can return anything. A calendar tool that returns the whole week for every machine, when the question concerns one machine on one day, adds thousands of tokens that no call needs. Designing a tool to return only what the model needs is among the cheapest savings available.

Worked example: shrinking a tool result

The calendar tool returns every booking for every machine for one week: 14 machines, about 10 bookings each, about 15 tokens per booking. A student asks about one machine on one day, and the result stays in the context for 4 model calls.

  1. Size of the full result: 14 × 10 × 15 = 2,100 tokens.
  2. Every call that follows the tool result carries it. It stays for 4 calls, so it costs 4 × 2,100 = 8,400 input tokens.
  3. Change the tool to take a machine and a date. The result is about 10 bookings for one machine, of which perhaps 3 fall on that day: 3 × 15 = 45 tokens.
  4. The new cost is 4 × 45 = 180 input tokens. The saving is 8,400 − 180 = 8,220 tokens, for a change in one function and no change to the model.

This is the link between context and the tool descriptions you will write for your team: the arguments of a tool decide how much it returns. A tool with a machine and date argument is smaller in the context than a tool with no arguments, and it is also easier for the model to use correctly.

What is kept between steps 8 min

Within one request, the default is to keep everything: every tool result stays in the list until the request ends. Example: the 3,000-token manual page in Figure 1 is resent at call 4, although the model has already used it. Keeping everything is simple and loses nothing, but it has two costs. The first is money, as Figure 1 showed. The second is quality: as the token count grows, the model's accuracy and recall degrade, a phenomenon called context rot (Anthropic Engineering).

Anthropic's engineers describe this with an attention budget: the model draws on a limited budget when it reads a large context, and each new token uses some of it. Context is therefore "a finite resource with diminishing marginal returns" (same source). A statistician's reading: every irrelevant token is noise added to the signal, and signal-to-noise falls as the window fills.

The goal is the smallest set of high-signal tokens that still produces the right answer. This practice is called context engineering: curating and maintaining the set of tokens the model sees (Anthropic Engineering). For a long task, that source names three techniques. Compaction means replacing part of the context with a shorter version, and a stub is a one-line placeholder saying a call happened.

  • Clearing tool results. Remove an old tool result that can be fetched again, and leave a stub saying the call happened. The source calls this "one of the safest lightest touch forms of compaction".
  • Compaction. Summarize the conversation when it nears the limit, then continue in a new window that starts from the summary. Detail that the summary omits is gone.
  • Sub-agents. A separate model call with its own clean window does a focused task and returns only a condensed summary, often 1,000 to 2,000 tokens, even if it used tens of thousands to explore. You will meet this properly in the lesson on several agents.

Compaction has a soccer parallel: the halftime talk. The coach does not replay 45 minutes. They give the team the three points that matter for the second half. It works if the three points are the right ones, and it fails if the key detail was dropped.

The platform documents the same ideas as features. Compaction "automatically summarizes earlier parts of the conversation on the server", and context editing can clear old tool results (Claude Platform docs). In your own program, you can do the same by editing the list before each call.

Choosing among the three techniques

The source says the choice depends on the task: compaction suits extensive back-and-forth, note-taking (the next section) suits iterative work with clear milestones, and sub-agents suit parallel research (Anthropic Engineering). Applied to your assistant, a first comparison looks like this.

TechniqueWhat it savesWhat it risksFit for the assistant
Clear a tool resultThe full size of the result, at every later callThe model cannot see the detail unless it fetches it againGood for manual pages and calendar listings
CompactionMost of a long conversationA fact the summary omits is lostRarely needed: in this lesson's examples, requests are 3 to 5 calls
Sub-agentThe exploration, not the resultExtra calls, and the summary is again lossyNot for a first design; see the later lesson on several agents

A makerspace request is short: a handful of calls, a few thousand tokens. For requests that size, the simplest effective step is to design tools that return less, and to clear a long manual page once its content has been used. Compaction becomes relevant only when a conversation runs long, such as a student who stays in one conversation for an hour asking about a project. Do the simplest thing that works, as the source advises, and measure before adding more.

What the context cannot protect you from

Trimming has a cost that is easy to overlook: it is a decision made by a program or a model about what will matter later, and it is made without knowing the future. A summary that drops the student's stated 3 pm preference will cause a wrong booking, and the cause will not be visible in the final answer. Two habits reduce this risk.

  • Summarize with explicit instructions on what must survive, such as every date, machine name and decision.
  • Keep the full text recoverable outside the context, so that a dropped detail can be fetched again.

The same idea returns in the next section: the context is a working copy, and the full record lives elsewhere.

Worked example: deciding what a summary must keep

A student spent 20 minutes with the assistant on a laser-cut enclosure project. The context holds 14,000 tokens. The program will compact it to about 600 tokens. List what the summary must keep.

  1. Facts the student gave that no tool can return: the project goal, the material (3 mm acrylic) and the deadline. If these are lost, the student must repeat them.
  2. Decisions already made: the booking for Friday at 3 pm, with its confirmation. Without it, the assistant might book again.
  3. Open questions: the student still needs to confirm the laser cutter's focus height. Without it, the assistant forgets to follow up.
  4. What may be dropped: raw manual pages and calendar listings. Each can be fetched again by calling a tool, and the facts used from them are already in steps 1 to 3.
  5. What must not be kept as a fact: "student is trained". The record is checked again whenever a permission is needed.

The summary is 600 tokens, down from 14,000, so each later call carries 13,400 fewer tokens.

A common mix-up

A larger window does not remove the need for these choices. It is tempting to buy a bigger window and keep everything, since a model with a million-token window can hold a whole shelf of manuals. But you pay for every token at every call, and recall degrades as the window fills. The window sets the maximum, not a target.

What is kept between sessions 10 min

A session is one conversation or request, from the first message to the end. When it ends, the context list is thrown away, and the next session starts from an empty list. The model has no hidden storage that carries over. Anything the assistant should know on Thursday about a visit on Monday must be saved outside the model and put back into the context.

An everyday version: a student has a desk, a pocket notebook and a library. The desk is the context window: only what lies on it can be used now, and it is cleared at the end of the day, which is the end of a session. The notebook is the saved notes: short, carried everywhere, and possibly out of date. The library is the manuals and records: the source of truth, fetched when needed. A notebook line "Priya is trained" is a copy that can disagree with the registrar's record, so the registrar decides.

The simplest form is notes as memory: the agent writes short notes to storage outside the context window and reads them back later (Anthropic Engineering). The source gives examples such as a to-do list and a NOTES.md file. Claude's file-based memory tool works the same way: Claude stores what it learns in files under a /memories folder, and the tool "operates client-side", meaning Claude requests file operations and your application runs them (Claude Platform docs).

This is the same tool pattern as your agent loop. A memory tool is an ordinary tool: view, create and so on are requests from the model, and your code decides where the files live, such as a folder per student or rows in a database. The persistence is entirely your application's storage.

# Monday's session ends: the program saves a short note, keyed by student
notes["priya"] = "Asked about laser cutter settings. Prefers afternoon slots."

# Thursday's session starts: the note is put back into the context
messages = [{"role": "user",
             "content": "Saved notes: " + notes.get("priya", "none") +
                        "\nStudent says: Book me the laser cutter Friday at 3 pm."}]

Notice the cost. This one-line note is about 20 tokens at every call of the new session. A longer note of 120 tokens, about 90 words, costs six times as much, so a note should be short and high-signal. A note that grows without limit is just a slower way to fill the window. Good notes are few, dated and specific, and old ones are pruned (deleted).

What deserves a note

Three questions decide whether a fact should be saved between sessions:

  • Will it matter at a later visit?
  • Can the assistant get it again from a tool?
  • Would it be harmful if it were out of date?

A good note matters later, cannot be fetched again and is safe if stale. The table sorts the makerspace facts with these questions.

FactMatters later?Fetchable?Harmful if stale?Decision
Priya prefers afternoon slotsYesNoNoSave as a note
Priya's laser cutter training statusYesYes, from the recordYes: a safety riskDo not save; read the record each time
The laser cutter's manualYesYes, by retrievalYes, if the manual is revisedDo not save; retrieve
Priya's open booking on FridayYesYes, from the calendarYes: it may be cancelledDo not save; read the calendar
Priya is building an enclosure projectYesNoNoSave as a note

Only two of the five facts become notes. The rest have an owner, either the training database, the manuals or the booking system, and the assistant should ask the owner. The subsection on stale notes, further below, applies this rule to a safety case: a note should hold what only the student can tell you, and not a copy of something another system keeps.

The memory tool in more detail

The memory tool gives the model a small set of file commands: view to list or read, create to write a file, str_replace and insert to edit, delete and rename (Claude Platform docs). Two practical points follow from the fact that your code runs them.

  • Your handler maps the /memories path to real storage, so you can give each student a separate folder.
  • Your handler (the code that carries out the model's file requests) must validate every path, so that a request such as /memories/../../secrets.env cannot escape the folder (same source).

A memory the model can write is a place where text of unknown quality can enter the context at the next session, so treat its contents as data to read, not as instructions to obey.

You do not have to use the memory tool to get the same behavior. The two-line code sample above, a dictionary keyed by student that the program reads at the start and writes at the end, is already memory. The tool differs in that the model decides what to write and when, which suits open-ended notes. For a fixed set of facts, such as "preferred time", a program that fills in a field is simpler and cheaper than letting the model manage files.

Worked example: the cost of a note

A note of 120 tokens is loaded at the start of every session, and the assistant makes an average of 4 calls per session. Notes grow by 40 tokens per visit if nothing is pruned. What does a student's note cost after 10 visits, over one session?

  1. Note size after 10 visits: 120 + 10 × 40 = 520 tokens.
  2. The note is in the context for every call of the session, so it is carried 4 times: 4 × 520 = 2,080 input tokens.
  3. Compare with a pruned note held at 120 tokens: 4 × 120 = 480 input tokens.
  4. The unpruned note costs 1,600 more input tokens per session than the pruned one, and the gap keeps widening each visit.

Notes can go stale, so they never decide a risky permission

Your assistant must remember each student's training status. A saved note is a copy of that status, and a copy goes out of date: the student may have been trained since, or may have had their access suspended.

For anything with real-world risk, such as running a laser cutter, the decision rests on the authoritative record, the training database kept by whoever is responsible. The program reads it through a tool at the moment of the decision, as check_training_record(student_id, machine). The student's own claim, and a note that says "trained", never decide it.

If the record cannot be read, because the tool fails or the student is not found, the safe answer is "not permitted yet", with a pointer to the staff member who can confirm. Memory still has a role here: a note may remind the assistant which record to check, or that the student asked about the laser cutter last week. The answer itself comes from the record.

A common mix-up

It is tempting to save "Priya: laser cutter training complete" as a note, since it saves a tool call at every visit. The note is only a copy. If the record changes, the note says "trained" while the record says otherwise, and the assistant books someone onto a machine they may not be allowed to use. Save the pointer, not the permission.

Retrieval: finding the right page 9 min

Retrieval means finding the few pieces of stored text that are relevant to the current question and placing only those in the context. It is the answer to a long manual. If a machine manual is 120 pages at about 600 tokens per page, it is 72,000 tokens. Putting it all in the context would carry 72,000 tokens at every call of the loop. Retrieving the three relevant pages carries 1,800.

Think of the analyst's scouting report in soccer. The coach does not read the full 120-page file on the league; they read the three pages on tomorrow's opponent. Retrieval does the same for the model.

The standard method has three steps.

  • Split the manual into chunks, pieces of a size a model can use, such as a page or a section.
  • Index each chunk, which means placing it in a lookup structure built in advance so that a search does not read every chunk.
  • At question time, score every chunk against the question and return the top few.

An embedding is one scoring method: a list of numbers that represents the meaning of a text, so that texts with similar meaning get similar lists. Closeness is usually measured by cosine similarity, the cosine of the angle between two lists, which you know from statistics as a normalized dot product. Plain keyword matching is the older alternative and is often good enough for part numbers and error codes.

import numpy as np

def top_k(question_vec, chunk_vecs, k=3, min_score=0.3):
    norms = np.linalg.norm(chunk_vecs, axis=1) * np.linalg.norm(question_vec)
    sims = chunk_vecs @ question_vec / norms         # cosine similarity per chunk
    order = np.argsort(sims)[::-1][:k]               # the k most similar chunks
    return [i for i in order if sims[i] >= min_score]  # empty list: not in the manuals

The last line is the minimum-score safeguard from the subsection on searches that find nothing, further below.

Two ways to run the search

Anthropic's engineers distinguish two designs (Anthropic Engineering).

  • Up-front retrieval. The program searches before the model is called and puts the top chunks in the first message. It is fast and predictable, with one search per question. It fails when the question was vague or needs a second look.
  • Just-in-time retrieval. The model gets a search tool and decides when to call it, with which words, and whether to search again. It can refine, but "runtime exploration is slower than retrieving pre-computed data", and without good guidance on its tools the agent can waste context (same source).

The source describes a hybrid strategy that mixes both, and its advice is "do the simplest thing that works". For your assistant, a fixed up-front search over the manuals for the machine named in the question, plus a search tool for follow-ups, is a reasonable first design to defend.

Measuring whether retrieval works

You can judge a retriever with two familiar numbers. Precision is the share of retrieved chunks that are relevant. Recall is the share of all relevant chunks that were retrieved. These are the standard definitions.

Numeric case: a question about acrylic settings.

  • Relevant pages in the manual: 2. Pages returned: 3, of which 2 are relevant.
  • Precision = 2/3, about 0.67. Recall = 2/2 = 1.0.
  • The wrong page costs 600 tokens of noise.
  • Returning only 1 relevant page would give precision 1.0 but recall 0.5, so the answer would miss half the settings.

This is the same trade-off you know from classification. Retrieving more chunks raises recall, and it lowers precision while adding tokens to every later call.

Chunk size is a design choice

How you split the manual changes what retrieval can find. Small chunks, such as a paragraph of 150 tokens, make a match precise and cheap, but a procedure that spans several paragraphs is cut into pieces, and a retrieved piece may lack the warning in the paragraph before it. Large chunks, such as a 1,200-token section, keep a procedure whole, but each retrieved chunk brings more irrelevant text. The usual starting point is a section or a page, with chunk boundaries at headings, because a manual's headings already mark where a topic starts and stops.

Numeric case. A question needs one 150-token paragraph.

  • 150-token chunks, top 3: 450 tokens, of which 150 are useful. The useful share is 150/450, about 33%.
  • 1,200-token chunks, top 3: 3,600 tokens, of which the same 150 are useful. The useful share is 150/3,600, about 4%.
  • Over 4 calls, the large chunks cost 14,400 input tokens against 1,800.

Chunks also need labels. A chunk that reads "Set the speed to 40%" is useless without knowing which machine and which material it concerns. Many designs store the machine name, the manual title and the section heading as metadata (data about a chunk, not its text) with each chunk, and restrict the search to the machine named in the question. That one restriction often raises precision more than a better scoring method does.

When the search finds nothing

A retriever always returns its top few chunks, even when none is relevant, because it ranks and does not judge. If the student asks about a machine the makerspace does not have, the search still returns the three closest pages, and the model may build a confident answer on the wrong ones.

Two safeguards are cheap. Set a minimum similarity score below which the result is treated as "nothing found", and tell the model in the system prompt to say so, and to point to makerspace staff, when the pages do not answer the question. Both come back to the first recall question: a model writes plausible text whether or not the text is supported, so the design must give it a way to say "not in the manuals".

Worked example: choosing the design for the manuals

The assistant answers from 6 machine manuals of 120 pages each, at about 600 tokens per page. A typical request involves 4 model calls. Compare three designs by the input tokens that the manual content adds to a request.

  1. Everything in context. 6 × 120 × 600 = 432,000 tokens, carried by 4 calls: 1,728,000 input tokens. This is impractical, and it invites context rot.
  2. One manual in context. The program picks the machine named in the question: 120 × 600 = 72,000 tokens, carried by 4 calls: 288,000 input tokens. It still carries 70,000 tokens that the question does not need.
  3. Retrieve the top 3 pages. 3 × 600 = 1,800 tokens. If they arrive at call 2 and stay for 3 calls, the cost is 3 × 1,800 = 5,400 input tokens.
  4. Compare. Retrieval costs 5,400 tokens against 288,000 for one manual in context, about 1.9% of it. Its risk is the one from the precision and recall section: the right page may not be in the top 3.

The numbers do not settle the design alone. A design review needs both the cost and the quality argument: retrieval is far cheaper, so the team must then show on test questions that recall is high enough. A reasonable test is to write 20 real student questions, mark the relevant pages by hand, and compute precision and recall for the search.

A common mix-up

It is tempting to think retrieval means the model looks things up in its own memory of training. It does not. Retrieval is a program step that fetches text from your own store and puts it in the context. Because the model reads that text at the call, it can answer from a manual it never saw in training, and you can update the manual without retraining anything.

Worked example and practice 7 min

Worked example

General rule: each call carries the base, the loaded note and every earlier addition, and a risky permission is decided by the record, never by the note. Applied to Priya: she returns on Thursday and writes, "Book me the laser cutter Friday at 3 pm." Design what is in the context at each call, and count the input tokens. Assume the base (system prompt and tool definitions) is 1,500 tokens, her saved note has grown to 120 tokens after several visits, and her message is 40 tokens.

  1. Load the note. The program looks up Priya's note and puts it in the first message. Call 1 carries 1,500 + 120 + 40 = 1,660 tokens. Reason: the context starts empty each session, so the note must be put back.
  2. Read the record, not the note. The model requests check_training_record. Request 60 tokens, result 80 tokens. Call 2 carries 1,660 + 60 + 80 = 1,800. Reason: booking a laser cutter is a risky permission, so the record decides.
  3. Check the calendar. Request 60, result 300. Call 3 carries 1,800 + 60 + 300 = 2,160.
  4. Book it. Request 60, result 70. Call 4 carries 2,160 + 60 + 70 = 2,290. This call writes the final answer, since nothing further is needed.
  5. Total. 1,660 + 1,800 + 2,160 + 2,290 = 7,910 input tokens for the request.
  6. Save a note. After the session, the program saves one line: "Prefers afternoon slots." It does not save "trained" or the booking. Reason: a note holds only what Priya can tell you, while the booking stays in the calendar and the next permission check goes to the record again.

  • Part C: Name one thing that could go wrong with the summary.
Show a solution

Part A: call 3 = 2,620 + 60 + 80 = 2,760. Call 4 = 2,760 + 60 + 300 = 3,120. Call 5 = 3,120 + 60 + 70 = 3,250. Total = 1,660 + 2,620 + 2,760 + 3,120 + 3,250 = 13,410 tokens.

Part B: the summary removes 800 tokens from each of calls 3, 4 and 5. Call 3 = 1,960, call 4 = 2,320, call 5 = 2,450. Total = 1,660 + 2,620 + 1,960 + 2,320 + 2,450 = 11,010 tokens, which saves 2,400.

Part C: any setting left out of the 100-token summary is gone from the context, so the final answer could omit or misstate it. Mitigation: the program can keep the full page recoverable by calling the search tool again, or write the settings the answer needs into the summary first.

Practice: does the order of tool calls matter? 4 min

Your turn

Sam asks, "Is the 3D printer free tomorrow morning, and what temperature for PETG?" The base, note and message total 1,630 tokens at call 1. Each tool request adds 60 tokens. check_calendar returns 200 tokens and search_manuals returns 1,200 tokens. The final answer is written at call 3.

  • Part A: the model calls the calendar first, then the manual search. Compute the input tokens of calls 1, 2 and 3, and the total.
  • Part B: the model calls the manual search first, then the calendar. Recompute.
  • Part C: explain why the totals differ.
Show a solution

Part A: call 1 = 1,630. Call 2 = 1,630 + 60 + 200 = 1,890. Call 3 = 1,890 + 60 + 1,200 = 3,150. Total = 6,670.

Part B: call 2 = 1,630 + 60 + 1,200 = 2,890. Call 3 = 2,890 + 60 + 200 = 3,150. Total = 7,670.

Part C: the 1,200-token result is carried by two calls in Part B instead of one, which adds 1,200. The 200-token result is carried by none instead of one, which removes 200. The net difference is 1,000. The same information costs more when a large result arrives early. The final call is identical in both.

Design review rehearsal 7 min

Your design review will ask you to justify where each kind of information lives. Rehearse with a new case before you look at the answers. A different assistant is described below, and you decide for each item whether it belongs in the context for the current call, in saved notes, or behind a tool or retrieval step.

Your turn

The assistant has just received this message from a student named Sam: "Can I use the 3D printer to print a bracket from PETG? I'd like a morning slot like last time." Place each item in one of three places: the context at this call, a saved note, or a tool or retrieval step. Give a one-line reason for each.

  • Item 1: Sam's message itself.
  • Item 2: Sam's preference for morning slots, observed on earlier visits.
  • Item 3: The printer's temperature settings for PETG.
  • Item 4: Whether Sam has completed the 3D printer training.
  • Item 5: Whether the printer is free tomorrow at 9 am.
  • Item 6: The rules the assistant follows, and the descriptions of its tools.
Show a solution

Item 1: context. It is the current input, so it is in the list at every call. Item 2: saved note, loaded into the context at the start of the session. Only Sam can tell the assistant this, and a stale preference is harmless.

Item 3: retrieval. The settings are in the manual, which is too long to carry, and the manual may be revised. The top pages enter the context for the calls that need them.

Item 4: a tool reading the training record, at the moment of booking. It is a permission with real-world risk, so a note, a claim, or the model's judgment cannot decide it. If the lookup fails, the answer is "not permitted yet", with a pointer to staff.

Item 5: a tool reading the calendar. It changes constantly, so a saved copy would be stale. Item 6: context, as the system prompt and tool definitions at every call; this is the fixed base, so keep it short and precise because every call pays for it.

Notice the pattern in the solution. Only items 1, 2 and 6 are text the assistant carries. Items 3, 4 and 5 are things the assistant goes and gets. When your team asks "why not just put everything in the prompt?", the answer has three parts: cost grows with every call, recall degrades as the window fills, and stale copies can cause a wrong action.

Check yourself

A teammate proposes saving the whole manual for each machine as a note, so that the assistant "remembers" it. What is the strongest objection?

Show the answer

A manual stored as a note still has to be put in the context to be used, so it costs tokens at every call. Retrieval puts in only the pages that are needed.

Summary 3 min

  • The context window holds everything the model sees in one call: instructions, tool definitions, messages and tool results. The model keeps nothing between calls; the program resends the list each time.
  • Each call carries all earlier steps, so cost grows faster than the conversation, and accuracy falls as the window fills.
  • Between steps, keep what is needed, clear re-fetchable results, and summarize when the window is crowded.
  • Between sessions, save short notes outside the model and put them back. A note never decides a risky permission; the record, read through a tool, does.
  • Retrieval puts only the top chunks of a long manual in the context. Check it with precision and recall.

Say it in your own words: without looking, explain to a teammate where each of these lives in your assistant: the student's question, the laser cutter's manual, the student's training status, and the note that Priya likes afternoons. Say which ones sit in the context, and when.

Show a model answer

The student's question: in the context, in the first message, at every call. The laser cutter manual: in storage, retrieved as the top 3 pages, and in the context only for the calls after retrieval. The training status: in the training record, read through a tool at the moment of booking, and never saved as a note. Priya's afternoon preference: in saved notes, loaded into the first message of each session at about 20 tokens.
