The context window 2 min

A language model has no memory of its own between calls. On every call it reads only the text you send it, and that text is the context. The context window is the limit on how much text, counted in tokens (small chunks of text), the model can read and write in one call. Anthropic's documentation says everything in the request counts toward it: the system prompt (the fixed instructions sent on every call), every message, every tool result, the tool definitions, and the model's own reply.

A larger window does not remove the problem. The same documentation notes that accuracy and recall (how reliably the model uses a fact that is in its text) degrade as the token count grows, an effect called context rot. Anthropic's engineering team therefore treats context as a finite resource with diminishing marginal returns.

Think of a soccer coach who has only the halftime talk to brief the team. The talk is the context window, and the coach cannot say more than fits in the break. A rambling talk buries the two instructions that matter, which is context rot.

Statistics view: treat the manual page that answers the question as signal and the rest of the loaded text as noise. Loading a 60,000-token manual to use one 1,500-token page makes 1,500 / 60,000 = 2.5% of the text relevant; retrieving that page makes it 100%. Accuracy falling as noise grows resembles an estimate degrading when irrelevant observations enter a sample.

Between steps and between sessions 2 min

Between steps of one loop, the program keeps a list of messages and sends all of it again each call. Tool results stay in that list, so unless you trim or summarize it, the context only grows (previous turns are preserved completely). Between sessions, nothing carries over unless your program saves it: a new conversation starts with an empty list. A session is one conversation, from the student opening the assistant to closing it.

Example: on Monday a student says she prefers evening slots. On Tuesday the program starts a new call with an empty message list, so the assistant cannot know this unless the program saved it on Monday.

In numbers: if the first call reads T0 tokens and each step adds r tokens, call i reads T0 + (i - 1)r. So n calls read n·T0 + r·n(n - 1)/2 tokens in total, which grows with the square of n. With T0 = 3,000 and r = 1,500, four calls read 3,000 + 4,500 + 6,000 + 7,500 = 21,000 tokens.

Retrieval and notes 2 min

Retrieval means fetching only the needed piece of a large source into the context, instead of loading everything. Anthropic describes agents that keep lightweight identifiers such as file paths and load data at runtime with tools. For a manual, a suggested design has four steps:

  • Split the manual into pages and give each page an identifier.
  • Give the model a search_manuals(query) tool that returns the best two or three pages.
  • Rank pages by keyword match, or by embedding similarity: each page becomes a list of numbers, and the pages whose numbers lie closest to the query's are returned.
  • Let the model request a neighbouring page by its identifier, because retrieval can miss the right page.

Notes are the other half: the agent writes notes outside the context window, which are pulled back in at later times. Notes can be a to-do list within a long task, or a per-student file across visits.

A safety rule

A note is a copy, and copies go stale. Analogy: a sticky note on the fridge says "milk in stock". It tells you where to look, but you open the fridge before you plan breakfast. Likewise, if a student's note says "trained on the laser cutter", the assistant must still call a check_training(student, machine) tool on the training database before booking. The note may say which record to check; it never decides. If the lookup fails, answer "not permitted yet" and point to the staff who can confirm.

Worked example and practice 2 min

Worked example: cost of loading the whole manual

Setup: instructions and tools use 3,000 tokens. One manual is 60,000 tokens; one page is 1,500. Loading everything answers in one call. Retrieval needs two calls: search, then answer. Ignore the model's replies and price discounts.

  1. Load everything: one call reads 3,000 + 60,000 = 63,000 tokens.
  2. Retrieve one page: call 1 reads 3,000; call 2 reads 3,000 + 1,500 = 4,500; total 7,500.
  3. Ratio: 63,000 / 7,500 = 8.4, so loading everything costs about 8 times more here.
  4. Each extra step on the same question resends the whole manual. Three calls cost 3 × 63,000 = 189,000 tokens, against 3,000 + 4,500 + 4,500 = 12,000 with retrieval.
Your turn

Same setup, but the model needs two pages of 1,500 tokens, each retrieved in its own step, then answers (three calls). Step 1 is given: call 1 reads 3,000 tokens. Find the total.

Show a solution

Call 2 reads 3,000 + 1,500 = 4,500. Call 3 reads 3,000 + 1,500 + 1,500 = 6,000. Total: 3,000 + 4,500 + 6,000 = 13,500 tokens. Loading the whole manual would answer in one call at 63,000 tokens, so retrieval is still 63,000 / 13,500, about 4.7 times cheaper.

Here is a minimal long-term note store in Python, loaded at session start:

import json, pathlib

def load_notes(student_id):
    p = pathlib.Path(f"notes/{student_id}.json")
    return json.loads(p.read_text()) if p.exists() else {}

notes = load_notes("s123")
system_prompt = "You help at the makerspace.\nStudent notes: " + json.dumps(notes)

def save_note(student_id, key, value):
    p = pathlib.Path(f"notes/{student_id}.json")
    data = json.loads(p.read_text()) if p.exists() else {}
    data[key] = value   # a hint only; verify permissions with check_training
    p.write_text(json.dumps(data))

Summary 1 min

  • The model keeps nothing; the program resends the context every call.
  • Within a loop the context grows with each tool result, and long contexts cost more and recall worse.
  • Across sessions, only what your program saves and reloads survives.
  • Retrieval loads the needed page; notes carry facts forward; permissions come from a record checked by a tool.
