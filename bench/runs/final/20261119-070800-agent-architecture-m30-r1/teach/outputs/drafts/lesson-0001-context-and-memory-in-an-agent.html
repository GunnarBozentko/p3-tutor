Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context (the text sent to the model on each call), in saved notes (short facts the program stores between visits), or in a searchable manual (a document store the assistant searches for the right passage).

Objective O3: context and memory in an agent About 30 minutes
Why this matters for you

Your assistant must answer from long machine manuals and remember each student between visits, all on a small budget. Every one of those choices is a context and memory choice, and your design review will ask you to defend them.

Check your answer

The program must include the step 1 request and its result, because the model keeps nothing between calls. Today's lesson builds on this: what exactly goes into each call, what it costs, and what survives when the session (one student visit, from the first message to the end of the chat) ends.

The context window 4 min

When a student asks the makerspace assistant, "Which blade do I use for acrylic?", the program sends the model one block of text: the standing instructions, the conversation so far, and the descriptions of the available tools. The model can use only that block. The block is the context, the set of tokens given to the model on one call (Anthropic, context engineering). A token is a small piece of text, often a short word or part of a word. The context window is the maximum number of tokens the model can handle in one call, counting its own answer too (Anthropic docs).

Everything in a request counts toward that limit: the system prompt (the standing instructions sent with every call), every message so far, and your tool definitions (the written descriptions of each tool). The model has no other view of the world. If a fact is not in the context and was not learned in training, the model cannot use it. This is the floor you already established: the model works from training plus the text it is given.

Think of a soccer coach at halftime with a whiteboard of fixed size. The game plan written at the top is the system prompt. The notes on what each player has done so far are the messages. The scouting slips pinned on are the tool results. The final instruction to the team must also fit on the board, so it is the answer. When the board is full, something old is erased before anything new goes on.

Tokens also set the price. Providers charge per token, usually separately for input tokens (what you send) and output tokens (what the model writes), and the Anthropic pricing is quoted per million tokens (Anthropic pricing). So the context is both a size limit and a cost driver.

A common mix-up

It is tempting to think the model "remembers" the conversation, as a person does. It does not. The model keeps nothing between calls. A chat feels continuous only because the program sends the whole earlier conversation again with each new message. The docs describe each turn's input as all previous conversation history plus the current message (Anthropic docs).

What is kept between steps 5 min

Inside one request, the agent loop runs several model calls. What is kept from one step to the next? Everything the program chooses to resend. In the simplest design, that is all of it: the system prompt, the tool definitions, the question, each tool request the model wrote and each tool result that came back. The context grows at every step, because each step appends its request and its result.

The consequence is about cost. Because every call resends the whole context, the input you pay for is the sum of the context sizes of all calls, not the final size. The example below shows it.

Worked example: one request, three calls

A student asks: "Is the bandsaw free on Saturday morning, and which blade do I use for acrylic?" The system prompt and tool definitions take 2,000 tokens and the question 100. Each tool request the model writes takes 150 tokens, and the final answer 200. The tool results are: calendar 300 tokens, manual search 1,500 tokens.

  1. Call 1 input: 2,000 + 100 = 2,100 tokens. The model requests the calendar tool (150 output).
  2. Call 2 input: 2,100 + 150 + 300 = 2,550. It requests the manual search (150 output).
  3. Call 3 input: 2,550 + 150 + 1,500 = 4,200. It writes the final answer (200 output).
  4. Total input = 2,100 + 2,550 + 4,200 = 8,850 tokens. Total output = 150 + 150 + 200 = 500 tokens. The final context is only 4,400 tokens, yet you paid for 8,850 input tokens.
  5. At made-up round prices of $1 per million input tokens and $5 per million output tokens, the request costs 8,850 × $1/106 + 500 × $5/106 = $0.00885 + $0.0025, about 1.1 cents. Replace these prices with your chosen model's rates from the pricing page before you quote a budget.

Now the pattern behind it. Let S be the fixed part (system prompt, tool definitions and question) and d the average tokens each step adds (one request plus one result). Call k then has an input of about S + (k−1)·d, and n calls total about n·S + d·n(n−1)/2. The derivation: call k has input S + (k−1)·d, so the total is the sum over k = 1 to n, which is n·S + d·(0 + 1 + … + (n−1)) = n·S + d·n(n−1)/2. The first term grows linearly with n, and the second grows with the square of n.

Check it on the example. S = 2,100, and the context grew from 2,100 to 4,200 over 2 steps, so d = 1,050. For n = 3: 3·2,100 + 1,050·3 = 6,300 + 3,150 = 9,450, within 7% of the exact 8,850 because the steps were uneven.

For the trend, take a lighter d = 700. Ten calls give 10·2,100 + 700·45 = 52,500 input tokens. Twenty calls give 20·2,100 + 700·190 = 175,000. Doubling the steps made the input about 3.3 times larger. This is why a step limit and short tool results matter for your budget.

Prompt caching lets a provider charge less for a repeated prefix (the unchanged opening part) of the context. It changes what you pay, not what the window holds, so cached tokens still occupy the window (Anthropic docs). Because the repeated prefix is the system prompt, tool definitions and earlier steps, caching can cut the resend cost described here. Check the pricing page for the cached-read rate before you finalize a budget.

When the context gets too full 3 min

Suppose a booking chat has run twenty calendar lookups, and every raw listing is still in the context and resent at each call. Two limits apply. The hard limit is the window: past it, the call fails or the answer stops early (Anthropic docs). The soft limit is quality: Anthropic's engineers call the effect context rot, meaning that as the number of tokens grows, the model's ability to recall information from the context decreases, gradually rather than at a cliff (Anthropic, context engineering). The goal is the smallest set of high-signal tokens (tokens that carry information the job needs) that gets the job done.

Three tools manage a full context, each from the same source:

  • Compaction: summarize a conversation that nears the limit, then start a new context window with that summary.
  • Tool-result clearing: once a tool result is deep in the history, remove the raw output. The post calls this one of the safest, lightest forms of compaction.
  • Sub-agents: a helper agent does a focused task in its own clean context and returns only a short summary, often 1,000 to 2,000 tokens.

Compaction works like replacing a dataset of 10,000 rows with its mean and variance. The summary is small and answers the questions you planned for, but a question that needs a raw row can no longer be answered. The conversation is the dataset, the summary is the summary statistic, and the lost exact detail is the information the statistic does not capture.

A common mix-up

It is tempting to think that a bigger window removes the problem: if everything fits, include everything. Fitting is not the same as working well. A bigger window still costs you input tokens at every call, as the worked example showed, and recall can still degrade as the context fills. Size limits what is possible; curation decides what is good.

Check yourself

In a long booking chat, an old raw calendar listing of 800 tokens is no longer needed; its conclusion, "free Saturday at 9 am", is already noted. Which action fits best?

Show the answer

The second option. Clearing a stale tool result is the lightest form of compaction and saves its tokens at every later call.

What is kept between sessions: notes 5 min

A student books the laser cutter on Monday and returns on Wednesday. The model keeps nothing between calls, so it sees nothing of Monday unless the program supplies it. A session is one visit by a student, from the first message to the end of the chat, and its context is gone when it ends. Memory between sessions is therefore something the program builds, not something the model has. The standard pattern is structured note-taking: the agent writes short notes to storage outside the context window, and the notes are pulled back into context later. Your program will do the pulling at the start of each session (Anthropic, context engineering).

Notes cost few tokens, unlike resending a whole old conversation.

In soccer terms, the context is the match itself, and the notes are the scouting file the coach reads before the next match. The file does not remember the match; it holds what someone chose to write down.

A minimal version in Python needs no model call at all. The program loads the notes and adds them to the system prompt:

import json, pathlib

def load_notes(student_id):
    path = pathlib.Path(f"notes/{student_id}.json")
    return json.loads(path.read_text()) if path.exists() else []

def save_note(student_id, text):
    pathlib.Path("notes").mkdir(exist_ok=True)
    notes = load_notes(student_id)
    notes.append(text)
    pathlib.Path(f"notes/{student_id}.json").write_text(json.dumps(notes))

BASE_PROMPT = "You are the makerspace assistant."

def start_session(student_id):
    notes = "\n".join(load_notes(student_id))
    return BASE_PROMPT + "\nNotes on this student:\n" + notes

Who calls save_note? Two designs are common:

  • Model-driven: give the model a tool save_note(text) and let it decide what to keep. The Anthropic post describes agents writing their own notes in this spirit. It is more adaptive.
  • Program-driven: at session end, make one extra model call that asks for three short notes from the conversation, and save them. It is easier to predict, which helps with a budget.

Which notes are worth saving? Preferences ("works mostly on the laser cutter"), unfinished business ("asked about a 3D-printer booking, no slot found"), and pointers (notes that name which record or manual section to check). Notes grow, so they need care too: keep them short, drop the stale ones, and do not save what a tool can fetch again.

A safety rule for notes

Your assistant must not rely on a remembered training status between visits. A note is a copy, and a copy goes stale.

  • A note saying "trained on the laser cutter" must not decide a booking. Neither may the student's own statement.
  • The decision comes from the training database kept by the makerspace, read through a tool at the moment of booking.
  • If the tool fails or the student is not found, the answer is "not permitted yet", with a pointer to staff who can confirm.
  • A note may only remind the assistant which record to check.
def may_book(student_id, machine):
    result = check_training_record(student_id, machine)   # tool call to the real record
    if result is None:               # tool failed or student not found
        return "Not permitted yet. Please ask makerspace staff to confirm."
    return "Permitted." if result["trained"] else "Not permitted yet. Training is required."

Retrieval: finding the right page 5 min

The manuals are too long to put in every call. A machine manual might run 120 pages at about 500 tokens a page, which is 60,000 tokens. Sent with each of three calls, that is 180,000 input tokens for one request, which at $1 per million tokens is 18 cents. That is about 20 times the 0.9 cents of input cost in the earlier worked example. It also invites context rot.

Compare cooking from a 120-page cookbook. You do not read the whole book before dinner; you look up the dish in the index and read only that page. The index lookup is the similarity ranking, the recipe page is the retrieved chunk, and the counter space for one open book is the context window.

Retrieval fixes this: the assistant finds the few relevant passages and puts only those in the context. The idea was formalized as retrieval-augmented generation, which pairs the model with a searchable store of documents (Lewis et al., NeurIPS 2020).

A common way to search uses embeddings. An embedding is a list of numbers, a vector, that represents the meaning of a piece of text, so that texts with similar meaning get vectors pointing in similar directions. The steps are:

  • Split each manual into chunks, short passages of a few hundred tokens each, so that a chunk is small enough to be useful.
  • Compute an embedding for each chunk once, and store them.
  • At question time, embed the question and rank chunks by similarity.
  • Put the top few chunks into the context.

The usual similarity is cosine similarity: the cosine of the angle between two vectors, which is the dot product divided by the product of their lengths. It is 1 for the same direction, 0 for perpendicular and −1 for opposite. For a statistician: if both vectors are mean-centered, cosine similarity equals the Pearson correlation coefficient, so ranking chunks by cosine is ranking them by correlation with the question.

Worked example with toy vectors

Real embeddings have hundreds of numbers. Here they have two, with invented axes. The question is q = (3, 4), with length 5. Chunk A is (5, 12), length 13. Chunk B is (12, 5), length 13. Chunk C is (4, −3), length 5.

  • A: dot = 3·5 + 4·12 = 63, so cosine = 63 / (5·13) = 0.97.
  • B: dot = 3·12 + 4·5 = 56, so cosine = 56 / 65 = 0.86.
  • C: dot = 3·4 + 4·(−3) = 0, so cosine = 0.

The same ranking in Python:

import numpy as np
q = np.array([3, 4])
chunks = {"A": np.array([5, 12]), "B": np.array([12, 5]), "C": np.array([4, -3])}
def cosine(u, v):
    return u @ v / (np.linalg.norm(u) * np.linalg.norm(v))
ranked = sorted(chunks, key=lambda k: cosine(q, chunks[k]), reverse=True)
print(ranked)   # ['A', 'B', 'C']

Chunk A ranks first and C is unrelated. With top-1 retrieval (keeping only the single highest-ranked chunk), only chunk A (say 400 tokens) enters the context, which is 150 times less than the whole 60,000-token manual.

When should retrieval run? Two patterns exist. Up-front retrieval fetches chunks before the model is called. Just-in-time retrieval gives the model a tool, such as search_manuals(query), and lets it decide when to search and what to ask. Anthropic notes that up-front retrieval is faster, runtime exploration is slower but lets the agent discover context step by step, and a hybrid of the two can work best (Anthropic, context engineering).

Its advice is to "do the simplest thing that works". A search tool that the assistant calls inside its loop is the second pattern, just-in-time retrieval.

A common mix-up

It is tempting to think retrieval means the model "looks things up" in its own memory. It does not. Retrieval is ordinary program code that returns text, and the text only helps once it is in the context. If the search returns the wrong chunk, the model answers from the wrong chunk, so the quality of chunking and ranking decides the quality of the answer.

Worked example: placing four items

For each item, ask three questions: does it change between sessions, is it large, and is permission or accuracy at stake?

  1. "Student prefers mornings." Small, personal, changes slowly: save as a note, load at session start.
  2. The 120-page bandsaw manual. Large, shared by all students: keep in a retrieval store and fetch chunks on demand.
  3. Tomorrow's calendar for the laser cutter. Changes within minutes: never store it; fetch it with a tool in the current session and let it leave the context when stale.
  4. Whether the student is trained on the bandsaw. Permission matters: read it from the training record by tool at the moment of booking. A note may only say "check training record."

Start with call 3's input, which is 2,550 + 150 + 6,000. Find the total input over four calls.

Show a solution

Call 3 input = 8,700. Call 4 input = 8,700 + 150 + 100 = 8,950. Calls 1 and 2 are unchanged at 2,100 and 2,550. Total = 2,100 + 2,550 + 8,700 + 8,950 = 22,300 input tokens. A single large result is resent in every later call, which is why returning only the right chunk keeps the cost under control.

Summary 2 min

  • The model keeps nothing between calls. The context is what the program sends each time, within a fixed window, and it also sets the cost.
  • Within a request, the context grows each step and is resent, so total input cost grows faster than the number of steps: 10 calls cost 52,500 input tokens and 20 calls cost 175,000 (with S = 2,100 and d = 700), which is 3.3 times more. Trim stale tool results.
  • Between sessions, only what the program saves survives: short notes read back at session start. A note never decides a permission; the record read by tool does.
  • For long manuals, retrieval fetches only relevant chunks into the context, cutting cost and distraction.
