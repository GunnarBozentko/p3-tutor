Context and memory in an agent

By the end of this lesson you can decide, for any piece of information in the makerspace assistant, whether it lives in the context window, in saved notes, in a record read through a tool, or in a searchable manual.

Objective O3: the context window, what is kept between steps and sessions, retrieval and notes as memory About 30 minutes Builds on your session on the agent loop
Why this matters for you

Your assistant must answer from long machine manuals, remember each student's visits, and stay within a small model budget. Every one of those three demands is a context and memory decision, and you will defend these decisions at your design review.

Check your answer

A 40-page manual is about 16,000 tokens (40 × 400). Now the first question: your program runs the tool. The model only writes a request for it. Each step is a separate model call, and that is the fact this lesson builds on. A language model knows only what it learned in training plus the text it is given, so the question for today is what text each call is given.

The context window and what it costs 5 min

A token is the unit of text a model reads and writes: often a short word or a piece of a longer one. The context window is everything the model is given in one call, measured in tokens: instructions, tool descriptions, the conversation so far and tool results. Anything outside that window does not exist for the model on that call. Example: for the question "Is the laser cutter free Friday?", call 1 receives 2,500 tokens of instructions and tool descriptions plus the 50-token question, 2,550 tokens in all, and nothing else.

Soccer maps onto the idea:

  • The pitch is the context window: only the players on it can touch the ball, and the number is fixed.
  • The bench and the club archive are information outside the window.
  • A substitution is retrieval: a needed player comes on from the bench.
  • Taking a finished player off is clearing a tool result.
  • The coach's notebook, kept after the final whistle, is memory between sessions.
  • Limit of the map: a pitch is capped by player count, a window by tokens.

Two limits apply. The first is the hard limit: the window has a maximum size. Window sizes differ by model; this lesson assumes about 200,000 tokens, so check the figure for your model. As a size guide, 200,000 tokens is about 500 pages of material (Anthropic, Contextual Retrieval). Dividing, that is roughly 400 tokens a page, the figure this lesson uses. The second limit is softer. Anthropic reports context rot, where the model's ability to recall information accurately falls as the window grows, as a gradient and not a hard cliff (Anthropic, Effective context engineering for AI agents).

The stated reason is attention, the step in which the model weighs how relevant each token is to every other token; that gives n² pairs for n tokens. At n = 1,000 that is 1,000,000 pairs; at n = 10,000 it is 100,000,000, a hundred times more for ten times the text.

The third consequence is cost. Because each step is a separate call, each call sends the whole context again. Suppose a request to the assistant runs like this:

Worked example: tokens billed across one request

Instructions and tool descriptions take 2,500 tokens. The student's question takes 50. Each tool call the model writes takes about 50 tokens.

  • Call 1 reads 2,500 + 50 = 2,550 tokens. The model asks for the calendar.
  • Call 2 adds the 50-token request and a 400-token calendar result: 2,550 + 450 = 3,000 tokens. The model asks for the manual page.
  • Call 3 adds 50 and a 1,500-token manual excerpt: 3,000 + 1,550 = 4,550 tokens. The model asks to book.
  • Call 4 adds 50 and a 300-token booking result: 4,550 + 350 = 4,900 tokens. The model writes the final answer.

The final context holds 4,900 tokens, but the input processed across the four calls is 2,550 + 3,000 + 4,550 + 4,900 = 15,000 tokens, about three times as much. Every call re-reads everything added before it, so the total is a sum of growing terms and rises faster than the number of calls.

Worked example: what that costs on a budget

Assume a placeholder price of $3 per million input tokens; check your provider's real price, which will differ.

  • One request: 15,000 × 3 / 1,000,000 = $0.045.
  • 1,000 requests: 1,000 × $0.045 = $45.
  • Halving the tokens per request saves $22.50 per 1,000 requests.

The price is an assumption; the lesson is that cost scales with the summed context, which you control.

Prompt caching means the provider stores an unchanged start of the context, so repeat reads are faster and cheaper; the source cites latency cut by more than 2x and cost by up to 90% (Anthropic, Contextual Retrieval). It lowers the price of repeats; it does not shrink the context.
Check yourself

A request needs 5 model calls. The context is 3,000 tokens at call 1 and grows by 1,000 tokens at each later call. How many input tokens are processed in total?

Show the answer

25,000 tokens. Proof of the shortcut: write the sum S = 3,000 + 4,000 + 5,000 + 6,000 + 7,000 and again in reverse. Each column adds to 10,000 and there are 5 columns, so 2S = 50,000 and S = 25,000. In general, for k calls, start c and growth g per call, S = k·c + g·k(k−1)/2. Total cost therefore grows with k², the same quadratic shape as the attention pairs.

What is kept between steps 4 min

The model keeps nothing between calls. Your program keeps the conversation as a list of messages and sends the whole list on every call. The model appears to remember step 1 at step 4 only because step 1 is in the list again. This is why you decide what is in the list: the model sees nothing else.

Everyday version: an assistant who forgets everything after each phone call and must reread the whole email thread before each reply. The thread is the message list. Rereading it before every reply is resending the list on every call. A longer thread means more to reread, so more tokens billed per call.

messages = [{"role": "user", "content": "Is the laser cutter free Friday?"}]
while True:
    reply = call_model(instructions, tools, messages)   # one separate model call
    messages.append({"role": "assistant", "content": reply.text})
    if not reply.tool_request:
        break                                           # final answer: stop
    result = run_tool(reply.tool_request)               # your program runs the tool
    messages.append({"role": "tool", "content": result})

The code is a simplified sketch with invented function names, not a real library. Notice that messages only grows. Dropping, shortening or replacing items in that list is how you control context; the model cannot do it for you.

Worked trace: the message list for the laser-cutter question
  • Start: 1 message, the question.
  • After call 1: the calendar request and the calendar result are added, so 3 messages.
  • After call 2: the manual request and the manual excerpt are added, so 5 messages.
  • After call 3: the booking request and the booking result are added, so 7 messages.
  • Call 4 receives all 7 and writes the final answer, so the list ends at 8 messages.

Each call receives the full list. That is why the token total in the previous section is a sum and not a single number.

Check yourself

Each loop pass adds 2 messages, and call 1 received 1 message. How many messages does call 5 receive?

Show the answer

9 messages: the calls receive 1, 3, 5, 7 and 9.

A common mix-up

The model holds no running memory of the conversation, although a chat feels continuous. If you called it with only the last tool result, it would answer as if the question had never been asked. The continuity lives in the list your program resends.

Check yourself

Show the answer

The third option. The call is all the model has, so a call that lacks the question gives an answer that ignores it.

When the window fills up 3 min

Long manuals and long conversations push the context toward its limit, and context rot makes it worse before the limit is reached. Anthropic's guidance is to find the smallest set of high-signal tokens that makes the desired outcome likely (Anthropic, Effective context engineering). Three tools follow from that guidance:

  • Clearing tool results: the lightest form. Once the assistant has used a 1,500-token manual excerpt, delete it from the list and keep the one-line conclusion.
  • Compaction: summarize a conversation that is nearing the limit and start a new window with the summary. Claude Code (Anthropic's coding assistant) keeps decisions and unresolved problems and drops redundant tool output.
  • Notes outside the window: defined in the next section.
Worked examples: clearing and compaction
  • Clearing. After call 3 of the earlier request, replace the 1,500-token manual excerpt with a 40-token conclusion such as "Laser cutter: acrylic, 40% speed." Call 4 then reads 4,900 − 1,500 + 40 = 3,440 tokens, which is 1,460 fewer.
  • Compaction. A 40-message chat of 20,000 tokens is summarized into 1,500 tokens. That frees 18,500 tokens, a reduction of about 13 times (20,000 / 1,500 ≈ 13.3). The cost is that anything the summary leaves out is gone.
Check yourself

A 6,000-token tool result is replaced by a 100-token conclusion. How many tokens does each later call save?

Show the answer

5,900 tokens per later call: 6,000 − 100.

Compaction is lossy: a summary can drop a detail that turns out to matter. Anthropic advises tuning it for recall first, meaning keep everything relevant (recall, as in classification, is the share of relevant items kept), and only then remove what is superfluous.

Check yourself

A booking chat has run for 40 messages. Early messages hold a long calendar listing the assistant no longer needs. Which fix is lightest?

Show the answer

Clear the old listing. Compaction is the next step up if clearing is not enough.

Between sessions: notes and records 5 min

When a session (one continuous conversation with its own context window) ends, the window is gone, so a new session starts empty, even for a student who visited yesterday. Example: on Monday a student says she prefers morning slots; on Friday the assistant knows nothing of it unless the program saved a note. To remember across sessions, the program must write something to storage outside the window and read it back at the start of the next one.

Anthropic calls one form structured note-taking: the agent regularly writes notes to memory outside the context window and reads them back later (Anthropic, Effective context engineering). Their example is an agent playing a game that keeps tallies and maps, then reads its own notes after each context reset.

Anthropic's memory tool packages this as a folder of memory files that the model reads and edits through tool calls. The tool is client-side, meaning it runs in your program and not at the provider: the model requests a file operation and your application runs it (Anthropic, Memory tool). You choose the storage, such as a folder or database rows per student. You also carry the security duty: a path such as /memories/../../secrets.env can escape the folder, so your handler (the function that carries out each memory request) must validate every path.

def handle_memory(path, student_id):
    if path != "/memories" and not path.startswith("/memories/"):
        return "Error: path must be inside /memories"
    root = (STORE / student_id).resolve()               # one private folder per student
    target = (root / path.removeprefix("/memories").lstrip("/")).resolve()
    if not target.is_relative_to(root):                 # blocks "../" tricks
        return "Error: path is outside the memory folder"
    ...                                                 # then view, create, edit the file
A risky mix-up

A note saying "trained on the laser cutter" must not decide a booking on the next visit. A note is a copy. It can be wrong when written, or stale when the training lapses. For anything with real-world risk, such as running a laser cutter, the decision rests on the training database, an authoritative record (the one source officially responsible for that fact) read through a tool at that moment. A student's own claim, a saved note or the model's guess never decides it.

Everyday version: a fridge note reading "electricity bill paid" versus the bank statement. The note is the saved note; the statement is the training database. Deciding whether to pay again is deciding whether to book, and checking the statement is calling check_training. The note can be wrong or out of date, so the statement decides.

def check_training(student_id, machine):
    record = training_db.lookup(student_id, machine)    # the authoritative record
    if record is None:
        return "not permitted yet: ask makerspace staff to confirm"
    return "permitted" if record.is_current else "not permitted yet: training expired"

If the lookup fails or the student is not found, the safe answer is "not permitted yet" plus a pointer to staff. Notes still have a role: a note such as "this student is working toward the laser cutter" can remind the assistant to run check_training. It points to the record and never replaces it. Good uses of notes are preferences ("books mornings") and progress ("finished the first part of the project"). For training status between visits, you do not store it; you read it from the record each visit.

Check yourself

The notes file says "prefers afternoon slots." The training database says the student's welding certificate expired last month. The student asks to book the welder for tomorrow afternoon. What should the assistant do?

Show the answer

Decline and point to staff. The record settles the permission; the note only shapes which slot to offer once booking is allowed.

Retrieval: finding the right page 5 min

Retrieval means fetching only the relevant pieces of a large body of text into the context instead of loading all of it. Example: for "fault code E-4417 on the vinyl cutter", the assistant pulls the 4 manual pieces that mention the code, not all 480 pages. The standard method has these steps (Anthropic, Contextual Retrieval):

  • Split the manuals into chunks, pieces a few hundred tokens long, and index them (store them in a searchable form) so each can be found on its own.
  • Convert each chunk to an embedding, a list of numbers that places chunks of similar meaning near each other, and rank chunks by closeness to the question.
  • Embeddings can miss exact matches, so also rank with BM25, a keyword-ranking method that favors chunks sharing the question's rarer words. It is strong for unique identifiers such as "Error code TS-999".
  • Merge the two rankings and send the top chunks to the model.
Worked example: merging two result lists

For "fault code E-4417", embeddings return chunks A, B, C. BM25 returns D, A, E, and D is the page that contains the code. The merged candidate set is A, B, C, D, E, so the exact-match page D is no longer missed.

def merge(embedding_hits, bm25_hits):
    merged = []
    for chunk in embedding_hits + bm25_hits:   # A, B, C, then D, A, E
        if chunk not in merged:
            merged.append(chunk)
    return merged                               # A, B, C, D, E

Production systems usually combine the two rankings with rank fusion; this union shows the idea.

A common mix-up

The model has not read your manuals. Without retrieval it writes a plausible answer from training, which is how a chatbot states an outdated fact with confidence.

Two further points from that source apply to your manuals. First, a chunk can lose its context. "The company's revenue grew by 3% over the previous quarter" does not say which company or period, and "Set the speed to 40%" does not say which machine.

The fix is to prepend a short description of where the chunk comes from before indexing it: "Set the speed to 40%" becomes "Laser cutter manual, cutting acrylic: Set the speed to 40%." Anthropic reports that this cut the top-20 retrieval failure rate (the share of questions for which none of the 20 top-ranked chunks holds the answer) from 5.7% to 3.7%, or to 2.9% when combined with contextual BM25.

Read the rates as counts. Out of 1,000 questions, plain retrieval misses the right chunk in the top 20 for 57 of them (5.7%). With added context it misses 37, and with BM25 as well it misses 29. The relative reductions are (5.7 − 3.7) / 5.7 ≈ 35% and (5.7 − 2.9) / 5.7 ≈ 49%.

Second, retrieval is not always needed. Anthropic notes that a knowledge base under about 200,000 tokens, roughly 500 pages, can go straight into the prompt (the text sent in one call, the same thing as the context), with caching to make that cheaper. Compare that with the cost lesson above.

There is also just-in-time retrieval. The agent keeps lightweight identifiers, such as file names, and loads content with tools when it needs it. Anthropic describes names and folder structure as signals for relevance. The trade-off is speed: exploring at run time is slower than reading precomputed results, and a poorly guided agent can waste context chasing dead ends (Anthropic, Effective context engineering). Anthropic's advice is to do the simplest thing that works.

Retrieval can also serve as memory. Past conversation summaries or per-student notes can be indexed and searched the same way as manuals. Use notes when the content is small and read whole, such as a preference list. Use retrieval when the store is large and only a part is needed per question, such as a year of project logs.

Worked example: notes or retrieval?
  • A preference list is 6 lines, about 60 tokens. Read it whole at the start of each session.
  • A year of project logs is 300 entries of 150 tokens each, 45,000 tokens. Loading it on each of 4 calls costs 180,000 tokens.
  • Retrieving the 3 best-matching entries (450 tokens) per call costs 1,800 tokens across 4 calls, 100 times less.
  • Decision: notes for the first, retrieval for the second.

Worked example and practice 4 min

For each piece of information, ask these questions in order:

  1. Is it needed on every call?
  2. Must it survive the end of the session?
  3. Is it a large collection of which only a small part is needed per question?
Worked example: placing information in the makerspace assistant

The assistant serves 12 machines with 40 manual pages each. Place each item.

  1. Instructions and tool descriptions. Needed on every call, so they sit at the start of the context. They are about 2,500 tokens and benefit from caching.
  2. The 480 manual pages. At about 400 tokens a page that is 192,000 tokens. Sending it on every call would cost 192,000 tokens per call; across four calls, 768,000. Retrieving 4 chunks of 400 tokens gives 1,600 per call, about 120 times less. Use retrieval.
    • Loading whole is just under the 200,000-token rule of thumb, but the manuals plus instructions would use about 194,500 of an assumed 200,000-token window, re-read on every call.
    • Retrieved text across four calls is 4 × 1,600 = 6,400 tokens, against 768,000.
    • With a small budget, retrieval wins even allowing for caching. Loading whole with caching is a fair alternative only if the manuals were a quarter of this size.
  3. A student's training status. It decides a risky action, so it comes from the training database through a tool at booking time. It is never saved as a note.
  4. "This student prefers morning slots." A harmless preference that must survive between sessions. Save it as a note, per student.
  5. Today's calendar lookup. Needed for this request only. Keep it in context while in use, then clear it.

Summary 2 min

  • The context window is all the model sees in one call. Your program rebuilds it every step by resending the message list, so every call pays again for everything in it.
  • Cost: tokens billed equal the sum of every call's whole context, so clearing, compaction and retrieval each lower the bill.
  • A long window is costly and degrades recall, so keep the smallest set of useful tokens: clear finished tool results and compact when needed.
  • Memory between sessions is storage outside the window: notes for preferences and progress, which your program writes and reads back.
  • Anything that grants a risky permission comes from the authoritative record, read through a tool at that moment, never from a note or a claim.
  • Retrieval can also serve as memory: small stores are read whole as notes, large stores are searched.
  • For long manuals use retrieval: chunks with their context, keyword and embedding search together, and whole-manual prompts only when the text is small.
