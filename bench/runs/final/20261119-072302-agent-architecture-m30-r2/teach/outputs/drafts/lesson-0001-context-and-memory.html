Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in saved notes, or in a searchable manual.

Objective O3: the context window, what is kept between steps and sessions, retrieval and notes as memory About 30 minutes
Why this matters for you

Your assistant must answer from long machine manuals, remember each student between visits, and stay inside a small model budget. All three problems are decided by what the model sees at each step. This lesson gives you the tools to decide that, and to defend the decision at your design review.

Warm-up 2 min

Recall

From memory: what does a language model take in and produce? And in the agent loop, who runs a tool, the model or the program around it?

Check your answer

The model takes in text and produces text, one token at a time. A token is a small chunk of text, often a short word or part of a word. The program around the model runs each tool; the model only writes a request for it. Today's question follows from this: if the model only ever sees text, what exactly is in that text at each step?

The context window 4 min

A language model has no access to anything except the text it is handed on each call. The context window is that text: everything the model can reference when it writes a response, including the response itself. Anthropic's documentation calls it a "working memory" and distinguishes it from the training data the model learned from (Claude context windows). It is measured in tokens, and every model has a maximum size. A token is a small chunk of text, often a short word or part of a word, and it is the unit in which limits and prices are counted.

Think of a soccer match at halftime. The coach is the model, and the coach's years of experience are its training, fixed during the match. The whiteboard is the context window, and the coach can act only on what is written on it. The assistant coach is the program: before every play it copies the plan onto a fresh board, and anything it leaves off, the coach never sees. If the board is full, something must be erased before anything new goes on.

What sits on the board in an agent? Four things, and all of them count toward the limit:

  • the system prompt, which is the standing instructions you write for the assistant;
  • the tool definitions, meaning each tool's name, description and parameters;
  • every message so far: the student's questions, the model's replies, and every tool result;
  • the model's own output, which becomes input for the next call.

The documentation confirms all four count toward the window. Prompt caching means the provider stores a repeated start of the prompt and bills it at a lower rate. Cached prefixes still occupy the window; caching changes what you pay, not whether they count.

Window sizes depend on the model. The documentation gives 200,000 tokens for some models and 1,000,000 for others. The exact numbers change as models change, so check the current page when you pick a model. For this lesson, the size matters less than a second fact: you pay for the tokens you send, so everything on the board costs money.

A common mix-up

It is tempting to believe the model "remembers" a student from the last message the way a person does. It does not. The model keeps nothing between calls. The program resends the whole conversation each time, and the documentation says each turn's input "contains all previous conversation history plus the current user message." If the program leaves something out, the model has no way to know it ever happened.

What is kept between steps 5 min

In the agent loop from your earlier lesson, each step is a separate model call. What connects the steps is a list the program keeps, usually called the message history. After each tool runs, the program appends the model's request and the tool's result to that list and sends the whole list again. So the context grows at every step, and nothing is ever removed unless you decide to remove it.

history = [{"role": "user", "content": question}]
while True:
    reply = call_model(system_prompt, tools, history)  # whole list sent every call
    history.append(reply)
    if reply.is_final:
        break
    history.append(run_tool(reply.tool_request))       # list grows each step

Here call_model and run_tool are placeholders for your own functions. The comment on the call line is the point: the whole list goes in every time.

This has a cost consequence. Input tokens, the tokens sent to the model in a call, are billed on every call; output tokens are the ones it writes back. So an early message is paid for again on every later call. The model's per-step work looks small, but the bill grows faster than the number of steps.

Here is the arithmetic for one makerspace request, with assumed round numbers. The system prompt plus tool definitions take 1,500 tokens and the student's question takes 50. Each model request for a tool takes 60 tokens. The calendar result is 300 tokens, a manual excerpt 2,000 and a training-record result 100.

  • Call 1 input: 1,500 + 50 = 1,550 tokens.
  • Call 2 input: 1,550 + 60 (request) + 300 (calendar) = 1,910 tokens.
  • Call 3 input: 1,910 + 60 + 2,000 (manual excerpt) = 3,970 tokens.
  • Call 4 input: 3,970 + 60 + 100 (training record) = 4,130 tokens.

The total input billed is 1,550 + 1,910 + 3,970 + 4,130 = 11,560 tokens. If the history were not resent, four calls on the question alone would cost 4 × 1,550 = 6,200. The extra 5,360 tokens pay for the model seeing its own earlier steps. That is the price of continuity, and the 2,000-token manual excerpt is billed on call 3 and again on call 4.

Turn that into money with an assumed price of $3 per million input tokens. The input cost of this request is 11,560 × 3 / 1,000,000 = $0.035, about 3.5 cents. Output tokens are billed separately, at their own rate, and are not counted here; caching would lower the repeated part. At 1,000 requests the input cost is about $34.68. Divide your sponsor's budget by the full per-request cost to get how many requests you can serve.

Why the bill grows faster than the number of steps: let the first call have input I, and let every later step add the same a tokens. Call k then has I + (k−1)a input tokens, so n calls cost nI + a·n(n−1)/2. The first term is linear in n and the second is quadratic.

Check with I = 1,000, a = 500, n = 4: the formula gives 4,000 + 500 × 6 = 7,000, and the direct sum 1,000 + 1,500 + 2,000 + 2,500 also gives 7,000. A result of size a that enters after call j is resent on calls j+1 to n, so it costs a(n−j) in total. The earlier it enters, the more it costs.

Prompt caching can make repeated prefixes cheaper per token. It does not make them smaller: they still fill the window. The documentation states this directly.

Three times. The result enters the history after call 2, then calls 3, 4 and 5 each resend it. That is 9,000 input tokens for one 3,000-token result.

When the context gets too full 3 min

In the request above, call 4 carries 4,130 input tokens, and 2,000 of them are a manual excerpt the model has already used. Two limits apply to a history that grows like this. The hard limit is the window size: if the input alone exceeds it, the API returns an error. The soft limit is quality. The documentation states that "as token count grows, accuracy and recall degrade, a phenomenon known as context rot," so curating what is in context matters as much as the space available. Here recall means how reliably the model uses a fact that is present in its context; it is not the statistical rate (Claude context windows).

Anthropic's engineering team describes context as a finite resource with diminishing returns, and says each new token uses up part of the model's "attention budget," its limited capacity to weigh every token against every other token. Their guiding rule is to find the smallest set of high-signal tokens that gives the behavior you want (Effective context engineering for AI agents). A related research result is that models use information at the start and end of a long input better than information in the middle (Liu et al., Lost in the Middle).

So a long agent run needs housekeeping. Two techniques, both from the sources above, are the ones to know:

  • Tool result clearing: after the model has used a bulky tool result, the program removes it from the history. This is the lightest fix.
  • Compaction: when the history nears the limit, the model summarizes it and the conversation continues from the summary. Anthropic's advice is to tune the summary for recall first, so it keeps what matters, and only then trim.

Apply tool result clearing to the earlier example. Suppose the program clears the 2,000-token manual excerpt after call 3, once the model has used it. Call 4 then has 4,130 − 2,000 = 2,130 input tokens, and the total becomes 1,550 + 1,910 + 3,970 + 2,130 = 9,560. That saves 2,000 tokens, about 17% of the 11,560 total, on one request.

Compaction is like replacing a dataset with summary statistics. A 40,000-token history becomes a 2,000-token summary, so every later call carries 38,000 fewer tokens. The risk is the one a mean carries: an outlier, such as one student's allergy note, is lost and cannot be recomputed from the summary.

A common mix-up

"The window holds a whole textbook, so we can load the manuals and stop worrying." It is tempting because the limit is large. Two things go wrong. You pay for those tokens on every call, and recall gets worse as the context fills. A large window raises the ceiling; it does not remove the need to choose what goes in.

Check yourself

The first option is right. Clearing used tool results removes dead weight and keeps the rest. Wiping loses decisions; a bigger window costs more and leaves the clutter.

What is kept between sessions: notes 4 min

A session is one conversation, from the first message to the last. When it ends, the message history is gone unless the program saved it. The model itself changed nothing: training is not how an assistant learns that a student visited yesterday. So anything that must survive a session needs a store outside the context window, which the program writes to and reads from.

The simplest store is notes. Anthropic calls this structured note-taking, or agentic memory: the agent writes notes outside the context window and pulls them back in later. Their examples include Claude Code's to-do lists, an agent that maintains a notes file, and a Claude playing Pokémon that kept tallies and maps and read its own notes after each context reset (Effective context engineering for AI agents). Think of the match report a team files after each game: the next coach does not need the video, only the report.

A minimal version for the makerspace, in Python, uses two functions that the program exposes as tools:

import json, pathlib

NOTES = pathlib.Path("notes.json")

def save_note(student_id: str, note: str) -> str:
    """Save one short fact about a student for future visits."""
    data = json.loads(NOTES.read_text()) if NOTES.exists() else {}
    data.setdefault(student_id, []).append(note)
    NOTES.write_text(json.dumps(data))
    return "saved"

def load_notes(student_id: str) -> list[str]:
    """Return saved notes for a student, newest last."""
    data = json.loads(NOTES.read_text()) if NOTES.exists() else {}
    return data.get(student_id, [])

At the start of a session, the program calls load_notes and puts the result in the system prompt or first message. Now the model "remembers" that this student prefers evenings, because the text is on the whiteboard again. The memory lives in the file, and the context window is only where it is shown.

Notes cost tokens too, so keep them short and useful. A note such as "prefers evening slots" is cheap. A pasted transcript is not. A good rule: save facts that would change a future answer, and leave out anything the program can look up again.

Notes grow with every visit, and loaded notes are resent on every call. Example: 30 notes × 20 tokens = 600 tokens, and over 10 calls that is 6,000 input tokens, about $0.018 at $3 per million. Keep each student's notes short. When they pile up, have the program merge old notes into one summary line, or load only the notes that match the question, using the same search idea as for manuals.

A risky mix-up: notes are not permission

Suppose a note says "approved for the band saw," or the student says "a supervisor cleared me yesterday." Neither can decide whether to allow the band saw. A note is a copy that may be stale or wrong, and a claim is only what someone believes.

The permission comes from the system of record, the official database that owns a fact, such as the training database. The assistant reads it through a tool such as check_training_record at the moment of the decision.

  • A note may remind the assistant to check, or tell it which record to check.
  • If the record cannot be read, the answer is "not permitted yet", with a pointer to staff who can confirm.

Retrieval: finding the right page 5 min

Retrieval means fetching only the relevant pieces of a large body of text into the context, at the moment they are needed. It is memory of a different kind from notes: notes hold what the assistant learned, while retrieval holds what a source such as a manual already says. The manuals are too long to load every call, so the assistant must find the right page.

An everyday case: when cooking, you do not read a 200-page cookbook every time you need one step. You look up "braising" in the index, read two pages, and leave the rest of the book on the shelf. The index is the search tool, the two pages are the retrieved chunks, and the counter space is the context window.

Now the numbers, for an assumed 200-page manual at about 400 tokens per page, which is 80,000 tokens, and a request of 4 calls. A chunk is a passage cut from a manual, a few hundred tokens long.

  • Whole manual in the system prompt: 4 × 80,000 = 320,000 input tokens.
  • A search after call 1 returns three 500-token chunks, which is 1,500 tokens. They are resent on calls 2, 3 and 4: 3 × 1,500 = 4,500 input tokens, or 1,500 if the program clears them after use.
  • Ratio: 320,000 / 4,500 is about 71 times fewer tokens.

Recall is also better, because the context stays short.

The pieces of a retrieval system are:

  • Chunking: split each manual into passages of a few hundred tokens, each labeled with its machine and page.
  • Indexing: store each chunk so it can be searched, by keywords, by embeddings (lists of numbers that capture meaning, defined next), or both.
  • Search tool: a tool such as search_manuals(query) that returns the top few chunks, which the model reads like any tool result.

An embedding is a list of numbers that a separate embedding model produces for a piece of text, built so that texts with similar meaning get similar lists.

Closeness is often measured by cosine similarity, cos θ = (a·b) / (|a||b|), where θ is the angle between the two lists read as vectors; 1 means they point the same way. A query and a chunk are compared this way, and the highest scores are returned (the top-k nearest neighbors, as in k-NN). Worked example:

  • a = (1, 2), b = (2, 1).
  • a·b = 1×2 + 2×1 = 4.
  • |a||b| = √5 × √5 = 5.
  • cos θ = 4/5 = 0.8.

The link to statistics: Pearson correlation is cosine similarity after subtracting each vector's mean. Here both means are 1.5, the centered vectors are (−0.5, 0.5) and (0.5, −0.5), and cos θ = −0.5/0.5 = −1, which is r = −1.

import numpy as np
def cos(a, b): return a @ b / (np.linalg.norm(a) * np.linalg.norm(b))
cos(np.array([1, 2]), np.array([2, 1]))   # 0.8

Embeddings match meaning, so "the cutter keeps stopping" can find a page titled "Overheat fault". They can miss exact strings such as an error code "E-47" or a part number. Keyword search, which matches the exact words or strings of the query, catches those. Hybrid search, which uses both, is therefore the usual design; this is general practice, not a claim from the sources here.

Anthropic notes that many applications retrieve in advance this way, and that teams increasingly add "just in time" retrieval, where the agent holds lightweight identifiers, such as file paths or stored queries, and loads data with tools at the moment it needs them (Effective context engineering for AI agents). Their advice for choosing is "do the simplest thing that works."

For the makerspace assistant, a sensible first design is: a short system prompt always loaded, a search tool over the manuals that returns a few labeled chunks, and no manual text in context until the model asks for it.

Worked example and practice 5 min

Worked example

Student 42 returns for a second visit and asks, "Can I book the laser cutter Saturday at 10, and what was that focus setting for 3 mm acrylic?" Decide where each fact comes from.

  1. Identify the facts needed. Saturday availability, permission to use the laser cutter, the focus setting, and how this student likes to be answered.
  2. Availability changes constantly, so use a tool. Call check_calendar("laser cutter", "Saturday"). A saved note would be stale.
  3. Permission is a risky decision, so use the record. Call check_training_record(42, "laser cutter"). Student 42's saved note says "prefers short answers with steps", and the student says staff cleared them for the CNC router last week. The note says nothing about permission and the claim is only a claim, so neither decides it. If the call fails, answer "not permitted yet" and point to staff.
  4. The focus setting is in a long manual, so use retrieval. Call search_manuals("laser cutter focus 3 mm acrylic"). Only the top chunks enter the context.
  5. The preference is stable and personal, so use notes. The note "prefers short answers with steps" was loaded at the start of the session and sits in the system prompt. At the end, save a new note only if it would change a future answer.
  6. Tidy before the next steps. If the manual chunk is large and has been used, clear it from the history before booking, so later calls do not resend it.

Summary 1 min

  • The context window is all the text the model sees on one call: system prompt, tool definitions, messages, tool results and its own output. Nothing else exists for it.
  • Between steps, the program resends the whole history, so input cost rises at every step and large early results are paid for repeatedly. Clear or compact what is no longer needed.
  • Between sessions, nothing survives unless the program saves it. Notes are a store outside the window that the program reloads into it.
  • Retrieval puts only the relevant chunks of a large source into context, found by keyword or embedding search.
  • Notes and claims never decide a risky permission; the record, read through a tool, does.
