Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context (the text it can see on one call), in saved notes, or in a searchable manual, and you can estimate what that choice costs.

Why this matters for you

Your assistant must answer from long machine manuals, and it must know each student's training status between visits, all on a small model budget. Where each fact lives decides whether the answers are correct, whether the assistant is safe, and what each request costs. You will defend these choices at your design review.

The context window: what the model can see 8 min

The context window is all the text the model can look at when it writes a response, including the response it is writing. Example: when a student asks "Can I book the 3D printer on Friday?", the window holds the assistant's instructions, its tool list and that question, and nothing about last week's booking. Anthropic's documentation describes the window as the model's working memory, as opposed to the training data (Claude documentation: context windows). In soccer terms, the players on the pitch can act only on what they can see and hold in their heads right now. Last season's tape stays in the office unless someone brings it onto the pitch.

The window is measured in tokens, the small pieces of text a model reads and writes. A token is often a short word or a fragment of a longer one. As a rough rule, one token is about three-quarters of an English word, so 1,000 words is roughly 1,300 tokens (a rule of thumb, not from the sources below). The ratio varies with the model and with the text, and code and part numbers use more tokens per word. To get exact counts, use the provider's counting tool (token counting).

Three facts follow. First, the window has a hard size limit: input beyond it is rejected. Second, you pay per token, for input (the text sent to the model) and for output (the text it writes), so every token in the window costs money each time the model reads it. Third, the window is the only channel to the model. If a fact is not in the window on a given call, the model cannot use it, however much it "knew" a moment ago.

What fills the window

According to the same documentation, the window holds the system prompt, every message including tool results, documents and images, and your tool definitions. The output counts as well. For the makerspace assistant, that is the following list.

  • The system prompt: the standing instructions ("You are the makerspace assistant. Never book a machine for an untrained student.").
  • The tool definitions: names, descriptions and argument lists for check_calendar, book_slot, search_manuals and check_training_record.
  • The conversation so far: the student's messages, the model's earlier outputs, and every tool result.
  • Anything the program adds on its own, such as the student's saved notes or retrieved manual pages.
Worked example: estimating the fixed part
  • System prompt of 300 words: 300 / 0.75 = 400 tokens.
  • Four tool definitions of 150 words each: 600 words / 0.75 = 800 tokens.
  • Fixed part: about 1,200 tokens.

Real definitions carry argument lists and run larger, so this lesson uses 2,000 tokens for the fixed part. Check your own with the counting tool.

Many current models have a 1,000,000-token window and some older ones 200,000, according to the documentation. Check the number for the model your team picks. Design the assistant so that it does not depend on the window being huge.

What is kept between steps 10 min

Between two steps of the agent loop, the model itself keeps nothing: each step is a separate model call that starts fresh. The program keeps the memory, a list of messages that it sends again in full on every call. Example: after the model requests the training record at call 1, it knows the result at call 2 only because the program sent the request and the result back with the new call. The documentation says the same: each turn's input is the earlier history plus the new message, and the model's output becomes part of the next input (context windows).

Think of a substitute goalkeeper who comes on at every stoppage. The coach (the program) hands over a written match log. The keeper knows only what is in the log and nothing about the half before it. The goalkeeper is the model, and the log is the message list.

In everyday terms, it is a phone call to a help line whose agent forgets you after every sentence. You keep a written transcript and read all of it aloud before each new question, and the line bills by the minute. The agent is the model, the transcript is the message list, reading it aloud is resending it, and the per-minute bill is the per-token price. A longer transcript costs more on every later question.

The loop, with the memory made visible

messages = [{"role": "user", "content": question}]

while True:
    reply = call_model(system_prompt, tools, messages)   # model sees ALL of messages
    messages.append(reply)                               # the program remembers the reply
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_name, reply.tool_args)  # the program runs the tool
    messages.append(tool_result(result))                 # and remembers the result

This is pseudocode, a code-style sketch that is not meant to run: call_model stands for whichever library call your team uses. The point is the list. The variable messages is the only thing that carries information from one step to the next. Delete a line from that list and the model has lost that fact, with no way to notice.

A worked example in tokens

Take the request "Can I book the 3D printer this Friday at 10 am for a 4-hour print, and which filament should I use?" The assumed sizes are:

  • Fixed part (system prompt plus tool definitions): 2,000 tokens. Question: 50.
  • Each tool request from the model: 100.
  • Training record result: 150. Calendar result: 300. Booking confirmation: 80.
  • Manual search result: five chunks (passages of a few hundred tokens cut from a manual; section 5 explains how) of 600 tokens each, 3,000 in total.
Worked example: input tokens per call
  1. Call 1 input: 2,000 + 50 = 2,050. The model replies with a request for check_training_record.
  2. Call 2 input: 2,050 + 100 (its request) + 150 (the record) = 2,300. It requests check_calendar.
  3. Call 3 input: 2,300 + 100 + 300 = 2,700. It requests search_manuals.
  4. Call 4 input: 2,700 + 100 + 3,000 = 5,800. It requests book_slot.
  5. Call 5 input: 5,800 + 100 + 80 = 5,980. It writes the final answer.
  6. Total input tokens billed: 2,050 + 2,300 + 2,700 + 5,800 + 5,980 = 18,830.

The new content added during the whole run is only 50 + 100 + 150 + 100 + 300 + 100 + 3,000 + 100 + 80 = 3,980 tokens beyond the fixed 2,000. The bill is 18,830 because the earlier content is read again on every call.

To see what that costs, pick an illustrative price of $3 per million input tokens (a made-up number for arithmetic, not a real quote). Then 18,830 tokens cost 18,830 × 3 / 1,000,000 = about $0.056. Output tokens are billed too, at a higher illustrative rate of $15 per million. The run writes four 100-token requests and a 200-token answer: 600 tokens, and 600 × 15 / 1,000,000 = $0.009. One run costs about $0.065, and input is about 86 percent of it.

Why longer runs cost more than proportionally

A run with twice as many calls costs more than twice as much, because the content added at each step is reread on every later call. Proof, for a fixed part F and d tokens added per step over n calls:

  • Call k reads F + (k − 1)d tokens.
  • Total = nF + d(0 + 1 + … + (n − 1)).
  • Pair the terms of the sum: (0 + (n − 1)) + (1 + (n − 2)) + … gives n/2 pairs, each equal to n − 1, so the sum is n(n − 1)/2.
  • Total = nF + d × n(n − 1)/2. The first term is linear in n and the second grows with n², so doubling n more than doubles the total.
  • Numbers, with F = 2,000 and d = 1,000: n = 4 gives 8,000 + 6,000 = 14,000; n = 8 gives 16,000 + 28,000 = 44,000, a factor of 3.1.
  • As n grows the factor approaches 4, because the n² term dominates the fixed part.
Providers offer prompt caching, which makes a repeated beginning of the input cheaper. It lowers the price of rereading, but the cached text still occupies the window (context windows). Ask about it later, when you build.
A common mix-up

"The assistant remembers the conversation, so memory is built into the model." It is tempting because chatbots feel continuous. In fact the continuity is the program resending the list. If your program forgets to append a tool result, the model asks for the same tool again, because from its view the result never came. (The provider's API itself rejects a list in which a tool request has no matching result; the same loss happens silently if the program drops an older result.)

A full window is a costly, weaker window 8 min

A long message list is costly and also less accurate. Example: in the 3D printer run, a 3,000-token manual result is reread on every later call, although the answer needed only one line of it. Anthropic's documentation calls the accuracy loss context rot: recall degrades as the token count grows, and "more context isn't automatically better" (context windows). The engineering post frames the window as a finite attention budget, where every token spends some of it, and advises the smallest set of high-signal tokens that gets the job done (Effective context engineering for AI agents).

In statistics terms, each irrelevant token dilutes the signal, like adding noise variables to a regression, so relevance per token matters more than the total. In soccer terms, two pages of scouting the coach can act on beat forty pages that bury the one useful line.

So the program's job is to curate the list, not only to append to it. Three techniques, from lightest to heaviest, are in use today.

  • Clearing old tool results. Once a tool has been called, the raw result is often not needed again. The program replaces the bulky result with a short stub, such as "[manual search result removed]". The engineering post calls this one of the safest, lightest forms of trimming.
  • Compaction. When the list nears the limit, the program asks the model to summarize it, then starts a fresh list holding only that summary. It keeps decisions and open problems and drops repeated tool output. A summary can lose a detail, so use it when clearing is not enough.
  • Handing a sub-task to a helper. A helper agent (a second model run with its own message list) works in its own window and returns only a short summary, often 1,000 to 2,000 tokens, however much it read (engineering post). Whether this pays off belongs to a later lesson.
Worked example: clearing one result

In the 3D printer run, the model used the 3,000-token manual result to write its answer, and the student follows up with a 60-token question. The manual result has served its purpose. Replace it with a 20-token stub before the next call.

  1. Call 6 input without clearing: 5,980 + 200 (the answer) + 60 (the follow-up) = 6,240.
  2. Remove the 3,000 tokens and add 20: 6,240 − 3,000 + 20 = 3,260.
  3. Saving on this call: 2,980 tokens, about 48 percent. Each further call keeps the same saving, so a longer run saves more.
  4. Risk: if the student then asks "what was the exact temperature you found?", the detail is gone from the list. Clear only what the task is finished with, or keep the key fact in the model's own answer or a short note.
Worked example: compaction

A booking session (one conversation, from the first message to the end) has reached 40,000 tokens, 2,000 of them fixed.

  1. The summarizing call reads 40,000 tokens and writes an 800-token summary.
  2. The new list is 2,000 + 800 = 2,800 tokens.
  3. Each later call reads 40,000 − 2,800 = 37,200 fewer tokens.
  4. After two later calls the saving, 74,400 tokens, exceeds the 40,000 the summarizing call read, so compaction pays for itself in input tokens.
  5. Risk: the summary can drop a detail that a later question needs.

In statistics terms, compaction replaces a data set with a summary statistic: the 40,000-token list is the data, the 800-token summary is the statistic, and a later question is a new inference. If the summary is not sufficient for that question, the dropped detail is lost.

Worked example: a helper

A common mix-up

"With a window of a million tokens, I can paste every manual in and skip retrieval (searching the manuals and loading only the relevant pages, section 5)." It is tempting because it removes engineering work. It fails on three counts:

  • Accuracy and recall degrade as the window fills.
  • The size limit is shared with the conversation and the reply.
  • You pay to reread the pasted manuals on every call; section 5 puts numbers on the cost.

What is kept between sessions: notes 9 min

A session is one conversation, from the first message until it ends. When the next session starts, the list of messages is empty. The model remembers nothing about the student's visit last week, for the reason you already know: it sees only what it is sent.

To remember across sessions, the program must save information outside the window and load part of it back in. That saved information is memory, and the simplest form is notes: small files or database rows that the agent writes and later reads.

Anthropic's engineering post calls this structured note-taking: the agent regularly writes notes to storage outside the context window, and the notes are pulled back into the window later (engineering post). The provider's memory tool packages the idea. Claude can create, read, update and delete files that persist between sessions. The tool works on your side: the model requests a file operation, and your application runs it and decides where the files live (memory tool documentation).

Memory lives entirely in your application, so it is a design decision your team owns.

In everyday terms, a café barista forgets every customer overnight but keeps an index card per regular: "oat milk, no sugar". The card is read when the customer arrives and updated when they leave. A wrong card costs little, because the customer corrects it. An allergy is never taken from the card; it is asked about on each order. The barista is the model, the overnight forgetting is the empty list at the next session, the card is the notes store, and the allergy question is the training-record tool you will meet below.

A tiny version of the idea

def load_notes(student_id):
    return notes_db.get(student_id, "")          # your storage: a file, a table

def start_session(student_id, question):
    notes = load_notes(student_id)
    system = BASE_PROMPT + "\nSaved notes about this student:\n" + notes
    return system, [{"role": "user", "content": question}]

def end_session(student_id, messages):
    old = load_notes(student_id)
    prompt = NOTE_PROMPT + "\nExisting notes:\n" + old
    # NOTE_PROMPT: "Rewrite as at most 10 lines: keep durable facts, add new ones, drop stale ones"
    summary = call_model(prompt, [], messages)
    notes_db[student_id] = summary.text

Three design questions hide in these lines. What do you write down: a few durable facts such as "prefers morning slots" and "asked about resin printer settings twice", not a transcript. When do you write: at the end of a session, or as facts appear, in case the session is cut off. And what do you load: only what the next session needs, because loaded notes occupy the window just like any other text, and old notes go stale.

With the provider's memory tool, the model itself writes the note during the session, by requesting a file create or edit. The code above does the same job from the program side at the end of the session, and the ten-line cap lives in the prompt. The tool also nudges the model to look at its memory before doing anything else, because its context may be reset at any moment.

Worked example: notes cost tokens on every call
  1. Twenty note lines of 15 words each is 300 words, or 300 / 0.75 = 400 tokens.
  2. Over a five-call run, that is 5 × 400 = 2,000 input tokens.
  3. At the illustrative $3 per million, that is 2,000 × 3 / 1,000,000 = $0.006 per run.

That is small, but it grows with every note you keep and with every request. Cap the notes, for example at ten lines, and delete stale ones.

A common mix-up: notes are not the truth

A note says "Sam completed laser cutter training." It is tempting to let the assistant book the laser cutter on the strength of that note, or of Sam's own statement, "I finished the training last week." Both are only copies of the real record. The note may be stale, and the claim may be mistaken. Training status is a safety fact, so it is decided from the makerspace's training database, read through a tool at the moment of booking.

Here is the design the makerspace assistant should follow. A note may remind the assistant which check to run ("Sam asked about the laser cutter, so check that record"). The answer itself comes from check_training_record(student_id, machine), called on this request, never from a note, never from the student's claim and never from the model's guess. If that tool fails, or the student is not found, or the record is unclear, the assistant says the booking is not permitted yet and points to a staff member who can confirm. The same holds for booking itself: the booking system, not a note, tells you whether the slot is free.

Retrieval: finding the right page in a long manual 10 min

Retrieval is searching a large collection for the few pieces relevant to the question, and putting only those into the window. Example: for "What power setting for 3 mm birch on the laser cutter?", the program searches the laser cutter manual and puts the two matching passages into the window, not all 120 pages. It is memory of a different kind: not what the assistant wrote down, but a library it can consult. In the soccer analogy, it is the video analyst who pulls three clips of the opponent's corner kicks instead of handing the coach the whole season. The engineering post describes the same pattern as just-in-time retrieval: the agent keeps lightweight references, such as file paths or stored queries, and uses tools to load data into context at runtime (engineering post).

The cost case, in numbers

Worked example: paste the manual or retrieve?

A 3D printer manual has 120 pages of about 500 words each. Use the rule of one token per 0.75 words, and the five-call run from earlier.

  1. Words: 120 × 500 = 60,000. Tokens: 60,000 / 0.75 = 80,000.
  2. Paste the manual into the system prompt: no search is needed, so the run has four calls, each carrying the manual: 82,050 + 82,300 + 82,700 + 82,880 = 329,930 input tokens.
  3. Retrieve five chunks of 600 tokens, once: the run costs 18,830 tokens in total, as computed before.
  4. Ratio: 329,930 / 18,830 is about 17.5. Pasting costs roughly seventeen times more, before counting context rot. Prompt caching would cut the price of the repeated manual, but not its place in the window.

The retrieval route has its own risk, though: if the search returns the wrong five chunks, the answer is missing a page it needed. Retrieval trades cost for the chance of a miss, so you must measure the miss rate. Measuring it means computing recall at k on a labelled set of questions: the share of questions whose correct chunk is in the top k.

How a search finds the right chunk

The program first splits each manual into chunks, passages of a few hundred tokens each (defined in section 2), because a whole manual is too big to rank and a single sentence loses its meaning. Then two search methods are common, and they are often combined.

  • Keyword search (for example the BM25 method) scores chunks by how many of the query's words they contain, giving more weight to rare words. It is excellent for exact strings such as an error code "E-204" or a part name.
  • Embedding search turns each chunk and the query into a list of numbers, an embedding, built so that texts with similar meaning point in similar directions. It finds "the print is weak" when the manual says "increase nozzle temperature", where no words match.
Worked example: why a rare word wins

This is a standard information-retrieval weighting, not from the sources above. Weight each query word by log10(N / df), where N is the number of chunks and df is how many chunks contain the word. Let N = 1,000, the code "E-204" appear in 1 chunk and "printer" in 400.

  1. Weight of E-204: log10(1,000 / 1) = 3.
  2. Weight of printer: log10(1,000 / 400) = 0.40.
  3. Chunk X contains E-204 once: score 3.
  4. Chunk Y mentions printer five times: score 5 × 0.40 = 2.0.
  5. X ranks first.

This weight is the inverse document frequency (IDF) of TF-IDF, a standard text-mining feature. Real BM25 also caps the credit for repeated words, but the rare-word effect is the same.

Embedding search ranks chunks by a similarity score. The common score is cosine similarity: the dot product of the two vectors (the lists of numbers) divided by the product of their lengths, which equals the cosine of the angle between them. It is 1 for the same direction, 0 for unrelated and below 0 for opposite directions.

Worked example: ranking three chunks

The formula is cosine = (q · x) / (|q| |x|), a standard information-retrieval measure that the sources above do not cover. Use two numbers instead of hundreds, so the arithmetic fits on a line. The query vector is q = (3, 4). The chunk vectors are A = (4, 3), B = (1, 0) and C = (−4, 3).

  1. Length of q: √(9 + 16) = 5.
  2. A: dot product 3×4 + 4×3 = 24; length 5; cosine = 24 / (5 × 5) = 0.96.
  3. B: dot product 3; length 1; cosine = 3 / (5 × 1) = 0.60.
  4. C: dot product −12 + 12 = 0; cosine = 0.00.
  5. Rank: A, then B, then C. Top-k retrieval keeps the k highest-scoring chunks: with top-1 only A enters the window; with top-2, A and B.
import math

def cosine(q, x):
    dot = sum(a * b for a, b in zip(q, x))
    return dot / (math.hypot(*q) * math.hypot(*x))

chunks = {"A": (4, 3), "B": (1, 0), "C": (-4, 3)}
q = (3, 4)
ranked = sorted(chunks, key=lambda k: cosine(q, chunks[k]), reverse=True)
top2 = ranked[:2]   # ["A", "B"]

The ranking function is a similarity estimate, so treat the top results as candidates. In a real retriever the vectors have hundreds of numbers and come from a trained embedding model; you call that model as a service and do not train it.

A known weakness, and a published fix

Chunks lose their surroundings. A chunk saying "revenue grew 3 percent" does not say which company or year. In the makerspace, a chunk saying "set power to 60 percent" does not say for which material or machine.

Anthropic's Contextual Retrieval method prepends a short, chunk-specific context, usually 50 to 100 tokens, to each chunk before indexing (storing for search), and combines embeddings with keyword search. In their tests, this reduced the number of failed retrievals in the top 20 chunks by 49 percent (from 5.7 percent to 2.9 percent), and by 67 percent when a reranking step was added. Reranking is a filtering step that passes only the most relevant chunks to the model (Introducing Contextual Retrieval). Those numbers come from their data sets, so measure on your manuals.

A common mix-up

"Retrieval means the model searches the manuals itself." The model does not touch the library. It writes a request for search_manuals with a query, the program runs the search, and the top chunks come back as a tool result. That is the loop you already know, and the chunks occupy the window like any other tool result.

Worked example and practice: the assistant's design 9 min

The skill your design review needs is a decision for each fact: window, notes, or library. Ask three questions, in this order:

  • Needed on every call? Then it belongs in the fixed part of the window, and it must be short.
  • Persistent about this student and harmless if stale? Then it goes in notes.
  • Large, shared and stable, or a fact with an owner such as a booking or a training record? Then it stays outside, and a tool reads it on demand.
Worked example: one request, end to end

Request, in a new session: "Book the laser cutter tomorrow at 3 pm for the same material as last time. What power setting should I use?"

  1. Session start. The program loads this student's notes (short): "Uses 3 mm birch plywood; prefers afternoon slots." These go into the system prompt. "Same material as last time" is answerable only because of the notes, so this is the right place for that fact.
  2. Call 1. The model requests check_training_record(student, "laser cutter"). Training status is a safety fact, so it is read fresh from the training database through a tool, not taken from the notes.
  3. Call 2. The result says trained and current. The model requests check_calendar("laser cutter", "tomorrow"). Availability changes by the minute, so it is not stored anywhere in the assistant.
  4. Call 3. The slot is free. The model requests search_manuals("laser power birch plywood 3 mm"). The program returns two chunks of about 600 tokens, the top-2 by the combined keyword and embedding score.
  5. Call 4. The model requests book_slot. The program runs it and returns a confirmation.
  6. Call 5. The model writes the final answer with the booking and the setting. The program clears the manual chunks from the list if the run continues, and, at the end of the session, saves one new line to the notes: "Booked laser cutter, birch 3 mm."

If the training tool had failed in call 1, the assistant would stop and say the booking is not permitted yet, and direct the student to staff to confirm. It would not fall back on the note.

Summary 3 min

The two kinds of memory are notes, written by the agent per student, and retrieval, a read-only library searched on demand.

  • The model sees only the context window, on each call. Between steps, the program keeps the message list and resends it, so the input bill grows with every step.
  • A long window is costly and weaker, because accuracy degrades as it fills. Clear finished tool results first, summarize when needed.
  • Between sessions, nothing survives unless the program saves it. Notes hold harmless, durable facts about the student. A note never decides a safety question: the training record is read through a tool each time.
  • Retrieval searches a large manual and loads only the best few chunks. Keyword search finds exact codes, embeddings find paraphrases, and combining them lowers misses.
  • Numbers to keep: one token is about 0.75 words; the five-call 3D printer run reads 18,830 input tokens; pasting a 120-page manual costs about 17 times more than retrieving five chunks; Contextual Retrieval cut top-20 retrieval failures by 49 percent, and by 67 percent with reranking.
  • Decision rule: needed every call, short, in the window; durable and harmless, in notes; large, shared or owned by a system of record (the database that officially holds the fact), outside and read by a tool.
