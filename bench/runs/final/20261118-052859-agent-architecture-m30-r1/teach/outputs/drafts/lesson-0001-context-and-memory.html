Lesson 1 · 30 minutes

Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in saved notes, in a retrieval index or in a live record lookup, and you can estimate what that choice costs.

Objective O3: context and memory in an agent About 30 minutes Builds on your work on the agent loop
Why this matters for you

Your assistant must answer from long machine manuals and must know each student's training status at every booking, read from the official record rather than recalled from earlier visits. Your sponsor's budget is small, and both problems are decided by what the model is given on each call. At your design review, you will need to say what the assistant keeps in context, what it saves, and how it finds the right manual page. Two terms used in the goal above: a retrieval index is a searchable copy of the manuals, and a live record lookup is a tool call that reads the official record at the moment of use.

Warm-up 2 min

In your work on the agent loop, you learned that each tool result goes back to the model as input. Predict before you open the answer.

Check your answer

The model sees only what the program sends again with the follow-up. It stores nothing between calls.

That is today's topic: what exactly each call receives, how much of it there is, and what the program must save so that it can be sent again.

The context window 4 min

A token is a small chunk of text, often a short word or part of a word, and it is the unit a model reads and writes. The context window is all the text a model can reference when it produces a response, including the response itself. The documentation calls it the model's “working memory” (Anthropic, context windows). It has a fixed size, measured in tokens. Example: when a student asks the makerspace assistant about vinyl blade depth, the window holds the assistant's rules, its tool list, the whole conversation so far and the answer being written. A step is one model call.

Think of the whiteboard a coach uses at halftime. The coach writes on it the lineup (the system prompt, the fixed role and rules given to the model), the set plays available (the tool definitions, the description of each tool the model may call) and the match notes so far (the message history, every earlier message and tool result). The coach is the program, which writes the board and decides what stays on it; the players are the model, and the board has a fixed size. Before every instruction, the players walk in with no memory and read the whole board from the top. Anything not on the board did not happen for them.

For one call, all four parts count toward the limit: the system prompt, the tool definitions, the message history, and the model's new output added on top. Tool definitions count even though the user never sees them (Anthropic, context windows).

The window matters for two reasons. First, it is a hard limit: a request that does not fit cannot be answered. Second, it is a price: input tokens are billed, so a larger window used in full costs more per call. Some current models allow windows of up to 1M tokens, and most bill long requests at standard rates. Even so, the same documentation says “more context isn’t automatically better,” because accuracy and recall degrade as the token count grows (Anthropic, context windows).

A common mix-up

It is tempting to think the model “remembers” a conversation, the way a person does, because a chatbot appears to. It does not. The model keeps nothing between calls. The program sends the earlier messages again each time, and the model reads them fresh. If the program leaves a message out, for the model that message never happened.

What is kept between steps 5 min

Inside one request (one student question and everything the assistant does to answer it), the agent loop makes several model calls. Between those steps, the only thing kept is the message list the program maintains. After each step, the program appends the model's output and the tool's result, then sends the whole list again. Anthropic describes the effect directly: an agent in a loop “generates more and more data that could be relevant for the next turn of inference” (Anthropic, effective context engineering).

In code, the memory between steps is nothing more than a Python list:

messages = [{"role": "user", "content": question}]
while True:
    reply = call_model(system_prompt, tool_definitions, messages)
    messages.append(reply)                 # model output joins the history
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_request)  # the program runs the tool
    messages.append(result)                # the result joins the history

Each pass through the loop sends everything in messages. Nothing is sent as a small update. That has a direct cost consequence, which you can compute exactly.

Worked example: one request, token by token

A student asks, “What blade depth for 0.5 mm vinyl, and is the vinyl cutter free Thursday at 1 pm?” The sizes are:

  • System prompt and tool definitions together: 2,000 tokens.
  • Question: 50 tokens.
  • Each model tool request: 60 tokens.
  • Manual search result: 1,500 tokens.
  • Calendar result: 300 tokens.

These sizes are illustrative, not measured: measure your own manuals and prompts with a token counter.

  1. Call 1 receives system and tools plus the question: 2,000 + 50 = 2,050 input tokens.
  2. Call 2 adds the first request (60) and the manual result (1,500): 2,050 + 1,560 = 3,610.
  3. Call 3 adds the second request (60) and the calendar result (300): 3,610 + 360 = 3,970. This call writes the final answer.
  4. Total input processed: 2,050 + 3,610 + 3,970 = 9,630 tokens.
  5. The new text across the whole request, not counting the final answer, is only 2,000 + 50 + 120 + 1,500 + 300 = 3,970 tokens, so you were billed for about 2.4 times the amount of text that was actually new (9,630 divided by 3,970).
  6. This counts input only. The model's own output tokens are billed separately, at a higher rate.

Generalize it:

  • B = base tokens (system prompt, tools, question).
  • a = tokens added per step.
  • Call k receives B + (k − 1)a tokens.
  • Total input over n calls = nB + a · n(n − 1) divided by 2.

Proof of the total. Call k receives B + (k − 1)a, so the sum over k = 1 to n is nB + a(0 + 1 + … + (n − 1)). Let S = 0 + 1 + … + (n − 1). Write S forward and backward and add the two rows: each of the n columns adds to n − 1, so 2S = n(n − 1) and S = n(n − 1) divided by 2. Check with n = 4: S = 6, and 500 × 6 = 3,000.

The second term is an arithmetic series (a sum in which each term exceeds the previous one by a constant), so for long runs the total grows roughly with the square of the number of steps. In the worked example the added amount varies by step. The formula treats it as an average, which is enough to see the shape.

Numeric case: take B = 2,000 and a = 500. For n = 10, the total is 20,000 + 500 × 45 = 42,500 tokens. For n = 20, it is 40,000 + 500 × 190 = 135,000 tokens. Doubling the steps multiplies the cost by about 3.2, not 2. For your budget, this is the main reason a loop needs a step limit and short tool results.

Budget check, with an assumed price. If input costs $3 per million tokens (check your provider's current price), the 9,630 input tokens above cost about $0.029 per request, and 1,000 requests cost about $29. Dropping the 1,500-token manual result before call 3 saves 1,500 tokens, about 16% of that request.

Prompt caching means the provider stores a repeated prompt prefix and bills it at a reduced rate. It can lower the price of repeated tokens, but the documentation says it “changes what you pay for those tokens, not whether they count” toward the window (Anthropic, context windows). Treat it as a discount to look into later, not as a way around the limit.
Check yourself

With the same B = 2,000 and a = 500, the agent takes n = 4 calls. What is the total input across the request?

11,000. The calls receive 2,000, 2,500, 3,000 and 3,500 tokens, and these sum to 11,000.

When the context fills up 4 min

Example: a run carries a 6,000-token manual result through 15 more steps. It still fits in the window, yet that text is billed at every step, and the model may recall the student's original question less reliably. That second effect is context rot: the drop in the model's ability to recall information accurately from its context as the number of tokens grows. Anthropic's engineering team describes the context as “a finite resource with diminishing marginal returns” and says the aim is the smallest possible set of high-signal tokens (Anthropic, effective context engineering). A statistician will recognize the shape: past some point, each added token buys less and costs the same.

Three techniques keep a long run inside its budget. Each trades some detail for space.

  • Clearing old tool results. After the agent has used a large result, the raw text rarely matters again. The post calls this “one of the safest lightest touch forms of compaction,” defined in the next item.
  • Compaction. The program summarizes the conversation so far and starts a fresh context holding the summary. This keeps the thread of a long task. The risk is that the summary drops a detail that mattered later.
  • Sub-agents. A second model call with its own clean context does a side task, such as searching manuals, and returns only a short summary. The large intermediate text never enters the main context.

Soccer gives the picture. During a match, the coach does not replay every pass to the players. The program, acting as analyst, reduces the first half to three points, and that summary goes into the halftime talk. That is compaction. The first-half detail is wiped from the board, so if the analyst's three points missed something, the players never see it.

Numeric case: a run has reached 40,000 tokens of history with 10 steps left. A compaction summary of 2,000 tokens replaces it. Each remaining call now carries 2,000 instead of 40,000 history tokens, so the 10 calls save 38,000 × 10 = 380,000 input tokens. The cost is that any detail the summary missed is gone.

Whether to split work across several agents is a design question with its own cost, and a later lesson covers it. Here, note only that it is one way to keep the main context small.
Check yourself

The third option. The result has done its job, and clearing it saves 6,000 × 15 = 90,000 input tokens over the rest of the run.

What is kept between sessions 5 min

A session is one run of the assistant for one request or visit. When it ends, the message list is gone. The next session starts with an empty history, so by default the assistant has no idea who the student is. Anything that must survive has to be written outside the context window and read back in.

Anthropic calls this structured note-taking: the agent “regularly writes notes persisted to memory outside of the context window” and pulls them back in later (Anthropic, effective context engineering). The long-term memory in this picture is an external store, not the model (Weng, LLM powered autonomous agents).

For the makerspace assistant, the mechanism is two small functions. At the start of a session, the program loads the notes for this student and puts them in the context. At the end, the program asks the model for any new facts worth keeping and saves them.

def start_session(student_id):
    notes = notes_store.get(student_id, [])        # saved facts, may be empty
    return [{"role": "user", "content": "Saved notes: " + "; ".join(notes)}]

def end_session(student_id, new_facts):  # the model's proposed facts, reviewed by the program
    notes_store[student_id] = notes_store.get(student_id, []) + new_facts

Everyday version: a sticky note on your fridge says “gym membership paid through June.” The door scanner at the gym ignores the note and checks the gym's own system. The note is the saved note, the gym's system is the training record, the scanner reading it is the tool call, and you saying “I am a member” is the student's claim.

Notes are a copy, and a copy can go stale. This matters most where a mistake has a physical cost. A note that says “Dana completed the lathe training in March” is useful for greeting Dana or for knowing which record to check. It must never decide whether Dana may run the lathe.

That decision rests on the authoritative record, the training database kept by whoever is responsible for it, and the assistant reads it through a tool at the moment of the booking, such as check_training_record(student, machine). A student's own claim, a saved note and the model's guess about who sounds experienced all fail the same test: none of them is the record.

If the tool fails, or the student is not found, the safe answer is “not permitted yet,” with a pointer to makerspace staff who can confirm. The assistant never guesses in either direction.

Saved notes cost tokens too. Loaded notes of 200 tokens ride along in every call of the session. Over a 4-call request that is 800 extra input tokens, so keep notes short and keep only stable facts.

A common mix-up

It is tempting to treat saved notes as the assistant's knowledge, so that anything it once learned about a student can be trusted. Notes only record what was true when they were written. Training can be revoked, expire or have been logged wrongly. So a note may tell the assistant which record to check, and the record gives the answer.

The second option. Preferences are low-risk and stable. Permissions and availability change, and they come from the system that owns them.

Retrieval: finding the right page 5 min

Retrieval means fetching only the relevant text from a larger store and placing it in the context for this call. A machine manual may run to 60,000 tokens. Putting all of it in every call would use most of a small window and, with the arithmetic from earlier, be billed again at every step. Instead, the program searches the manual and adds a few relevant passages. In an agent, this search is usually a tool: the model calls search_manuals(query), and the returned chunks (pieces of the manual, a few hundred tokens each) join the message history like any tool result, as the 1,500-token manual result did in the worked token example.

A common mix-up

It is tempting to think retrieval finds the right page whenever one exists. It returns only the closest chunks. If the right chunk ranks below the cutoff, the model never sees it, and nothing signals the miss.

The usual search method uses embeddings. An embedding is a list of numbers that represents the meaning of a piece of text, produced by a model, so that texts with similar meanings get similar lists. Before any question arrives, the manual is cut into chunks of a few hundred tokens, and each chunk is given an embedding. When a student asks something, the question gets an embedding as well, and the program returns the chunks whose embeddings are closest (Weng, LLM powered autonomous agents, describes the external vector store and fast retrieval behind this).

“Closest” is usually measured by cosine similarity, the cosine of the angle between two vectors: dot product divided by the product of their lengths.

Why this formula: the law of cosines gives |u − v|² = |u|² + |v|² − 2|u||v|cos θ. Expanding the left side directly gives |u|² + |v|² − 2 u·v. Equating the two gives u·v = |u||v|cos θ, so cos θ is the dot product divided by the product of the lengths.

Numeric case with two-number embeddings. The question is q = (3, 4), with length 5.

  • Chunk A = (6, 8): dot product 18 + 32 = 50, lengths 5 and 10, similarity 50 divided by 50 = 1.0.
  • Chunk C = (4, 3): dot product 24, lengths 5 and 5, similarity 24 divided by 25 = 0.96.
  • Chunk B = (4, −3): dot product 12 − 12 = 0, similarity 0.

The program returns A, then C, and ignores B.

Retrieval has a cost and a risk. The cost is the tokens of the returned chunks: three chunks of 400 tokens add 1,200 tokens, against 60,000 for the whole manual. The risk is a miss: if the right chunk is not among the top few, the model never sees it and will answer without it or from training patterns. A miss is silent, so test retrieval on real student questions before trusting it.

There is a second style. Anthropic describes “just in time” retrieval: the agent keeps lightweight identifiers, such as file paths or stored queries, and loads data with tools at runtime, instead of preparing everything up front. The trade-off is stated plainly: “runtime exploration is slower than retrieving pre-computed data.” A hybrid is common, with a small set of stable facts loaded up front and the rest fetched when needed (Anthropic, effective context engineering).

The embedding search above is the pre-computed style: the index (the stored list of chunk embeddings) is built before any question arrives, and the model calling search_manuals(query) only decides when to search. A just-in-time version would keep a list of section titles in the context and give the model a tool such as read_section(manual, section) to open one on demand. For the makerspace, a hybrid fits: machine list and safety rules loaded up front, manuals searched by embedding, and training status read from the record.

Check yourself

Worked example and practice 4 min

Worked example: placing four facts

The assistant handles a request from Sam: “Book the laser cutter Friday at 2 pm, and what power setting for 3 mm acrylic?” Place each fact where it belongs.

  1. Laser cutter power for 3 mm acrylic. It sits in a long manual and is needed for this question only. Use retrieval: search the manual and add the top chunks to the context.
  2. Sam's training on the laser cutter. It is a safety permission. Read it through the training record tool at the moment of booking. A note from last visit may say which machine to check, but it cannot grant the booking.
  3. Sam prefers metric units. It is low-risk and stable. Save it in the notes store at the end of the session, and load it at the start of the next.
  4. The 1,500-token search result, after Sam's power setting has been extracted. It is no longer needed. Clear it from the history so it does not cost tokens at each later call.
Your turn

Alex messages the assistant: “Book the lathe Monday at 10 am.” The saved notes say “Alex finished lathe training in September.” Alex adds, “I am certified, just book it.” First step given: list what each source is allowed to decide. Now finish: what does the assistant do, what happens if the lookup fails, and what goes into the notes afterward?

Show a solution
  1. Alex's claim and the saved note cannot grant the booking. Each is a copy or a statement, not the record.
  2. The assistant calls the training record tool for Alex and the lathe, and decides from the result.
  3. If the record shows current training, it calls the calendar tool and books if the slot is free. If the record shows none, it declines and explains how to get trained.
  4. If the lookup fails or Alex is not found, the answer is “not permitted yet,” with a pointer to makerspace staff who can confirm.
  5. Afterward, it may save a harmless fact such as “Alex books the lathe on Mondays.” It does not save “Alex is certified” as something to rely on later.
Your turn: cost

A manual is 60,000 tokens. Option 1 puts all of it in the context for the 5 remaining calls. Option 2 retrieves three 400-token chunks once, and they stay in the history for the same 5 calls. Compute the input tokens each option adds across those calls.

Show a solution

Option 1 adds 60,000 × 5 = 300,000 tokens. Option 2 adds 1,200 × 5 = 6,000 tokens. Retrieval is 50 times smaller, which is the reason to retrieve.

Summary 1 min

  • The context window is everything the model reads on one call: system prompt, tool definitions, message history and its own output. The model keeps nothing between calls.
  • Between steps, the program resends the growing message list, so total input grows faster than the number of steps: roughly with its square for long runs.
  • Long runs stay cheap and accurate by clearing old tool results, compacting, and using sub-agents.
  • Between sessions, only what the program saves survives. Notes suit stable, low-risk facts, and a record read through a tool decides every safety question.
  • Retrieval puts only the best-matching chunks in context. Test it, because a miss is silent.

Say it in your own words: without looking, explain to a teammate why the assistant is billed for more input than the text that was new, and name what you would load at the start of a visit from a student.
