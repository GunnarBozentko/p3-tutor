Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in saved notes, in a searchable manual, or in an official record read by a tool.

Objective O3: context and memory in an agent About 30 minutes Builds on learning record 0002, "An agent is a model called in a loop, with tools and a way to stop"
Why this matters for you

Your assistant must answer from long machine manuals, remember each student's training status between visits, and stay inside a small model budget. All three problems are context and memory problems. At your design review you will need to say what the assistant keeps, what it saves and how it finds the right page.

Warm-up 2 min

Think of a soccer match. The coach's whiteboard in the dugout is wiped and rewritten as play goes on; it maps to the context window, the text the model sees on one call. The match report filed after the game outlasts the match; it maps to saved notes, information the program stores outside the window. The video analyst pulls the one clip you ask for from hours of footage; it maps to retrieval, finding the few relevant passages in a large store.

A fourth item is the league's official registry of players, which maps to the official record that a tool reads. A coach does not field a player because the match report says he is registered; the referee checks the registry before kickoff. The assistant treats training status the same way.

Recall

A token is roughly three-quarters of an English word. About how many tokens is a 300-word paragraph? Then guess: what does the model receive on its third call in a loop that it did not receive on its first?

Check your answer

300 / 0.75 = 400 tokens. Tokens are what the window and the bill count. On the third call the model receives the material from the earlier calls as well. That growing pile is today's subject.

The context window 3 min

A language model reads text as tokens, which are short pieces of text, roughly three-quarters of an English word each. The context is the set of tokens given to the model for one call, and the context window is the maximum number of tokens that set may hold. Example: a 300-word student question is about 400 tokens, and with a 2,000-token system prompt the context is 2,400 tokens, which leaves 197,600 tokens of room in a 200,000-token window. Anthropic's docs describe the window as the model's "working memory": all the text it can reference when generating a response, including the response itself (Claude docs, context windows). Nothing outside the window exists for the model on that call.

Everything the program sends counts toward the window. That includes the system prompt (the standing instructions), the tool descriptions (the text that tells the model each tool's name, purpose and inputs), every earlier message, every tool result and the new reply. The window is the whiteboard: when it is full, something must be erased, or the call fails. The docs state that an input that exceeds the window alone produces an error.

The window caps what the model can see on one call. It does not set your bill. You are billed for the tokens you actually send and receive, so a fuller context means a more expensive call, every time. The window is the ceiling; the bill follows the tokens in use.

What is kept between steps 5 min

The model itself keeps nothing between calls. Each call starts from zero, and the model sees only the tokens in that call's context. What looks like memory inside a single run is the program resending the whole message history, the list of every request and result so far, with the new item added at the end. That list, plus the system prompt and tool descriptions, is the entire state of the agent within one run.

Here is the loop as code. The list messages is the agent's short-term memory, and the program owns it.

messages = [{"role": "user", "content": question}]

# call_model and run_tool are placeholders, not a real library
for step in range(MAX_STEPS):
    reply = call_model(system_prompt, tools, messages)   # one model call
    messages.append(reply)                  # the model's own output is kept
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool_name, reply.arguments)  # the program runs it
    messages.append(tool_result(result))    # the result is kept

Each pass through the loop sends a longer messages list than the pass before. This is why cost grows faster than the number of steps. Suppose the system prompt and tool descriptions take 2,000 tokens and the question takes 50. Each tool result is 1,500 tokens and each model request is 100 tokens. The input sizes of four consecutive calls are:

CallWhat is in the inputInput tokens
12,050 start2,050
2start + 1 request + 1 result2,050 + 1,600 = 3,650
3start + 2 requests + 2 results2,050 + 3,200 = 5,250
4start + 3 requests + 3 results2,050 + 4,800 = 6,850

The run is billed for 2,050 + 3,650 + 5,250 + 6,850 = 17,800 input tokens, although the last call holds only 6,850. In general, with a start of S tokens and a growth of g tokens per step, n calls cost n·S + g·n(n−1)/2 input tokens: the sum is quadratic in n. Derivation: call i has input S + g(i − 1), so summing over i = 1 to n gives nS + g(0 + 1 + … + (n − 1)) = nS + g·n(n − 1)/2, because the integers 0 to n − 1 sum to n(n − 1)/2. Check with n = 4: 4(2,050) + 1,600(6) = 8,200 + 9,600 = 17,800. Doubling the steps roughly quadruples the growth term.

Prompt caching, which discounts a repeated beginning of the prompt, lowers the price per token, but it does not shrink the window. As an illustration only, take a hypothetical price of $3 per million input tokens. The 17,800 tokens cost 17,800 × 3 / 1,000,000 = $0.053 for this one request. Multiply by your requests per week, and use the real price from your provider.

A common mix-up

"The model remembers what happened earlier in the run." It does not. The model is a function from the tokens it is given to the tokens it writes, and it holds no state of its own. It looks like memory because the program resends the history. If the program drops a tool result from the list, the model has no trace of it, and it will not know anything was removed.

Bigger context also means worse recall. Anthropic calls the effect context rot: as the token count grows, the model's ability to recall information from the context decreases. The article frames context as "a finite resource with diminishing marginal returns" and sets the goal as "the smallest possible set of high-signal tokens" (Anthropic Engineering, effective context engineering).

Research on long inputs found a related pattern: accuracy tends to be best when the relevant text is at the start or end and worse when it sits in the middle (Liu et al., Lost in the Middle). That study tested 2023-era models, and newer models may show a weaker effect, so test your own model. More context is not free, and it is not automatically better.

Keeping the context small 3 min

Because the program owns the message history, the program can edit it. Three edits are standard, from lightest to heaviest. The docs and Anthropic's article describe all three (Anthropic Engineering; Claude docs).

  • Clear old tool results. Replace a result the model no longer needs with a short stub such as "calendar result removed". The article calls this one of the safest, lightest forms of trimming.
  • Compaction. When the history nears the window limit, summarize it and continue with the summary in place of the full text. The article says compaction "typically serves as the first lever in context engineering". A summary should keep decisions and open problems and drop repeated tool output.
  • Hand off to a sub-agent. A second agent does a bulky search in its own fresh context and returns only a short summary, often 1,000 to 2,000 tokens. You will meet this again when we discuss splitting work across agents.

Return to the table. Suppose that before call 4 the program clears results 1 and 2, replacing each 1,500-token result with a 20-token stub. Call 4 shrinks by 2 × 1,480 = 2,960 tokens, from 6,850 to 3,890. The model answers just as well if it no longer needs those calendar rows. Clearing is a decision, though: a cleared result is gone, and a wrong clear loses information the model needed.

Compaction is lossy by design. A summary written by a model can drop a detail, such as a student's allergy to a material. Tune what the summary must keep before tuning how short it is.

What is kept between sessions 5 min

A session is one conversation or run. When it ends, the message history is gone unless the program saved it, and the next session starts with an empty list. To remember something across sessions, the program must write it to storage outside the context window and read it back into the next session. Anthropic's article calls this structured note-taking: the agent regularly writes notes persisted to memory outside the context window, which are pulled back in later. This is the match report from the warm-up.

The Claude memory tool shows the standard design. Claude asks to create, read, update or delete files in a /memories directory. The tool is client-side, which means that your application runs each operation and returns the result, so memory lives entirely in your application (Claude docs, memory tool).

The model writes the notes, but your code decides where they are stored. The docs also put security on you: your handler (the code that runs each memory operation) must reject paths outside /memories and cap file sizes. A minimal version is a per-student file:

import os
os.makedirs("notes", exist_ok=True)

def read_notes(student_id):
    # validate student_id (letters and digits only) before building the path
    path = f"notes/{student_id}.txt"
    return open(path).read() if os.path.exists(path) else ""

def save_note(student_id, text):
    with open(f"notes/{student_id}.txt", "a") as f:
        f.write(text + "\n")

# at the start of a session, put the notes in the context:
system_prompt += "Notes about this student:\n" + read_notes(student_id)

The function save_note is exposed to the model as a tool, so the model decides what is worth saving. The program can also write a summary note itself when the session ends.

The notes are loaded into the context, so they cost tokens on every call. Keep them short and about what changes the assistant's behavior, such as "prefers morning slots" or "asked about laser cutter lenses last visit". Writing a note does not teach the model anything, since training is out of scope here and no weights (the numbers the model learned in training) change. The next session simply reads the file.

Notes are loaded whole. After 50 visits a student's file may hold 5,000 tokens, which is too many to load every time. At that point notes need the same treatment as manuals: store them as chunks (passages of a few hundred tokens) and retrieve (look up by similarity to the question) the few that match. Notes and retrieval are one idea at two scales: external memory read back in on demand.

A common mix-up

"If the assistant saved a note that Sam is trained on the laser cutter, it can book the laser cutter for Sam." This is tempting because the note feels like knowledge, but a note is a copy: it may be stale, or it may record only Sam's own claim. Booking a machine that can injure someone must rest on the system of record, the one database that is the authority for a fact, here the makerspace training database, read through a tool at the moment of booking, for example check_training_record(student_id, "laser_cutter"). The note may remind the assistant which record to check. It never answers the question itself. If the record cannot be read, the answer is "not permitted yet" and a pointer to staff who can confirm.

Retrieval from a long manual 5 min

Suppose the manuals total 120 pages at about 500 tokens a page, which is 60,000 tokens. Putting them all in the context would add 60,000 tokens to every call. Over a four-call run, that is 240,000 input tokens for the manuals alone, and the relevant paragraph would be buried, the middle-of-the-context problem again. Retrieval avoids this: the program finds the few passages that matter and puts only those in the context. This is the video analyst pulling one clip.

The usual method has three parts:

  • Split each manual into chunks, passages of a few hundred tokens.
  • Turn each chunk into an embedding, a list of numbers chosen so that texts with similar meaning get similar lists.
  • At question time, embed the question, rank chunks by closeness, and return the top k (k is how many chunks you keep, for example 3).

Closeness is usually measured by cosine similarity, the cosine of the angle between two vectors (u·v divided by |u||v|). It is 1 for the same direction and 0 for unrelated ones.

A toy case with two-number embeddings: the question is q = (3, 4), and the chunks are A = (6, 8), B = (4, −3) and C = (1, 0).

  • A: (18 + 32) / (5 × 10) = 1.0
  • B: (12 − 12) / (5 × 5) = 0
  • C: 3 / (5 × 1) = 0.6
  • Ranking: A, C, B. With k = 2, the context gets chunks A and C.
import math
def cosine(u, v):
    dot = sum(a * b for a, b in zip(u, v))
    return dot / (math.hypot(*u) * math.hypot(*v))

q = (3, 4)
chunks = {"A": (6, 8), "B": (4, -3), "C": (1, 0)}
ranked = sorted(chunks, key=lambda c: cosine(q, chunks[c]), reverse=True)
top_k = ranked[:2]   # ['A', 'C']

In your assistant, retrieval is a tool like any other, for example search_manuals(query, machine). The model writes the query, the program runs the search and the top chunks come back as a tool result. The model does not search the manuals itself. Anthropic describes this style as just-in-time retrieval: the agent keeps lightweight identifiers, such as file paths or stored queries, and loads data into the context at runtime with tools, instead of loading everything up front (Anthropic Engineering).

Retrieval can fail in two ways, and your statistics background names them.

  • Recall is the share of the relevant chunks that were retrieved. Low recall means a chunk that holds the answer is not in the top k.
  • Precision is the share of retrieved chunks that are relevant. Low precision means the top k is full of irrelevant text.

Tests with real student questions measure both. Exact terms such as a machine's model number are often better matched by keyword search (matching the exact words) than by embeddings, so many systems combine the two (Anthropic, Contextual Retrieval). Whatever is retrieved is added to the history, so it also grows the context. With k = 3 and 500-token chunks, one search adds 1,500 tokens rather than 60,000.

A common mix-up

"A model with a very large window makes retrieval unnecessary." It is tempting, since a window of a million tokens fits all your manuals. But every call would pay for those tokens, and the model would recall them less reliably as the context grows. Retrieval and a small context stay the cheaper and more accurate default.

Worked example and practice 5 min

Worked example

A student returns for a second visit and asks, "Book me the laser cutter on Friday at 3 pm, and remind me what focus height we discussed." Decide where each piece of information comes from.

  1. Standing material. The instructions and the tool descriptions go in the context on every call, because the model needs them at every step.
  2. Last visit's detail. The focus height was discussed last session, so the history is gone. The program loads the student's notes at session start. If a note says "laser cutter: focus 6 mm for 3 mm acrylic", the assistant can answer from it. The manual can confirm it by retrieval, since a note may be wrong.
  3. The booking. The assistant calls check_calendar("laser_cutter", "Friday"). The calendar is the system of record for free slots (the one database that is the authority for that fact), so it is read by a tool now.
  4. The permission. The assistant calls check_training_record(student_id, "laser_cutter") before booking. A note saying "trained" does not decide it, and neither does the student saying so.
  5. Trimming. After the booking is made, the 1,500-token calendar result can be cleared from the history. At session end, the program saves one short note, such as "booked laser cutter Friday 3 pm", to the notes store.

Summary 2 min

  • The context window is the cap on tokens read and written in one call. The model keeps nothing between calls: the program resends the history.
  • History growth makes cost quadratic in steps, and larger contexts recall worse. Keep the smallest set of high-signal tokens by clearing, compacting or handing off.
  • Between sessions the history is lost. Only notes the program saves in storage outside the context survive, and they cost tokens when loaded.
  • Long manuals are retrieved in chunks, a few per question, through a tool the program runs.
  • Safety-relevant facts, such as training status, come from the official record read by a tool, never from a note or a claim.
